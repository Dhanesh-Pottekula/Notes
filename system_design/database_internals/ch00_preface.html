01 · PREFACE

From a few relational choices to a crowded field

pdf p6–7 · cites [DECANDIA07]

Almost every business and most software depend on distributed databases. The split of work is simple: the application holds the logic and the user interface; the database looks after data integrity, consistency and redundancy.

In 2000 you had just a few options when choosing a database, most of them relational, so the differences between them were relatively small. They weren't identical, but they did similar things for similar uses.

Some systems already focused on horizontal scaling (scaling out): many database instances acting as one logical database, to gain speed and capacity. The book names the Gamma Database Machine Project, Teradata, Greenplum and Parallel DB2. Horizontal scaling is still one of the properties customers expect most, and the author ties that to cloud services: it is often easier to start a new instance and add it to the cluster than to scale vertically (scaling up) by moving the database onto a bigger machine. Those migrations can be long and painful, and may mean downtime.

Around 2010 a new class of eventually consistent databases appeared, along with the words NoSQL and later big data. Over the 15 years before the book (2019), open-source communities, large internet companies and vendors built so many databases and tools that it's easy to get lost in their uses and details.

The Dynamo paper [DECANDIA07], published by an Amazon team in 2007, had a huge impact and quickly inspired many variants. The most prominent: Apache Cassandra (created at Facebook), Project Voldemort (LinkedIn) and Riak (former Akamai engineers). Now the field is shifting again: after key-value stores, NoSQL and eventual consistency, we see databases that scale and perform well and run complex queries with stronger consistency guarantees.

Picture it

A shop that outgrows its counter. Scaling up is moving the whole shop into a bigger building: you close for the move, and one day there is no bigger building to rent. Scaling out is opening more counters side by side: no closing day, but now the counters must agree on stock, prices and who served whom. The rest of the book is mostly about that "agreeing" cost.

Model: scale up vs scale out over three years

The book makes a qualitative claim: adding a node is often easier than migrating to a bigger box, which can mean downtime. This model puts rough numbers on it. (model, not in the book)

What's happening behind it

Assumptions (all mine): demand starts at 100 units and grows by the slider each month (x-axis = months 0–36). Scale up: start on a 200-unit box; when demand passes 80% of the box, migrate to a box twice as big (each move = one downtime window, dashed line). The biggest box you can buy is 16× the first (3,200 units). Scale out: each node gives 100 units on its own; add a node (online, no downtime) whenever demand passes 80% of cluster capacity. Cluster capacity follows Gunther's Universal Scalability Law: X(n) = 100·n / (1 + σ(n−1) + κ·n(n−1)), where σ is time lost to contention (waiting on shared things) and κ is time lost keeping nodes coherent (talking to each other).

What to notice: scale-up costs one downtime window per doubling and hits a hard ceiling. Scale-out never stops for a migration, but each extra node adds less than the one before. With κ > 0 the curve even peaks at n* = √((1−σ)/κ) nodes, after which adding nodes makes things slower. Set growth to 12% and κ to 60 to see both ceilings. That coordination cost is exactly what Part II of the book studies: failure detection, leaders, replication, consensus.

Beyond the book: what "Dynamo-style" means in numbers

The preface only names Dynamo. Here is what the paper itself reports, so the name carries real content (DeCandia et al. 2007, the book's [DECANDIA07]):

  • Techniques (paper's Table 1, §4): consistent hashing for partitioning; vector clocks with reconciliation during reads; sloppy quorum and hinted handoff for temporary failures; anti-entropy with Merkle trees for permanent failures; gossip-based membership and failure detection.
  • Latency target (§2.2): an example service SLA is a response within 300 ms for 99.9% of requests at a peak of 500 requests/s. Amazon measured at the 99.9th percentile, not the mean.
  • Common config (§6): (N, R, W) = (3, 2, 2): 3 copies, a read waits for 2 replies, a write for 2 acks.
  • How often replicas really diverged (§6.3): over 24 hours of the shopping-cart service, 99.94% of requests saw exactly one version; 0.00057% saw 2, 0.00047% saw 3, 0.00009% saw 4.
  • A measured trade-off (§6.1): buffering writes in memory cut 99.9th-percentile latency by about 5× at peak, even with a buffer of a thousand objects, at the cost of durability (a crash can lose buffered writes).

Try it: why (3, 2, 2) works (model, not in the book)

A write is acknowledged by W of the N replicas; a later read asks R replicas. If R + W > N, every read set must overlap every write set, so at least one replica you read has the newest value. Pick values and see the chance that a read meets only stale replicas (read set chosen at random, before any background repair).

What's happening behind it

Shaded = holds the new write (W replicas). Outlined = asked by this read (R replicas). The stale-read chance is C(N−W, R) ÷ C(N, R): the number of ways to pick all R readers from the N−W replicas that missed the write, over all ways to pick R. With (3, 2, 2) that is 0, because 2 + 2 > 3. With (3, 1, 1) it is 2⁄3. Raising R or W buys consistency with latency and availability (more nodes must answer). Chapter 11 treats quorums properly; Dynamo's sloppy quorum relaxes this guarantee during failures.

Beyond the book: what "stronger consistency" costs

The preface ends with databases that offer stronger guarantees. Google's Spanner (the "Spanner paper" mentioned on pdf p10; the bibliography lists it as [CORBETT12]) is the usual example. Its TrueTime clock API returns an interval, not a point, and the paper reports the uncertainty ε as a sawtooth of about 1 to 7 ms, so about 4 ms most of the time (§3). Worked example: the time daemon polls every 30 s and assumes a worst-case drift of 200 µs/s, so ε grows by 30 × 0.2 ms = 6 ms between polls; about 1 ms more comes from the round trip to the time masters. That is where "1 to 7 ms" comes from. Before a commit becomes visible, Spanner waits out the uncertainty ("commit wait"); in the paper's single-replica benchmark that wait was about 5 ms, and Paxos added about 9 ms (§5.1). Strong consistency is bought with milliseconds on every write.

02 · AUDIENCE OF THIS BOOK

Who it's for, and the gap it fills

pdf p8–9

At conferences the author keeps hearing the same question: how do I learn database internals, and where do I even start? His answer explains the book. Most database books skip the details of storage engine implementation and treat access methods such as B-Trees at a high level. Very few cover newer ideas such as B-Tree variants and log-structured storage, so he usually tells people to read papers.

But papers are hard: you often lack context, the wording can be ambiguous, papers don't connect to each other, and they are hard to find. The book gives short summaries of the important concepts, so it works as a guide for going deeper and as a cheat sheet for people who already know the material.

You don't have to want to build a database. It is aimed at people who build software on databases: software developers, reliability engineers, architects and engineering managers. If your company depends on any infrastructure component (a database, a message queue, a container platform, a task scheduler), you have to follow its change-logs and mailing lists. Knowing the terms and the internals lets you get more out of those, use your tools better, and troubleshoot, identify and avoid risks and bottlenecks. When something breaks, you can form a hypothesis, validate it, find the root cause, and present it to the project's maintainers.

It is also for curious people who learn without an immediate need: those who hack on compilers, home-made operating systems, text editors or games, or pick up new languages for fun. Assumed background: some experience developing backend systems and using databases; knowing common data structures helps you go faster.

Picture it

Reading papers alone is like finding a city with single photographs of streets: each is sharp, but you can't tell how they join. The book is the street map that shows which photo connects to which, so you can then go and look at any one street in detail.

03 · WHY SHOULD I READ THIS BOOK?

A shared vocabulary that doesn't go out of date

pdf p10

Engineers describe databases by the algorithms inside them. The author lists typical remarks, each with the chapter that explains it: a system spreads membership by gossip (Ch.12); a team has implemented Dynamo; a design resembles the Spanner paper (Ch.13); ZAB and Raft are much alike (Ch.14); Bw-Trees are B-Trees built on log-structured storage (Ch.6); a tree uses sibling pointers as Blink-Trees do (Ch.5).

Such shortcuts let us discuss hard ideas without redefining terms every time, so attention moves to higher-level problems. Fundamental concepts, proofs and algorithms don't age. New ones keep coming, but they are often made after someone finds a flaw or room for improvement in a classic, so knowing the history explains the differences and the motivation. The author also finds it inspiring and rewarding: you see how the industry solved one problem after another, and the pieces click into a full picture you can share.

Picture it

Doctors say "MI" instead of "the blood supply to part of the heart muscle was blocked". The shortcut is only useful because everyone in the room knows what is behind it. This book teaches what is behind each database shortcut.

Measure it: how fast does gossip reach everyone? (simulation, not in the book)

The first phrase is the easiest to measure. In each round, every node that knows the news tells f random other nodes. The claim you will meet in Ch.12 is that the news reaches all N nodes in about log N rounds. Here 100 runs are pooled for each setting, so you see the spread, not one lucky run.

// one synchronous push round: everyone who knew at the START of the round tells f random peers function gossipRun(N, f, rand) { const knows = new Array(N).fill(false); knows[0] = true; let count = 1, rounds = 0, msgs = 0; const curve = [count / N]; while (count < N) { rounds++; const senders = []; for (let i = 0; i < N; i++) if (knows[i]) senders.push(i); for (const s of senders) for (let k = 0; k < f; k++) { let p = Math.floor(rand() * (N - 1)); if (p >= s) p++; // a random peer that isn't me msgs++; if (!knows[p]) { knows[p] = true; count++; } } curve.push(count / N); } return { rounds, msgs, curve }; }
What's happening behind it

Early on, the number of informed nodes multiplies by up to (1 + f) each round, so the growth phase takes about log1+f N rounds. The last few holdouts are slow: each one is missed by everyone with a probability near e−f per round, which adds about (ln N) ⁄ f rounds. Together, rounds ≈ log1+f N + (ln N) ⁄ f (a rough approximation; for f = 1 it is Pittel's classic log₂ N + ln N result, not in the book). The pooled simulation lands about one round above this estimate. Going from 64 to 4,096 nodes (64× more) adds only about 10 rounds at f = 1 (check it with the selector). Raising f buys speed with more messages per node per round, the redundancy trade-off Ch.12 discusses.

04 · SCOPE OF THIS BOOK

Storage engine and distribution: the inside, not the user's view

pdf p11

This is not a book about relational databases, nor about NoSQL. It is about the algorithms and concepts used in all kinds of database systems, focused on the storage engine and the components responsible for distribution.

Some topics are left to existing database textbooks: query planning, query optimization, scheduling, the relational model and a few more. Those books often describe them from the user's side; this one stays on the internals. Pointers to that literature are in the Part II Conclusion and in the chapter summaries. Query languages are not discussed at all, because the systems in the book share no common language.

To gather the material the author studied over 15 books, more than 300 papers, countless blog posts, source code, and the documentation of several open-source databases. His rule of thumb for including a concept: do people in the database industry and in research circles talk about it? If yes, it went on the list.

Picture it

A car magazine reviews dashboards, seats and how the car drives. This book opens the bonnet: the engine (storage) and the gearbox that shares power between the wheels (distribution). It skips the dashboard (query language) and the satnav (query optimizer) because good manuals for those already exist.

What's happening behind it

The layer names come from the book's DBMS architecture (transport, query processor, execution engine, storage engine: Part I introduction, pdf p19, and Ch.1). The colouring is my reading of p11: highlighted = the book's focus; struck out = left to other books; plain = described only as context. The split makes sense because the storage engine and the distribution layer are what change from system to system, while SQL planning theory is shared and well documented elsewhere.

05 · STRUCTURE OF THIS BOOK

Two axes: how data is stored, how it is distributed

pdf p12–13 · cites [SCHWARZ86]

Extensible databases with pluggable components exist (the book cites the Starburst system, [SCHWARZ86]) but are rare. Pluggable storage, on the other hand, is common. Likewise, vendors rarely talk about query execution but are very keen to talk about how they keep data consistent.

So the biggest differences between database systems sit on two axes: how they store data and how they distribute it. (Other subsystems sometimes matter too, but the book doesn't cover them.) Part I covers storage, Part II distribution.

Part I is about what happens on one node, centred on the storage engine, which the author calls the central component of a database and one of its biggest differentiators. It starts with DBMS architecture and ways to classify databases by primary storage medium and layout; moves to storage structures (disk-based vs in-memory), introduces B-Trees and the algorithms to maintain them on disk, including serialization, page layout and on-disk representation; then covers many B-Tree variants; and ends with several kinds of log-structured storage, used for file and storage systems, with the reasons to use them.

Part II is about organising many nodes into a cluster. It starts with why theory matters for fault-tolerant systems, how distributed systems differ from single-node programs, and the problems and constraints they face. Then come the distributed algorithms, in order: failure detection (notice failures, avoid failed nodes, which helps performance and stability); leader election, because many later algorithms rely on a leader; replication, consistency models, replica divergence and eventual consistency, since consistency is one of the hardest problems; anti-entropy and gossip, which eventually consistent systems use to converge and spread data; transactions (logical consistency); and finally consensus.

The author stresses that the book would have been impossible without the research and publications it draws on. References to them appear in square brackets in a monospace font, such as [DECANDIA07]; use them to dig deeper. Each chapter ends with a summary listing material for further study.

Picture it

Two dials on every database: a "storage" dial (B-Tree … LSM) and a "distribution" dial (one node … leader with followers … consensus … leaderless quorums). Most product pages are just a description of where those two dials are set.

Check yourself

answer before you open
1. According to the preface, what is the split of work between an application and its database?

The application provides logic and the user interface; the database takes care of data integrity, consistency and redundancy (section 01).

2. Why does the author say horizontal scaling stays so important, and what is the downside of scaling up?

Cloud services make it easy to start an instance and add it to a cluster. Scaling up means migrating to a bigger machine, which can be long, painful and cause downtime (section 01).

3. Name the three prominent Dynamo-inspired systems and where each came from.

Apache Cassandra (Facebook), Project Voldemort (LinkedIn), Riak (former Akamai engineers) (section 01).

4. With Dynamo's common (N, R, W) = (3, 2, 2), why can a read not miss the latest acknowledged write when no failures happen? What changes with (3, 1, 1)?

R + W = 4 > 3, so any 2 replicas read must include at least one of the 2 that acknowledged the write. With (3, 1, 1), the write reaches one replica and the read asks one; two of the three replicas are stale, so a random read is stale 2⁄3 of the time (section 01 model). Dynamo's sloppy quorum weakens the guarantee during failures.

5. Spanner's clock uncertainty grows by 200 µs per second between polls 30 seconds apart. How much is that, and why does it matter for writes?

6 ms, plus about 1 ms of communication delay: the "1 to 7 ms" sawtooth. Commits must wait out this uncertainty (commit wait, about 5 ms in the paper's benchmark), so stronger consistency costs latency on every write (section 01, beyond the book).

6. What four problems with reading research papers does the author list?

You often lack context, the wording can be ambiguous, papers have little or no connection to each other, and they're hard to find (section 02).

7. What troubleshooting procedure does the author say internals knowledge enables?

Form a hypothesis, validate it, find the root cause, and present it to the project's maintainers (section 02).

8. Match the phrases to chapters: gossip, Spanner, ZAB/Raft, Bw-Trees, Blink sibling pointers.

Gossip → Ch.12; Spanner → Ch.13; ZAB and Raft → Ch.14; Bw-Trees → Ch.6; Blink-Trees → Ch.5 (section 03).

9. Gossip with fan-out 1 takes about how many more rounds for 4,096 nodes than for 64? Why so few?

About 10 more: log₂ N + ln N goes from about 10.2 to about 20.3. Informed nodes roughly double each round, so 64× more nodes costs only log₂ 64 = 6 extra doubling rounds plus about 4 more for the stragglers (section 03 simulation).

10. Which topics does the book deliberately leave out, and why are query languages skipped?

Query planning, query optimization, scheduling, the relational model and a few others (covered in textbooks). Query languages are skipped because the systems discussed share no common language (section 04).

11. What was the author's rule of thumb for including a concept, and how much did he read?

Whether people in the database industry and research circles talk about it. He studied over 15 books, more than 300 papers, many blog posts, source code and documentation (section 04).

12. Why does the book split into storage (Part I) and distribution (Part II)?

Because the most significant differences between database systems are how they store and how they distribute data. Pluggable storage is common and vendors love discussing consistency, while extensible databases (like Starburst, [SCHWARZ86]) and talk of query execution are rare (section 05).

13. Why does leader election come before replication and consensus in Part II?

Many of the later algorithms rely on the concept of leadership, so it is introduced first (section 05).
