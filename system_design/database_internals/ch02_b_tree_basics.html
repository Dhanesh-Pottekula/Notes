B-Tree basics: why databases stopped using binary trees on disk

The whole chapter in plain words and in the book's order: why a binary search tree is fine in memory but bad on disk, what spinning disks and SSDs force on a data structure, and how a B-Tree answers that with wide nodes, separator keys, splits and merges. Every tree on this page is a live simulation you can step through, and the same code that drives it is printed in plate 18. Numbers marked "modelled" come from stated assumptions, not from the book or from benchmarks.

01 · CHAPTER OPENING

Why we need another kind of tree

pdf p56

Chapter 1 split storage structures into two families: mutable and immutable. Most mutable structures update data in place: an insert, update or delete changes the record directly where it sits in the file.

Real engines often keep several versions of one record (for example with multiversion concurrency control, or inside slotted pages). To keep things simple, this chapter assumes each key has exactly one record at one location.

The B-Tree is one of the most popular storage structures. Many open-source databases are built on it, and over the years it has proved to cover most use cases. It isn't new: Rudolf Bayer and Edward M. McCreight introduced it (the text says 1971; the bibliography entry [BAYER72] is their 1972 Acta Informatica paper). By 1979 there were already many variants, which Douglas Comer collected and organised in his survey [COMER79].

Before getting to B-Trees, the chapter asks why we can't simply use the classic search trees: binary search trees, 2-3-Trees and AVL trees [KNUTH98].

Picture it

An in-place structure is a whiteboard: to change a number you wipe it and write the new one in the same spot. An immutable structure is a notebook: you never erase; you write the new value on a fresh line and remember which line is current. This chapter is about the whiteboard.

02 · BINARY SEARCH TREES

A sorted tree with two pointers per node

pdf p57–58 · Fig 2-1, 2-2

A binary search tree (BST) is a sorted, in-memory structure for fast key-value lookups. Each node holds a key, the value for that key, and two child pointers (that's the "binary"). The tree starts from one node, the root; a tree has exactly one root.

The rule that makes it searchable: every node splits the key space into a left subtree and a right subtree. The node's key is greater than every key in its left subtree and less than every key in its right subtree [SEDGEWICK11].

  • Keep following left pointers down to the leaf level (nodes with no children) and you reach the smallest key. Keep going right and you reach the largest.
  • Values can live in every node, not just at the bottom.
  • A search starts at the root and can stop early, on a higher level, if it meets the key on the way down.
Picture it

A game of "higher or lower". At each node you ask one question, "is my key smaller or bigger than this one?", and the answer throws away a whole side of the tree. Orange numbers on the drawing are the order in which you asked.

What's happening behind it

The invariant "left < node < right" holds at every node, not just the root. That's why one comparison is enough to discard a subtree: everything in the discarded side is guaranteed to be on the wrong side of your key. The cost of a search is the number of nodes on the path, so the shape of the tree decides the speed. That's the next section.

Worked example

Same keys and shape as the book's Figure 2-1, built by inserting 5, 2, 6, 1, 4, 7, 3. Looking up 3: 3 < 5 → left; 3 > 2 → right; 3 < 4 → left; 3 = 3, found. Four comparisons, four nodes visited. Looking up 2 stops at the second level after two comparisons: the "stop early" case.

03 · TREE BALANCING

Insert order can turn a tree into a linked list

pdf p59–60 · Fig 2-3, 2-4

Inserts arrive in no particular pattern, so a BST can become unbalanced: one branch longer than the other. The worst case is a pathological tree that looks like a linked list, and lookups go from logarithmic to linear. Petrov admits the extreme example exaggerates a little, but some keys will certainly pile up on one side, and that alone slows searches noticeably.

A balanced tree is defined as one whose height is log₂N (N = number of items) and where the heights of the two subtrees differ by at most one [KNUTH98]. (Footnote 1: that strict rule is the AVL tree's; more generally, BSTs keep the height difference within a small constant factor.) Without balancing, the order of inserts and deletes decides the shape, and the BST loses its advantage.

In a balanced tree each step left or right halves the remaining search space on average, so a lookup is O(log₂ N). Unbalanced, the worst case is O(N).

So instead of letting one branch grow, the tree is rebalanced after each operation: nodes are reorganised to keep the height minimal and the node counts on each side within bounds. One way is a rotation. If an insert leaves a branch where two consecutive nodes each have only one child, rotate around the middle node. That middle node, the pivot, moves up one level and its old parent becomes its right child.

A rotation, step by step (the book's Figure 2-4 case)

Picture it

A coat hanger with everything hung on one end tips over. A rotation is grabbing the hanger by a point nearer the middle so it hangs level again. Nothing is added or removed; the same keys just hang from a different point.

What's happening behind it

A rotation changes only three pointers, and it keeps the sort order: 2 < 3 < 5 before and after. Rotations are cheap in memory. The trouble (plate 4) is that on disk each moved node may live on a different page, so "three pointer changes" can mean three page writes, after nearly every insert.

Measured on simulated inserts: how tall do trees really get?

Simulation (not in the book): for each size, 60 random insert orders with a fixed seed, pooled. Sorted input is left off the chart because its height equals the number of keys (2,048 at the right edge).

Worked example

15 keys. Perfectly balanced: height 4, because 2⁴ − 1 = 15. Inserted in sorted order without balancing: height 15, so the worst lookup does 15 comparisons instead of 4. Tick "rebalance" with sorted order: rotations bring it back to height 4.

04 · TREES FOR DISK-BASED STORAGE

On disk, every pointer you follow can be a seek

pdf p61–62

Unbalanced trees are O(N) in the worst case; balanced ones give O(log₂ N) on average. But because a BST has low fanout (defined here as the maximum number of children per node, so 2), it must rebalance, move nodes and update pointers often. That maintenance cost makes BSTs impractical on disk [NIEVERGELT74]. Keeping a BST on disk hits two problems:

  • Locality. Keys arrive in random order, so a new node isn't necessarily written near its parent. Child pointers can jump across several disk pages. Laying the tree out differently helps somewhat (paged binary trees, plate 8).
  • Height. With fanout 2, height is log₂ of the number of items, so a lookup needs O(log₂ N) seeks and the same number of disk transfers. 2-3-Trees and other low-fanout trees share the problem: fine in memory, but their small nodes make them impractical for external storage [COMER79].

A naive on-disk BST would do as many seeks as comparisons, because nothing in it keeps related keys together. So a disk-friendly tree needs:

  • High fanout, so neighbouring keys sit together (locality).
  • Low height, so a traversal does few seeks.

The book's note: fanout and height move in opposite directions. More children per node means fewer nodes and a shorter tree.

Picture it

Finding a word in a dictionary whose pages are scattered across town. A binary tree makes you drive to a new building after every single "before or after?" question. A wide node is one building where you can ask hundreds of questions before you need to drive again.

What's happening behind it

With fanout f, h levels can address about fʰ items, so h ≈ log_f(M) = log₂(M) ÷ log₂(f). Going from fanout 2 to fanout 256 divides the number of levels by log₂ 256 = 8. The comparisons don't go away (binary search inside each node still does about log₂ M of them); they just happen inside pages already in memory, where they cost nanoseconds instead of milliseconds.

Worked example (modelled)

1 billion keys. Balanced BST on disk: height ⌈log₂(10⁹+1)⌉ = 30, so 30 random page reads; at an assumed 10 ms each, 300 ms per lookup. B-Tree with fanout 256: ⌈log₂(10⁹) ÷ 8⌉ = 4 levels, 4 reads, 40 ms; and since the top levels are small enough to stay in RAM, in practice often 1 disk read. The latency figures are rough assumptions (not from the book); change them with the selector.

05 · DISK-BASED STRUCTURES

Some structures belong in memory, some on disk

pdf p63

Chapter 1 contrasted memory- and disk-based databases. The same split applies to individual data structures: some suit disk, some suit memory. Meeting the space and complexity requirements on paper isn't enough; a structure used for on-disk storage must be adapted to the limits of the persistent medium.

On-disk structures are used when the data is too big to keep entirely in memory, or when doing so isn't practical. Only a fraction of it can be cached at any moment; the rest must sit on disk in a way that can still be accessed efficiently.

Why the medium dominates (orders of magnitude, beyond the book)

Rough, commonly quoted orders of magnitude for one random access; real devices vary widely. Not from the book. Each step on the log axis is 10× slower.

Picture it

Memory is your desk; disk is a warehouse. You can't fit the warehouse on the desk, so the job is to arrange the warehouse so that each trip brings back as much useful stuff as possible.

What's happening behind it

When one trip to storage costs as much as tens of thousands to hundreds of thousands of memory accesses, the right measure of an algorithm is "how many trips?", not "how many CPU steps?". This is the external-memory way of counting cost, and the rest of the chapter uses it.

06 · HARD DISK DRIVES

Moving the head is the expensive part

pdf p64

Most classic storage algorithms were designed when spinning disks were the usual persistent medium, and that shaped them. Flash drives later inspired new algorithms and changes to old ones, and newer structures target non-volatile byte-addressable memory (the book cites HiKV [XIA17] and NoveLSM [KANNAN18]).

  • On a spinning disk, a seek makes random reads expensive: the platter must rotate and the read/write head must move into position.
  • Once that's done, reading or writing contiguous bytes (sequential I/O) is relatively cheap.
  • The smallest transfer unit is a sector: every operation reads or writes at least one whole sector. Sectors are typically 512 bytes to 4 KB.
  • Head positioning is the most expensive part of any HDD operation. That's why sequential I/O is praised so often.

Modelled, not measured: one random read = average seek + half a rotation + transfer. Defaults are typical desktop-drive assumptions, not figures from the book.

Picture it

A record player. Dropping the needle on a new song takes a few seconds; once it's down, the music streams for free. Random I/O is hopping between songs; sequential I/O is letting the album play.

What's happening behind it

For small requests, the fixed cost (seek + rotation, ~13 ms with the defaults) dwarfs the transfer time (~0.03 ms for 4 KB at 150 MB/s). So 4 KB random reads deliver well under 1 MB/s while a sequential stream delivers the full 150 MB/s. A data structure for HDDs must therefore (a) touch few distinct places per operation and (b) get as much useful data as possible out of each place it touches.

07 · SOLID STATE DRIVES

Write a page, erase a block

pdf p65–66 · Fig 2-5

SSDs have no moving parts: no spinning platter, no head. They're built as a hierarchy [LARRIVEE15]:

memory cell (1 or more bits)→string (typically 32–64 cells)→array→page (typically 2–16 KB)→block (typically 64–512 pages)→plane→die (an SSD has one or more)
  • The smallest unit you can read or write (program) is a page.
  • You can only write into empty cells, ones erased beforehand. The smallest unit you can erase is not a page but a whole block of pages, hence the name erase block. Pages in an empty block must be written in order.
  • The Flash Translation Layer (FTL) in the controller maps page IDs to physical locations and tracks empty, written and discarded pages. It also runs garbage collection: it finds blocks it can erase, first moves any still-live pages to new locations and remaps their IDs, then erases the block so it can be written again.
  • HDDs and SSDs both address chunks, not single bytes, so operating systems expose a block device abstraction [CESATI05]. It hides the internal layout and buffers I/O: reading one word from a block device reads the whole block that contains it. On-disk structures must always account for this.
  • On SSDs, random vs sequential matters much less than on HDDs, because their latencies are closer. Some difference remains from prefetching, reading contiguous pages, and internal parallelism [GOOSSAERT14].
  • Garbage collection usually runs in the background but can still hurt write performance, especially with random and unaligned writes. Writing only full blocks and combining writes to the same block reduces the number of I/O operations; the book returns to buffering and immutability as ways to do that.

A toy FTL you can push around (simulation, not in the book)

Toy drive: 6 blocks × 8 pages (real blocks hold 64–512), 32 logical pages of user data, so 1/3 of the flash is spare. Writes go to the next free page of the open block (orange). An overwrite marks the old copy stale (red, dashed). When only one block is left, garbage collection picks the block with the most stale pages, copies its live pages forward, and erases it. "Write amplification" (flash page writes ÷ pages the host asked to write) is a standard term, not one this chapter uses.

Picture it

A notebook written in pen where you may only tear out whole chapters. To "change" a line you write it again on the next blank line and cross out the old one. When the notebook is full, you pick a chapter that's mostly crossed out, copy its few good lines to the end, and tear the chapter out.

What's happening behind it

Random overwrites leave stale pages scattered across many blocks, so every erase first has to copy live neighbours: more flash writes than you asked for. Rewriting data in big sequential runs makes whole blocks go stale together; they can be erased with nothing to copy, and write amplification falls toward 1. Try it: press "Overwrite 20 random pages" a few times, then "Rewrite all 32 pages in order" twice and watch the last-action figure.

Worked example

Using the book's ranges: a 4 KB page in a 128-page block makes a 512 KB erase block. If a drive had to erase and rewrite the whole block for each 4 KB change, one small update could cost 128 page programs. The FTL avoids that by writing the new version elsewhere and erasing later, which is why it needs garbage collection.

08 · ON-DISK STRUCTURES

The block is the unit; design around it

pdf p67–68 · Fig 2-6

Apart from the cost of the access itself, the main constraint on any on-disk structure is that the smallest unit of disk operation is a block. To follow a pointer to one spot inside a block, you must fetch the whole block. Since you pay for the whole block anyway, change the layout to use it.

"Pointer" means something slightly different on disk. Unless you use memory-mapped files, you manage the layout yourself: you compute target addresses and follow them explicitly. Offsets are usually precomputed (when the pointer is written before the thing it points to) or kept in memory until flushed. Long chains of dependencies between on-disk parts make code and structure much more complex, so keep the number of pointers, and how far they reach, to a minimum.

In short, on-disk structures are built for their storage medium and mainly try to reduce disk accesses, by improving locality, optimising the internal representation, and cutting out-of-page pointers. Plate 4 asked for high fanout and low height; here we add that pointers cost space, and rebalancing that remaps them costs maintenance. B-Trees combine the answers: more fanout, less height, fewer node pointers, and less frequent balancing.

Sidebar: paged binary trees. Grouping BST nodes into pages, as in Figure 2-6, improves locality: the next node is often reached through a pointer inside a page you already fetched. But nodes and inter-node pointers still cost space, and laying the tree out and maintaining it is hard, especially when keys arrive unsorted. Balancing means reorganising pages, which means more pointer updates.

Same binary tree, three page layouts: pages touched per lookup (simulation)

A perfect binary tree with 2ʰ − 1 keys. "Random placement" puts nodes into pages in a random order, standing in for nodes written in arrival order. "Level order" packs the tree breadth-first. "Subtree pages" is the paged binary tree: each page holds a small complete subtree. Each figure is the average over every root-to-leaf path.

Picture it

A family tree drawn on index cards. Scatter the cards in a box and tracing one line of descent means pulling a new card for every generation. Glue each grandparent-parent-child trio onto one card and you pull a third as many.

What's happening behind it

With subtree pages holding d levels, a root-to-leaf walk of h levels crosses ⌈h ÷ d⌉ pages, the same count as a B-Tree whose node is that page. So paged binary trees fix the read side. What they don't fix is maintenance: an insert can trigger a rotation that moves a node to another page, so pages have to be reorganised and cross-page pointers rewritten. B-Trees keep the "one page = one node" layout and replace rotations with splits and merges that only touch a node, its sibling and its parent.

09 · UBIQUITOUS B-TREES

A catalogue room, not a corridor of doors

pdf p69–71 · Fig 2-7, 2-8

The section opens with a Winnie-the-Pooh epigraph, then gives the picture: a B-Tree is like a huge library catalogue room. Pick the cabinet, then the shelf, then the drawer, then flip through the cards. Each level narrows the search.

cabinet→shelf→drawer→cards
root→internal→internal→leaf (the records)

B-Trees build on balanced search trees. The difference: higher fanout (more children per node) and smaller height.

Binary tree nodes are usually drawn as circles: one key, splitting the range in two. B-Tree nodes are drawn as rectangles with the pointer blocks shown, to make the link between separator keys and child nodes visible. A binary tree can be drawn the same way (the book's Figure 2-8 redraws Figure 2-1 like that): the pointer-following logic is the same, and the difference is how balance is kept. In both, keys split the tree into subtrees and guide the search.

B-Trees are sorted: keys inside each node are in order, so a node can be searched with binary search, and lookups are logarithmic. Finding a key among 4 billion (4 × 10⁹) items takes about 32 comparisons. A disk seek per comparison would be painfully slow, but a B-Tree node stores dozens or hundreds of items, so you seek once per level, not once per comparison.

B-Trees serve both point queries (the equality predicate =, one item) and range queries (comparison predicates <, >, ≤, ≥, many items in order).

Picture it

The 32 comparisons are like 32 yes/no questions in a guessing game. A binary tree on disk makes you walk to a different room before each question. A B-Tree lets you ask the questions in batches of six or seven per room, so you visit 5 rooms instead of 32.

What's happening behind it

log₂(4 × 10⁹) = 31.9, hence "about 32". With N keys per node there are N + 1 children, and the number of levels is about log_(N+1)(M). Comparisons stay near 32 whatever the fanout; only the number of separate page fetches drops. Range queries are why the tree must be sorted: a hash table also gives fast point lookups but can't return "everything between 10 and 20" in order.

10 · B-TREE HIERARCHY

Root, internal nodes, leaves; node = page

pdf p72–73 · Fig 2-9

A B-Tree is made of nodes. Each holds up to N keys and N + 1 pointers to children. Nodes fall into three groups:

  • Root node: no parent; the top of the tree.
  • Leaf nodes: the bottom layer; no children.
  • Internal nodes: everything in between, linking root to leaves. Usually more than one level of them.

B-Trees are a page organisation technique: they organise and navigate fixed-size pages. So "node" and "page" are used interchangeably.

Occupancy is how many keys a node actually holds relative to its capacity. B-Trees are characterised by their fanout, here defined as the number of keys stored per node (plate 4 defined it as the maximum number of children; the two differ by one, and the book uses both). Higher fanout spreads the cost of the structural changes that keep the tree balanced over more keys, and reduces seeks by keeping keys and child pointers in one block or a few consecutive ones. Balancing operations, splits and merges, run when a node is full or nearly empty.

A real tree built by the page's own insert code (N = 3, 24 keys in random order). Empty cells are free slots, so you can see occupancy directly.

Sidebar: B⁺-Trees. The book uses "B-Tree" as an umbrella for a family of structures sharing most of these properties. The precise name for what it describes is B⁺-Tree; Knuth [KNUTH98] calls high-fanout trees multiway trees. A plain B-Tree may store values at any level (root, internal, leaf). A B⁺-Tree stores values only in leaves; internal nodes hold only separator keys that guide the search. So in a B⁺-Tree every insert, update, delete and read touches only leaves, and changes reach higher levels only during splits and merges. B⁺-Trees became so common that people just call them B-Trees: Graefe's survey [GRAEFE11] treats the B⁺-Tree as the default design, and MySQL InnoDB calls its B⁺-Tree a "B-tree".

Picture it

A B⁺-Tree is a building directory. The signs in the lobby and on each floor (internal nodes) only tell you where to go; the actual offices (values) are all on the ground row of leaves. Changing an office never requires repainting a sign, unless offices are merged or a new wing is added.

What's happening behind it

Keeping values out of internal nodes means more separators fit per page, so fanout is higher and the tree is shorter. It also means every key's record is at the same depth, so every lookup costs the same number of page reads; in a plain B-Tree a lucky lookup can stop early (like the BST in plate 2), but the internal pages hold fewer keys.

11 · SEPARATOR KEYS

Keys that act as signposts between subtrees

pdf p74–75 · Fig 2-10

Keys in B-Tree nodes are called index entries, separator keys or divider cells. They cut the tree into subtrees (also called branches or subranges), each holding a key range. Keys are sorted so a node can be binary-searched; you find the subtree by locating a key and following its pointer down a level.

  • The first pointer leads to items less than the first key.
  • The last pointer leads to items greater than or equal to the last key.
  • Every other pointer leads to items between two keys: Ki−1 ≤ Ks < Ki, where Ks is a key in that subtree.

Some variants add sibling pointers, most often between leaves, to make range scans simple: you don't have to go back up to the parent to find the next leaf. Some link leaves in both directions, a doubly linked list, so you can also iterate backwards.

What sets B-Trees apart: they're built bottom-up, not top-down like a BST. Leaves multiply, which adds internal nodes and eventually height. (Watch it happen in plate 15.)

Because B-Trees leave room in nodes for future inserts and updates, storage utilisation can drop as low as 50%, though it's usually much higher. Higher occupancy doesn't hurt B-Tree performance.

How full do the nodes end up? (simulation with this page's split rule)

Picture it

Road signs at a junction: "towns before 20 → left; 20 up to (not including) 40 → second exit; 40 up to 60 → third; 60 and beyond → straight on". A town named exactly 40 takes the third exit, because each range includes its lower boundary.

What's happening behind it

Splitting a full node in the middle leaves two half-full nodes, which is where the 50% floor comes from. Ascending inserts are the worst case for this split rule: every left half is abandoned at exactly half full (at even N), because new keys always land in the rightmost node. Random inserts keep refilling old nodes, and the average lands around 70% in this simulation. (Beyond the book: a classic analysis of random insertions by Andrew Yao, 1978, puts it near ln 2 ≈ 69%; real engines also special-case ascending inserts, see Ch.4 "Right-Only Appends", pdf p130.)

12 · B-TREE LOOKUP COMPLEXITY

Two costs, two logarithm bases

pdf p76

A B-Tree lookup has two kinds of cost:

  • Block transfers. The log base is the number of keys per node. Each level has that many times more nodes, and each pointer you follow cuts the search space by the same factor. At most logK M pages are read, where M is the total number of items. The number of pointers followed root-to-leaf equals the number of levels, the height h. (The book writes the base as N in one sentence and K in the next; both mean keys per node.)
  • Comparisons. The base is 2, because each node is binary-searched and each comparison halves the remaining space: log₂ M.

Keeping seeks and comparisons apart is what gives the intuition for how lookups really behave. Textbooks usually just write log M (footnote 2 points to [KNUTH98] as an example): the base is dropped because changing it multiplies by a constant, and constant factors don't change complexity. For a non-zero constant c, O(|c| × n) = O(n) [KNUTH97].

Model (beyond the book): fanout f = ⌊page ÷ (key + pointer)⌋ × fill, ignoring page headers; leaves assumed to hold f entries too; height h = ⌈log_f M⌉. Cached levels: the largest number of top levels whose pages all fit in the RAM budget.

Picture it

A phone book with 1,000 pages. Opening the right page takes about 10 page-flips if you halve each time (log₂ 1,000 ≈ 10). But if each flip lands you on a tab that already narrows to a chapter of 30 pages, you need 2–3 "trips" and then do the remaining halving with your eyes on one open spread. Trips are I/O; glances are comparisons.

What's happening behind it

log₂ M = log₂ f × log_f M. The comparisons are the same total; the B-Tree just groups them into h page visits of about log₂ f comparisons each. That's why page size matters: doubling it adds one comparison per node but can remove a whole level. And because each level is f times smaller than the one below it, the upper levels are tiny. For a billion keys at f = 512 the leaves take about 1.95 million pages (~16 GB at 8 KB), the level above about 3,815 pages (~30 MB), then 8 pages, then the root. Cache the top three levels and a lookup costs one disk read.

Worked example

1 billion keys, 8 KB pages, 8-byte keys and 8-byte pointers, nodes full: f = 8192 ÷ 16 = 512. 512³ ≈ 1.3 × 10⁸ < 10⁹ ≤ 512⁴, so h = 4 page reads. Comparisons: log₂ 10⁹ ≈ 29.9, so about 30, spread as ~9 per node. A balanced BST on disk would need ~30 page reads. With 128 MB of cache, the root, the 8 pages below it and the 3,815 pages of the third level (~30 MB) all fit, so only the leaf read goes to disk: 1 disk read per lookup.

Connects to
  • Papers: Knuth, TAOCP Vol. 1: Fundamental Algorithms (3rd ed., 1997) [KNUTH97] for the constant-factor rule.
  • Plate 4 (fanout vs height), plate 13 (where the comparisons happen).
13 · B-TREE LOOKUP ALGORITHM

One pass from root to leaf

pdf p77

To find an item, do a single traversal from root to leaf. The goal is the searched key or its predecessor. An exact match serves point queries, updates and deletes; the predecessor serves range scans and inserts.

  1. Start at the root. Binary-search its keys for the first separator greater than the searched key. That picks the subtree.
  2. Follow that pointer and repeat (find the separator, follow the pointer) until you reach a leaf.
  3. In the leaf, either find the key or conclude it's absent by locating its predecessor.

Each level gives a finer view: the root's ranges are the coarsest, each level down narrows them, and the leaves hold the data records. A point query ends once the key is found or not found. A range scan starts at the closest key found and follows sibling pointers until the range ends or the predicate is exhausted.

Picture it

Zooming into a map: country → state → city → street. Each zoom level is one page read, and you never zoom back out on the way down. A range scan is then walking along the street, door to door, using the sibling links.

What's happening behind it

"First separator greater than the key" is an upper-bound binary search: the pointer index equals the number of separators ≤ the key, which is exactly the invariant Ki−1 ≤ Ks < Ki from plate 11. In the leaf, the same search gives the position of the last key ≤ the search key, the predecessor. An insert puts the new key right after it; a range scan begins there.

14 · COUNTING KEYS

k and 2k, or N and N + 1: same tree, different bookkeeping

pdf p78

Sources count keys and child pointers differently.

  • Bayer & McCreight [BAYER72] use a device-dependent natural number k that represents the best page size. A page holds between k and 2k keys, may be partly filled, and has between k + 1 and 2k + 1 child pointers. The root holds between 1 and 2k keys. Later they introduce a number l and say any non-leaf page can have l + 1 keys.
  • Graefe [GRAEFE11] and others describe nodes holding up to N separator keys and N + 1 pointers, with otherwise the same rules.

Both describe the same thing; each just emphasises what its source needs. This book uses N as the number of keys (key-value pairs, in leaves).

Picture it

Describing a bus by "seats: 20 to 40" versus "capacity: 40". Same bus; the first also tells you the minimum the operator insists on.

What's happening behind it

Bayer's k form builds the minimum fill into the definition: every non-root page is at least half full (k of 2k). That is the 50% floor from plate 11, written as a rule. The N form states only the maximum and leaves the minimum to the split and merge rules (plates 15–16).

Connects to
  • Paper: Bayer & McCreight, "Organization and maintenance of large ordered indices", Acta Informatica 1(3):173–189, 1972 [BAYER72]. The original B-Tree paper, and worth reading for the cost analysis that picks k from device parameters.
15 · B-TREE NODE SPLITS

Overflow, split, promote, and (rarely) grow taller

pdf p79–81 · Fig 2-11, 2-12

To insert, use the lookup to find the target leaf and the insertion point, then add the key and value there. An update also finds the leaf by lookup, then attaches the new value to the existing key.

If the node has no room, it has overflowed (the book cites a 1966 linguistics note, [NICHOLS66], on whether the past participle is "overflowed" or "overflown") and must split in two. Precisely:

  • Leaf nodes: the node holds up to N key-value pairs and one more would exceed N.
  • Non-leaf nodes: the node holds up to N + 1 pointers and one more would exceed N + 1.

A split allocates a new node, moves half the elements into it, and adds its first key and a pointer to it into the parent: the key is promoted. The index where the node is cut is the split point (or midpoint). Elements after the split point go to the new sibling (for a non-leaf split, the split point itself goes too); the rest stay.

If the parent is also full, it splits too, and this can repeat all the way to the root. When the root splits, a new root holding the split-point key is allocated; the old root, now half full, moves down a level with its new sibling, and the tree is one level taller. Height changes only when the root splits or when two nodes merge into a new root. Below the root, the tree only grows sideways.

Figure 2-11 shows a full leaf getting key 11: cut it in the middle, keep half, move half, put the split-point value into the parent as a separator. Figure 2-12 shows a full non-leaf node splitting when 11 arrives: create a node, move elements from index N/2 + 1 onward, promote the split-point key. Non-leaf splits always come from a split one level down, which is why they carry an extra pointer (to the newly created child). Leaf or non-leaf makes no difference to the procedure, except that in a leaf split keys move together with their values. After the split, pick the right half for the new element using the separator rule: less than the promoted key → the old node; otherwise the new one.

  1. Allocate a new node.
  2. Copy half the elements from the splitting node to the new one.
  3. Place the new element into the right node.
  4. In the parent, add a separator key and a pointer to the new node.

Purple cell = the new key or the promoted separator · red cells = overflow (N + 1 keys in an N-key node) · dashed green border = newly allocated node, shown next to the node it split from until the parent points to it.

Picture it

A full drawer in the catalogue room. You buy a new drawer, move the back half of the cards into it, and stick a label on the cabinet: "cards from 13 onward are in the new drawer". If the cabinet has no room for another label, the cabinet itself gets split the same way. Only when the very top cabinet splits do you need a new top level.

What's happening behind it

The leaf and non-leaf cases differ in one detail that the figures show clearly. A leaf split copies the first key of the new leaf up (13 stays in the leaf and also appears in the parent), because the leaf must still hold that key's value. A non-leaf split moves the split-point key up: it appears in the parent and in neither half, because a separator is only a signpost and keeping it below would duplicate it. A split touches only the node, its new sibling and the parent, never other branches. That's the "less frequent, more local" balancing the chapter promised, compared with rotations.

Worked example (Fig 2-11 numbers)

N = 3. Leaf [10 | 13 | 15] is full, parent [18]. Insert 11 → 4 keys > 3, overflow. The cut leaves [10 | 11] and moves [13 | 15] to a new leaf; 13 is copied up, so the parent becomes [13 | 18]. For the non-leaf case, choose "Fig 2-12-style": a full internal node [10 | 20 | 30] receives separator 12 from a leaf split below, becomes [10 | 12 | 20 | 30] (overflow), keeps [10 | 12], sends 20 up, and moves [30] to a new node.

16 · B-TREE NODE MERGES

Underflow, merge, demote, and (rarely) shrink

pdf p82–84 · Fig 2-13, 2-14

To delete, find the target leaf and remove the key and its value. If neighbouring nodes now hold too few values (their occupancy has fallen below a threshold), the siblings are merged. This is called underflow. Bayer & McCreight [BAYER72] describe two cases: if two adjacent nodes share a parent and their contents fit in one node, merge (concatenate) them; if they don't fit, redistribute keys between them to restore balance (that's "Rebalancing", in Ch.4). Precisely, two nodes are merged when:

  • Leaf nodes: a node holds up to N key-value pairs, and the two neighbours together hold ≤ N.
  • Non-leaf nodes: a node holds up to N + 1 pointers, and the two neighbours together hold ≤ N + 1 pointers.

Figure 2-13 deletes 16: elements of one sibling move into the other, usually right into left, though the other direction works as long as key order is kept. Figure 2-14 deletes 10, after which two internal siblings fit in one node. Merging internal nodes means pulling the separator down from the parent (demoting it). The pointer count drops by one, because the merge itself was caused by a pointer being removed below, when a page went away. Like splits, merges can propagate all the way to the root.

  1. Copy all elements from the right node to the left one.
  2. Remove the right node's pointer from the parent (or demote the separator, for a non-leaf merge).
  3. Remove the right node.

A technique many B-Trees use to reduce the number of splits and merges is rebalancing (Ch.4).

This simulator applies the book's "merge if the two siblings fit in one node" test after every removal, trying the right sibling first, then the left. Real engines usually wait until a node drops below a fill threshold, to avoid merging and re-splitting the same pages over and over (beyond the book).

Picture it

Two half-empty drawers side by side. Pour the right one into the left, throw the empty drawer away, and peel its label off the cabinet. If those were cabinets rather than drawers, the label you peel off goes inside the merged cabinet, because it is still needed to tell its two halves apart.

What's happening behind it

Merging is a split run backwards. A leaf merge just concatenates and drops the separator; the separator was only a copy. An internal merge must bring the parent's separator down, because the merged node now covers both old ranges and needs that key to tell them apart: [9] + 11 + [13] → [9 | 11 | 13] with 4 pointers. If the root ends up with no keys and one child, that child becomes the new root and the tree is one level shorter. That's the only way height decreases.

Worked example (Fig 2-13 / 2-14 numbers)

N = 3, parent [11 | 20] over leaves […], [15 | 16], [20 | 25]. Delete 16 → [15]; with the right sibling it's 1 + 2 = 3 ≤ 3 → merge to [15 | 20 | 25], and separator 20 leaves the parent: [11]. Internal case: parent [5 | 11], children [9 | 10] (3 pointers) and [13] (2 pointers). Deleting 10 removes a leaf, so [9 | 10] loses a pointer and becomes [9] (2 pointers). 2 + 2 = 4 ≤ N + 1 = 4 → merge, demoting 11: [9 | 11 | 13], parent [5].

17 · SUMMARY + FURTHER READING

What the chapter established

pdf p85
  • On-disk storage needs its own structures. BSTs have similar complexity on paper but fail on disk: low fanout, and balancing causes many relocations and pointer updates.
  • B-Trees fix both: many items per node (high fanout) and less frequent balancing.
  • Splits and merges restructure the tree to keep it balanced as items come and go. Depth stays minimal, and items go into existing nodes while they have free space.
  • This is enough to build an in-memory B-Tree. A disk-based one also needs a node layout on disk and data-encoding formats: that's Ch.3.

Check yourself
answer before you open

  
1. A balanced BST already gives O(log N) lookups. Name the three reasons the book gives for not using one on disk.
Fanout 2 means height ≈ log₂ N, and on disk each level is a seek and a transfer (about as many seeks as comparisons). New nodes land anywhere, so child pointers cross pages (poor locality). And frequent rebalancing relocates nodes and rewrites pointers, which is expensive on disk (plate 4).

  
2. 1 billion keys, 8 KB pages, 16-byte key+pointer entries, full nodes. Page reads per lookup for a B⁺-Tree vs an on-disk balanced BST?
Fanout 512; 512³ ≈ 1.3 × 10⁸ < 10⁹ ≤ 512⁴, so 4 page reads. The BST needs ⌈log₂(10⁹+1)⌉ = 30 (plate 12).

  
3. In that B⁺-Tree lookup, roughly how many key comparisons happen, and why didn't the B-Tree reduce them?
About 30 (log₂ 10⁹ ≈ 29.9). Comparisons are base-2 because each node is binary-searched; the B-Tree only regroups them into 4 page visits of about 9 comparisons each (plate 12).

  
4. A node holds [20 | 40 | 60]. Which pointer does the search for 40 follow, and which invariant decides it?
The third one, covering 40 ≤ Ks < 60. Each subtree includes its lower separator: Ki−1 ≤ Ks < Ki (plate 11).

  
5. After a split, where does the split-point key end up in a leaf split vs a non-leaf split?
Leaf: it stays as the first key of the new leaf and a copy goes up to the parent (13 in Fig 2-11). Non-leaf: it moves up to the parent and is in neither half (plate 15).

  
6. When, and only when, does a B-Tree's height change?
When the root splits (a new root is allocated, height +1) or when a merge leaves the root with a single child that becomes the new root (height −1). Everywhere else the tree grows and shrinks sideways (plates 15–16).

  
7. Why do random small writes hurt SSDs even though there's no seek?
Pages can only be written into erased space and erasing works per block. The FTL writes updates elsewhere and must garbage-collect: before erasing a block it relocates the block's live pages. Scattered overwrites leave live pages in many blocks, so GC copies more and write performance drops (plate 7).

  
8. What's the difference between a B-Tree and a B⁺-Tree, and why does it matter for updates?
A B-Tree can store values at any level; a B⁺-Tree stores them only in leaves, with separator keys above. In a B⁺-Tree all data operations touch only leaves and reach upper levels only through splits and merges (plate 10).

  
9. In Bayer & McCreight's notation with k = 50, how many keys and pointers can a non-root page hold? And the root?
50–100 keys and 51–101 child pointers; the root holds 1–100 keys. In this book's notation that's N = 100 keys, N + 1 = 101 pointers (plate 14).

  
10. N = 4. Two sibling internal nodes have 2 and 3 pointers. Do they merge? What happens to the parent's separator between them?
2 + 3 = 5 ≤ N + 1 = 5, so yes. The separator is demoted into the merged node (between the left and right keys), and the parent loses one key and one pointer (plate 16).

  
11. Why do some B-Trees add sibling pointers at the leaf level, and what does a doubly linked leaf level add?
Range scans can walk to the next leaf without climbing back to the parent; links in both directions also allow reverse iteration (plates 11, 13).

  
12. A lookup for a key that isn't there: what does the algorithm return, and who uses it?
Its predecessor, the last key ≤ the searched key in the target leaf. Inserts use it as the insertion point and range scans use it as the starting position (plate 13).

  
13. Storage utilisation "can get as low as 50%". Where does the floor come from, and does a fuller tree run slower?
A split cuts a full node into two halves, and the k-to-2k rule makes half-full the minimum. Ascending inserts with a middle split leave every left node at that floor. The book says higher occupancy does not hurt performance (plates 11, 14).

  
14. On a spinning disk, which part of a 4 KB random read dominates, and by roughly how much (with typical assumptions)?
Head positioning: an average seek of ~9 ms plus ~4 ms of rotation versus ~0.03 ms of transfer, a few hundred times more (plate 6, modelled).
