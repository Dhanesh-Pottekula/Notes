01 · CHAPTER INTRODUCTION

Disk is read by offset, memory by pointer

pdf p86

In a program, memory access mostly "just works". Virtual memory hides where things physically live, so you follow a pointer and never think about offsets. A disk is different. You reach it through system calls, you name the offset inside the file you want, you get back raw bytes, and then you have to interpret those bytes into something your program can use. So an on-disk structure has to be designed around that gap: we need a file format that is easy to build, change and read back.

Petrov makes three framing points:

  • Knowing how B-trees split and merge (Chapter 2) is necessary but not enough to build one. Many parts have to work together.
  • Pointers work differently on disk. Think of an on-disk B-tree as a page management mechanism: the algorithms build and walk pages, and pointers to pages have to be calculated and stored.
  • Most B-tree complexity comes from mutability (changing data in place), so this chapter focuses on page layout, splitting, relocation and space reuse. LSM trees (Chapter 7) get their complexity from sorting and maintenance instead. The principles here apply to any on-disk structure, not only B-trees, and details vary between implementations.
Picture it

Memory is a library where a helper fetches any book you point at. Disk is a warehouse where you hand over a slip saying "aisle 7, shelf 3, 8 KB please", get a sealed box of bytes back, and have to unpack it yourself. The box's packing list (the file format) is what lets you unpack it.

What's happening behind it

A pointer in RAM is an address the CPU and OS resolve for you on every access. A file has no such help: the only "address" is a byte offset, and the only operations are read and write of byte ranges. That's why the rest of the chapter is about deciding, ahead of time, at which offset each thing lives and how its bytes are arranged. It also explains the phrase "page management": the unit you read and write is a whole page, so the structure is designed in pages.

Beyond the book: rough orders of magnitude

Widely quoted rule-of-thumb latencies (typical figures, not measured here): a main-memory access is on the order of 100 ns; a random read from an NVMe SSD is on the order of tens of microseconds; a random read from a spinning disk is on the order of milliseconds because of the seek. That gap, roughly 100× for SSDs and well over 10,000× for spinning disks, is why on-disk formats are built to touch as few pages as possible per operation.

02 · MOTIVATION

A file format is manual memory management, without the help

pdf p87–88

Designing a file format feels like writing data structures in a language without garbage collection (like C): you take a block, slice it with fixed-size primitives and structs, and use pointers to reach larger or variable-size things. But in C you can always ask for more memory and never worry whether a contiguous piece exists, whether it's fragmented, or what happens after you free it. On disk, garbage collection and fragmentation are your job.

Layout matters far less in memory than on disk. To be fast on disk you must place data so it can be reached quickly, respect how the storage medium behaves, design binary formats, and serialize/deserialize efficiently. Anyone who has written plain C knows the pain: structs have a fixed size, memory is allocated and freed by hand, and tracking which fixed-size segments are free is hard.

In memory most of these problems are absent or easy: variable-length and oversized values just get a pointer to a separately allocated buffer. People do still design special in-memory layouts to exploit CPU cache lines and prefetching, but mainly as an optimization (the book cites the LMAX architecture, [FOWLER11]). The OS and filesystem take over some duties, but on-disk structures still have more details and more pitfalls.

Picture it

Memory is a hotel with a front desk: ask for a room of any size and you get one. Disk is a parking lot you paint yourself. You decide the bay sizes, you write down which bays are empty, and when a big truck leaves a gap between two small cars, it's on you to notice that gap and reuse it.

What's happening behind it

malloc hides three jobs: finding free space, tracking it, and reclaiming it. A file has none of those, so a storage engine rebuilds them inside each page: a header that records free space (section 09), an availability list of freed pieces (section 12), and defragmentation (section 12). The "variable-size data" problem in memory is solved by a pointer; on disk it's solved by storing a length or offset next to the data (sections 05 and 07).

  • [FOWLER11] Martin Fowler, "The LMAX Architecture", martinfowler.com, July 12, 2011. What it gives you: a real system (a trading exchange) that designed its in-memory layout around CPU caches. It's the book's example of when in-memory layout does matter.

03 · BINARY ENCODING

No malloc, no free: only read and write

pdf p89

To store data well on disk it must be encoded in a format that is compact and easy to serialize and deserialize. People say layout a lot: since we only have read and write (no malloc/free), we must decide up front where each value sits. The same rules work for any binary format: file formats, serialization formats, network protocols.

Before organizing records into pages we need four things, which are the next sections: how to represent keys and records in binary, how to combine values into bigger structures, how to do variable-size types, and how to do arrays.

Picture it

Packing a suitcase with fixed compartments. You can't make a compartment bigger later, so you write on the lid: "socks: compartment 1, 4 cm; shirt: compartment 2, length on the tag".

Try it: append values to a byte buffer and watch where they land

What's happening behind it

Each value's position is the sum of the sizes before it. That's the whole idea of a layout: offsets are either fixed (because every earlier field has a fixed size) or computed from length fields you stored earlier. Try adding 513 as a u16: it's two bytes, 0x02 0x01, because 513 = 2 × 256 + 1. Switch to little-endian and the same two bytes swap places.

04 · PRIMITIVE TYPES
Fixed sizes, and agreeing on byte order
pdf p90–91 · Fig 3-1, 3-2

  
Keys and values have types (integer, date, string…) and can be serialized to, and read back from, raw bytes. Most numeric types are fixed-size. For any multi-byte number, the writer and the reader must use the same byte order (endianness):

  
    
    
  • Big-endian: starts with the most-significant byte (MSB), then bytes in decreasing significance. The MSB sits at the lowest address.
    • 
    
  • Little-endian: starts with the least-significant byte (LSB), then bytes in increasing significance.
    • 
  

  
Figure 3-1 shows the 32-bit value 0xAABBCCDD both ways, with AA as the MSB. Real example: RocksDB has platform-specific definitions to find the target platform's byte order. When it reconstructs a 64-bit integer whose endianness doesn't match the platform (EncodeFixed64WithEndian compares the value's endianness with kLittleEndian), it reverses the bytes with EndianTransform, which reads the value byte by byte in reverse order and appends to the result. (Footnote 1: kLittleEndian is set depending on the platform: macOS, Solaris, AIX, the BSDs, or Windows.)

A record is made of primitives (numbers, strings, booleans) and their combinations. But a network or a disk only carries byte sequences. So to send or store a record we serialize it (turn it into bytes someone can interpret), and after receiving or reading we deserialize it (turn bytes back into the record). Primitive sizes: byte 8 bits, short 2 bytes (16 bits), int 4 bytes (32 bits), long 8 bytes (64 bits).

Floating-point numbers (float, double) are stored as a sign, a fraction and an exponent, following IEEE 754. A 32-bit float is single precision. Counting from bit 0, the first 23 bits are the fraction, the next 8 the exponent, and the last bit (bit 31) the sign; Figure 3-2 draws them left to right as sign, exponent, fraction. Because the value is built from fractions, it is usually only an approximation of the number you meant. A double is double precision [SAVARD05]. Most languages' standard libraries can encode and decode floats; the book doesn't go through the full conversion algorithm.

Picture it
Writing the number 1,234 as "1234" or "4321" both work, as long as the reader knows which way you wrote it. Endianness is that agreement for bytes. A float is scientific notation in base 2: a sign, a "1.something", and "times 2 to the power of".

  
What's happening behind it
    
Endianness only exists for values wider than one byte; a single byte reads the same either way, which is why the string bytes in the round-trip widget never change. Mismatch the reader and the 4-byte id 1000 (00 00 03 E8) comes back as 3,892,510,720. Worse, the 2-byte name length is misread, so the decoder slices the wrong number of bytes, and every field after it is wrong too. That's why formats fix one byte order and write it into the spec.

    
Floats (standard IEEE 754 details, not spelled out in the book): value = (−1)sign × (1 + fraction/223) × 2exponent − 127. The "1 +" is a hidden bit, and 127 is the exponent bias. 0.1 has no exact binary form, so float32 stores 0.100000001490116…; 0.15625 = 1.25 × 2−3 is exact.

    
A note on Figure 3-2 (my observation): the text says the figure shows 0.15652, but the bits drawn (sign 0, exponent 01111100, fraction 0100…0) decode to exactly 0.15625. Press the 0.15652 button: its float32 has a different fraction pattern. The figure is right for 0.15625; the "0.15652" in the text looks like swapped digits.

  

  
Beyond the book: who uses which byte order
  • SQLite's file format stores all multi-byte header integers and its varints big-endian (sqlite.org/fileformat2.html).
  • LevelDB's table footer ends in a fixed 64-bit magic number stored little-endian (LevelDB doc/table_format.md).
  • x86-64 and (in practice) ARM64 CPUs run little-endian; the widget above detects your own machine's order.

05 · STRINGS AND VARIABLE-SIZE DATA
Say the size first, then the bytes
pdf p92 · p110 fn 2

  
All primitive numbers have a fixed size. Building bigger values works like a C struct: combine primitives, use fixed-size arrays, or point to other memory regions. Strings and other variable-size data (like arrays of fixed-size items) are stored as a size followed by that many bytes of data. For strings this is called a UCSD string or Pascal string, after a popular Pascal implementation. In the book's pseudocode the size is a uint_16 and the data is byte[size].

  
The alternative is a null-terminated string: the reader consumes bytes until it hits the end-of-string symbol. The Pascal layout wins on two counts: you learn the length in constant time instead of scanning the content, and you can build a string in your language by slicing exactly size bytes and passing them to a string constructor.

  

    

    
Pascal string
Null-terminated

    

    

    

  

  
Picture it
A Pascal string is a parcel with the weight written on the label: you know how big it is before opening it. A null-terminated string is a scroll: you only know its length after unrolling it to the end.

  
What's happening behind it
The size field is what lets a reader skip a value without reading it, and skipping is what makes later fields findable. With a 2-byte size, a string can hold at most 65,535 bytes; bigger values need a bigger size field (or an overflow page, Chapter 4). A null terminator also can't appear inside the data, so binary values (which may contain 0x00) can't use it at all (my addition).

  
Footnote 2: structs and padding
The book warns that compilers may add padding inside structs, depending on the architecture, which breaks assumptions about exact byte offsets. Illustration (my example, typical 64-bit ABI alignment): a struct { uint8 flags; uint32 key_size; uint32 value_size; } is usually laid out with 3 padding bytes after flags, giving offsets 0, 4, 8 and a size of 12 bytes. The book's key-value cell in section 10 puts the same fields at offsets 0, 1, 5 (9 bytes, packed). So never memcpy a struct to disk and hope; write each field at an explicit offset. The book points to databass.dev/links/58 for more on structure packing.

  
Beyond the book: variable-length size fields
Many formats store the size itself as a varint so short strings pay 1 byte, not 2. Protocol Buffers use 7 payload bits per byte with the top bit meaning "more bytes follow", least-significant group first; 150 encodes as 96 01, and a 64-bit value takes 1–10 bytes (protobuf.dev encoding guide). SQLite's varints are 1–9 bytes and big-endian (sqlite.org/fileformat2.html).

06 · BIT-PACKED DATA: BOOLEANS, ENUMS, AND FLAGS
When one byte is too much
pdf p93–94

  
Booleans can take a whole byte, or be written as 1 and 0. A whole byte for two possible values is wasteful, so developers often pack eight booleans into one byte, one bit each. A 1 bit is set; a 0 bit is unset or empty.

  
Enums (enumerated types) are stored as integers and are common in binary formats and protocols for often-repeated, low-cardinality values. The book's example encodes a B-tree node type: ROOT = 0x00, INTERNAL = 0x01, LEAF = 0x02.

  
Flags are a mix of the two: named booleans that are not mutually exclusive. Example: whether the page holds value cells, whether values are fixed- or variable-size, whether there are overflow pages for this node. Every bit is one flag, so masks must be powers of two (a power of two has exactly one set bit: 23 = 8 = 1000b, 24 = 16 = 0001 0000b). The book's masks: IS_LEAF_MASK = 0x01 ("bit #1"), VARIABLE_SIZE_VALUES = 0x02 ("bit #2"), HAS_OVERFLOW_PAGES = 0x04 ("bit #3").

  
Read and write flags with bitmasks and bitwise operators: set with OR (flags |= MASK) or with a shift and bit index (flags |= (1 << 2)); unset with AND and NOT (flags &= ~MASK); test by ANDing and comparing with 0 ((flags & MASK) != 0).

  

    

      
      
      
    

    

    

      
      
      
    

    

    

      
      
    

    

  

  
Picture it
A row of eight light switches on one wall plate. An enum is a dial with a few positions (only one at a time). Flags are the switches (any combination at once).

  
What's happening behind it
Watch the numbering: the book labels the masks "bit #1, #2, #3" (counting from 1), but its code uses 1 << 2 for HAS_OVERFLOW_PAGES, which is bit index 2 counting from 0. Both describe 0x04. In the widget, bit indexes start at 0, as in the shift. OR can only turn bits on, AND with a negated mask can only turn bits off, and AND with a mask isolates one bit so you can test it. None of them touch the other bits, which is why independent flags can share a byte.

07 · GENERAL PRINCIPLES
Decide the addressing, then the header, then the record shape
pdf p95–96 · Fig 3-3

  
Start a file format by deciding addressing: will the file be split into same-sized pages, each one block or several contiguous blocks? Most in-place update structures use same-size pages because it makes reads and writes much simpler. Append-only structures often write page by page too: records are appended one after another, and when the in-memory page fills up, it's flushed to disk.

  
A file usually starts with a fixed-size header and may end with a fixed-size trailer. They hold auxiliary information that must be found quickly or that's needed to decode the rest of the file. Everything in between is pages (Figure 3-3).

  

    
  

  

    
    
    
  

  

  
Many stores have a fixed schema: the number, order and type of a table's fields are known. That saves space: instead of writing field names again and again, you use their position. The book's example is a company directory (names, birth dates, tax numbers, genders). One approach puts the fixed-size fields first, then the variable-size ones:

  
fixed:     employee_id 4 B · tax_number 4 B · date 3 B · gender 1 B · first_name_length 2 B · last_name_length 2 B   (= 16 B)
variable:  first_name (first_name_length B) · last_name (last_name_length B)

  
To read first_name, slice first_name_length bytes right after the fixed area. To read last_name, find its start by adding up the sizes of the variable fields before it. To avoid that arithmetic across several fields, store both offset and length of each variable field in the fixed area; then any variable field can be found on its own.

Bigger structures are hierarchies: fields made of primitives, cells made of fields, pages made of cells, sections made of pages, regions made of sections, and so on. There are no strict rules; it depends on the data. Database files often have several parts, with a lookup table pointing to each part's start offset, stored in the header, the trailer, or a separate file.

  
Picture it
A book: the header is the title page and table of contents, pages are pages, the trailer is the index at the back. Same-size pages mean "page 100" tells you exactly where to open it, without counting.

  
What's happening behind it
Fixed-size pages turn addressing into one multiplication, so a page ID is enough to read a page with a single positioned read. A fixed schema is the same trick for records: the 16-byte fixed area is at known offsets, so employee_id is always bytes 0–3 and no names need to be stored. In the widget the JSON version of the same record is several times bigger, mostly because of the field names. The offset + length variant costs 4 more bytes but makes every variable field reachable in one step: a classic space-for-time trade.

  
Beyond the book: real headers and trailers
  • SQLite: the first 100 bytes of the file are the database header, starting with the 16-byte string "SQLite format 3" plus a 0x00 byte; page size is a power of two from 512 to 65,536 (sqlite.org/fileformat2.html).
  • LevelDB/RocksDB SSTables put a fixed-size footer (a trailer) at the end of the file with handles to the index and metaindex blocks and a magic number, so a reader seeks to file_size − footer size first (LevelDB table_format.md, RocksDB BlockBasedTable wiki).

08 · PAGE STRUCTURE
Pages, and Bayer's original fixed-size layout
pdf p97 · Fig 3-4

  
Databases keep records in data files and index files, cut into fixed-size units called pages, often several filesystem blocks each. Page sizes usually range from 4 to 16 KB.

  
In a B-tree, leaf nodes hold keys and data records; nonleaf nodes hold keys and pointers to other nodes. Each node takes one page, or several pages linked together, so "node", "page" and even "block" are used interchangeably.

  
The original B-tree paper [BAYER72] uses a simple page layout for fixed-size records: the page is just a run of triplets: a pointer p to a child page, a key k and its value v, as in p0 k1 v1 p1 k2 v2 p2 … kn vn pn, then unused space. Easy to follow, but with two downsides:

  
  • Adding a key anywhere except at the right end means relocating the elements after it.
  • It can't manage or access variable-size records efficiently; it only works for fixed-size data.

Picture it
A bookshelf with no gaps, sorted by title. To add a book in the middle you slide every book to its right along by one slot. With heavy books (big records) that's a lot of lifting.

  
What's happening behind it
A random insert lands, on average, in the middle, so it moves half the triplets. The cost per insert is proportional to record size × number of records. A slotted page (next section) moves only the 2-byte offsets, so the copy shrinks by a factor of about triplet size ÷ 2: with 16-byte keys and 100-byte values that's 60× less copying in the calculator's model. Bayer's layout also fixes the record size, so a 3-byte name and a 300-byte name would both need the 300-byte slot.

  
Papers cited here

What it gives you: the original B-tree, its page layout and its cost analysis. Worth reading to see how much of the modern design was already there in 1972.

09 · SLOTTED PAGES
Split pointers from data, and grow them toward each other
pdf p98–100 · Fig 3-5

  
With variable-size records the main problem is free space management: reusing the space of removed records. A hole of size m left by a deleted record can take a new record of size n only cleanly if m = n, or if another record of exactly m − n can fill the rest; otherwise the leftover stays unused. And a record bigger than the hole (k > m) can't use it at all, so it goes elsewhere and the hole stays wasted.

  
Cutting the page into fixed-size segments simplifies this but wastes space too: with 64-byte segments, a record of n bytes wastes 64 − (n mod 64) bytes unless n is a multiple of 64, because its last segment is only partly filled.

  
You could reclaim space by rewriting the page and moving records, but records' offsets must be preserved, because pointers from outside the page may use them. And we want to waste as little as possible. So we need a page format that:

  
  • stores variable-size records with minimal overhead,
  • reclaims space from removed records,
  • lets others reference records in the page without knowing their exact location.

  
The answer is the slotted page (a page with slots) [SILBERSCHATZ10], also called a slot directory [RAMAKRISHNAN03], used by many databases including PostgreSQL. The page holds a collection of slots (cells), with pointers and cells in two independent regions at opposite ends of the page. Keeping order only means reordering the pointers, and deleting a record means nullifying or removing its pointer. A fixed-size header holds information about the page and its cells (Chapter 4 "Page Header"). Cells can differ in size and hold anything: keys, pointers, data records.

Picture it
A library with a card catalogue at the front and books shelved from the back wall. The catalogue (pointers) is sorted; the books sit wherever there was room. Re-sorting the catalogue is cheap, and you can rearrange the books as long as you update the cards.

  
What's happening behind it
Indirection is the trick: everyone outside refers to "slot 3", and only the slot knows the offset. Moving a cell inside the page (to defragment) then means updating one 2-byte number. Growing pointers forward from the header and cells backward from the end means both regions can grow into the same free gap without either needing a fixed budget. With the calculator's defaults (records of 20–300 bytes, 64-byte segments) about a sixth of the allocated space is padding, while the slotted page pays about 1% in offsets.

  
A subtlety (my note): "slot IDs are stable" and "slots are kept in key order" pull in different directions, because inserting into a sorted pointer array shifts later slots. PostgreSQL heap pages keep a line pointer's index stable (a tuple's ctid is page number + line pointer index), while B-tree pages, which must be sorted, are found by key search from the parent instead of by a stable slot number.

  
Beyond the book: PostgreSQL's slotted page
PostgreSQL pages are usually 8 kB. Each starts with a 24-byte header (pd_lsn, pd_checksum, pd_flags, pd_lower, pd_upper, pd_special, pd_pagesize_version, pd_prune_xid), followed by 4-byte item identifiers (offset, length, flag bits) allocated forward from the start of free space, while the items themselves are allocated backward from the end. pd_lower and pd_upper mark the two edges of the free gap. An item identifier is never moved until it's freed, so its index can be used long-term even when the item moves to compact free space (postgresql.org/docs/current/storage-page-layout.html).

10 · CELL LAYOUT
Cells: a fixed header, then the variable bytes
pdf p101–102

  
With flags, enums and primitives we can design cells, combine cells into pages, and pages into a tree. There are two kinds:

  
  • Key cells hold a separator key and a pointer to the page between two neighbouring pointers (nonleaf nodes).
  • Key-value cells hold keys and their data records (leaves).

  
All cells in a page are assumed uniform: all key-only or all key-value, all fixed-size or all variable-size, never mixed. So the description of the cells can be stored once in the page header, not repeated in every cell.

  
A key cell needs: cell type (inferable from page metadata), key size, ID of the child page, key bytes. Variable-size layout: [int] key_size at 0, [int] page_id at 4, [bytes] key at 8. (A fixed-size key cell wouldn't need the size.) The fixed-size fields come first; not required, but then they sit at static, precomputed offsets and only the variable data needs computing.

  
A key-value cell holds a data record instead of a child page ID: cell type, key size, value size, key bytes, record bytes. Layout: [byte] flags at 0, [int] key_size at 1, [int] value_size at 5, [bytes] key at 9, [bytes] data_record at 9 + key_size.

  

    

      
      
      
      
    

    

    

  

  
Offset vs page ID. Pages have a fixed size and are managed by the page cache (Chapter 5 "Buffer Management"), so a cell stores only a page ID, which a lookup table later turns into a file offset. Cell offsets are page-local, relative to the page's start, so a smaller integer is enough and the format stays compact.

  
Sidebar: variable-size data. Neither key nor value has to be fixed-size; their locations come from the fixed-size cell header. To find the key, skip the header and read key_size bytes. To find the value, skip the header plus key_size bytes and read value_size bytes. Other designs work too, e.g. store a total size and get the value size by subtraction. What matters is having enough information to slice the cell into its parts.

  

    
Why page-local offsets are small (calculator)

    

      
      
    

    

    
Model: 24-byte page header (my assumption), 2-byte offsets, cells packed; compares with storing a full 8-byte file offset per cell instead.

  

  
Picture it
A shipping label: the fixed boxes ("weight", "length", "flags") are always in the same spot on the label, so the scanner knows where to look. The contents behind it can be any size because the label says how big they are.

  
What's happening behind it
Two levels of addressing, each sized for its job. Between pages: a page ID, small and stable, turned into an offset by multiplication or a lookup table, and still valid if the file is remapped. Inside a page: a page-local offset, which only has to count up to the page size (16 bits for pages up to 64 KiB). That's 6 bytes saved per pointer compared with an 8-byte absolute offset, on every cell.

  
Beyond the book: SQLite's version of this
SQLite's b-tree page header is 8 bytes on leaf pages and 12 on interior pages (the extra 4 hold the right-most child pointer), followed by a cell pointer array of 2-byte offsets in key order. A header value of 0 for the start of the cell area means 65,536 (sqlite.org/fileformat2.html).

11 · COMBINING CELLS INTO SLOTTED PAGES
Append the cell, sort the offsets
pdf p103–104 · Fig 3-6, 3-7, 3-8

  
Cells are appended toward the end of the page (the right side), and cell offsets are kept on the left side, after the header (Figure 3-6). Keys can arrive in any order; the logical sorted order is kept by sorting the offsets by key. Cells are never relocated on insert, update or delete, so appending is cheap.

  
The book's example: a page of names. Insert Tom, then Leslie. Physically the cells sit in insertion order, but the offsets are re-sorted (Leslie, Tom) so binary search works (Figure 3-7). Now add Ron: its cell is written at the upper edge of the free space, but the offsets must keep alphabetical order, Leslie, Ron, Tom, so the offsets after the insertion point shift right to make room for Ron's offset (Figure 3-8).

  

    

      
      
      
    

    

    

    
The same page as raw bytes (128-byte page, 16 per row)

    

    

  

  
Picture it
A guest list on a clipboard (offsets, alphabetical) and guests sitting wherever there's a free chair (cells, by arrival). When Ron arrives you seat him in the next free chair and write his name between Leslie and Tom on the list. Nobody else changes chairs.

  
What's happening behind it
An insert is: binary search the offsets for the insertion point (log2 n key comparisons, each following an offset to its cell), write the cell at upper − size, then memmove the offsets after the insertion point 2 bytes to the right and write the new offset. Look at the hex view: the header's bytes 1–2 count the cells, bytes 3–4 hold upper (where cells start), bytes 5–6 hold total free bytes; offsets are big-endian 2-byte numbers from byte 8. The header layout is my own small design for this demo (the book leaves headers to Chapter 4).

12 · MANAGING VARIABLE-SIZE DATA
Holes, the availability list, and when to defragment
pdf p105–106 · Fig 3-9

  
Deleting an item doesn't have to remove the cell and shift the others into the gap. The cell can just be marked deleted, and an in-memory availability list updated with the freed size and a pointer to it. The list stores offsets and sizes of freed segments. On insert, first check the list for a segment the new cell fits in (Figure 3-9 shows a fragmented page and its list).

  
SQLite calls these unoccupied segments freeblocks and keeps a pointer to the first one in the page header. Per the book, it also keeps a count of available bytes in the page, to check quickly whether a new element would fit after defragmenting. (Beyond the book, from SQLite's file-format spec: the on-disk page header does not hold a total free-byte count; it holds the first-freeblock pointer, the start of the cell area and a count of fragmented bytes, and the spec defines the total as a computed value: the unallocated gap plus all freeblocks plus the fragmented bytes (sqlite.org/fileformat2.html, section 1.6). So read the book's sentence as "SQLite can quickly tell the total free bytes".)

  
Which segment to use depends on the strategy:

  
  • First fit: take the first segment big enough. Can cost more, because the leftover after the cell may be too small for any other cell and is effectively wasted.
  • Best fit: take the segment that leaves the smallest remainder.

  
If there aren't enough consecutive bytes but there are enough fragmented bytes in total, the live cells are read and rewritten, defragmenting the page. If there still isn't room, create an overflow page (Chapter 4 "Overflow Pages").

  

    

      
      
      
    

    

    

    

    
Start: ten names inserted, then Grace (6 B), Ken (4 B) and Margaret (9 B) deleted. Try Jim (4 B) with each strategy: first fit cuts Margaret's 9-byte hole and leaves 5 B; best fit uses Ken's 4-byte hole exactly. Then try Alan (5 B): best fit takes Grace's 6-byte hole and leaves a 1-byte sliver no cell can use. Try a 40-letter name to force a defragmentation.

Note from the book: to improve locality, especially with small keys, some implementations store keys and values separately on the leaf level. Keeping keys together helps the search; once the key is found, its value is in a value cell with the matching index. With variable-size keys this needs an extra stored pointer to the value cell.

  
Summary of the layout so far: to keep things simple, each B-tree node is one page. A page = fixed-size header + cell pointer block + cells. Cells hold keys plus either child page pointers or data records. Two simple pointer kinds: page IDs to find child nodes in the file, and cell offsets to find cells in the page.

  
Picture it
A car park after some cars leave. First fit parks the next car in the first empty bay it sees, even a bus bay, leaving an awkward half-bay. Best fit hunts for the tightest bay. Defragmentation is closing the car park for five minutes and re-parking everyone bumper to bumper.

  
What's happening behind it
Three tiers of response, from cheap to expensive: reuse a hole (no copying), append into the contiguous gap (no copying), defragment (copy every live cell, but only within one page in memory), and finally overflow or split (touch another page). Defragmentation is safe because outsiders hold slot numbers, not offsets: watch the slot table stay in the same order while offsets change. My implementation also merges neighbouring holes and gives a hole back to the free gap when it touches it, which keeps the list short. In my runs at the default 20 seeds, keeping an availability list roughly halved the number of defragmentations compared with append-and-defragment only; best fit defragmented a little less often than first fit but left more bytes stuck in slivers under 5 bytes, which is the book's first-fit/best-fit trade-off seen from the other side. Refused inserts are identical across strategies because defragmentation always recovers every free byte: the strategy only changes how often you pay for it. Read these as "in this model": the result depends on the size mix and the workload.

  
Beyond the book: what SQLite actually stores
From SQLite's file-format spec: header offset 1 holds the start of the first freeblock (0 if none); each freeblock begins with a 2-byte offset of the next freeblock and a 2-byte size, so a freeblock needs at least 4 bytes and the chain is kept in increasing offset order. Gaps of 1–3 bytes are too small to be freeblocks; they are fragments, counted at header offset 7, and a well-formed page may hold at most 60 fragmented bytes. Overflow pages start with the 4-byte page number of the next overflow page. (sqlite.org/fileformat2.html)

13 · VERSIONING
Know which format you're reading before you read it
pdf p107

  
Databases evolve: features, bug fixes and performance work change the binary format. A storage engine usually has to read more than one format (the current one plus legacy ones for backward compatibility), so it must find out which version a file uses. Three ways the book describes:

  
    
    
  • In the file name. Apache Cassandra uses version prefixes, so you can tell the version without opening the file. As of 4.0, data files have the na prefix, e.g. na-1-big-Data.db; files written by 3.0 have the ma prefix.
    • 
    
  • In a separate file. PostgreSQL stores the version in the PG_VERSION file.
    • 
    
  • In the index file header. Then part (or all) of the header must use an encoding that never changes between versions. Once the version is known, create a version-specific reader. Some formats identify the version with magic numbers (Chapter 4).
    • 
  

  

    

      
      
    

    

  

  
// version dispatch: read the stable part first, then pick a reader
const readers = { na: readCassandra40, ma: readCassandra30 };
function openSSTable(fileName) {
  const prefix = fileName.split('-')[0];
  const reader = readers[prefix];
  if (!reader) throw new Error(`unsupported format version ${prefix}`);
  return reader(fileName);   // each reader knows its own byte layout
}

  
Picture it
A document's language is written on the envelope (file name), in a cover note (separate file), or in the first line in a language everyone reads (stable header), so you pick the right dictionary before reading the rest.

  
What's happening behind it
Every option reserves a small piece of information whose own format never changes, and uses it to choose the decoder for everything else. The name-based approach is cheapest (no I/O). The header approach keeps version and data together so they can't drift apart, at the cost of one read. Failing loudly on an unknown version is the safe default: misreading bytes silently is far worse than refusing.

  
Beyond the book
  • The magic strings in the widget: SQLite starts files with "SQLite format 3" plus 0x00 (verified, sqlite.org); Parquet files begin and end with PAR1; ORC files start with ORC; pg_dump custom-format archives start with PGDMP (from general knowledge, not checked against docs for this page).
  • The PostgreSQL behaviour shown (a server refuses a data directory from a different major version) is general knowledge, not from the book.

14 · CHECKSUMMING
Catch corruption before it spreads
pdf p108–109

  
Files get damaged by software bugs and hardware failures. To find this early and avoid passing corrupt data to other subsystems or even other nodes, use checksums and cyclic redundancy checks (CRCs). Some sources blur cryptographic hashes, non-cryptographic hashes, CRCs and checksums together. All of them reduce a big chunk of data to a small number, but their purposes and guarantees differ:

  
    
    
  • Checksums give the weakest guarantee and can't detect corruption across multiple bits. They're usually computed with XOR and parity checks, or by summing [KOOPMAN15].
    • 
    
  • CRCs detect burst errors (several consecutive bits corrupted); implementations usually use lookup tables and polynomial division [STONE98]. Multi-bit errors matter, because a large share of failures in networks and storage devices look like this.
    • 
  

  
Warning from the book: non-cryptographic hashes and CRCs must not be used to check whether data was tampered with; use strong cryptographic hashes for that. A CRC protects against accidental change, not attacks.

  
How it works: before writing, compute the checksum and write it with the data. When reading, recompute and compare. A mismatch means corruption, so don't use what you read. Computing over the whole file is impractical (you rarely read all of it), so checksums are usually computed per page and stored in the page header. That makes them more robust (each covers a small piece of data), and one bad page doesn't condemn the whole file.

// write path                              // read path
page.checksum = 0;                          const stored = page.checksum;
page.checksum = crc32(page.bytes);          page.checksum = 0;
pwrite(fd, page.bytes, pageId * PAGE);      if (crc32(page.bytes) !== stored) throw new CorruptPage(pageId);

  
Picture it
A checksum is counting the boxes in a delivery: it notices a missing box, but not two labels swapped. A CRC is a seal across every box's tape: tear any run of tape and it shows. Neither stops a thief who reseals the boxes; that's what a cryptographic signature is for.

  
What's happening behind it
XOR-of-bytes keeps one parity bit per bit position, so flipping the same bit position in two different bytes cancels out and is always missed; the widget's second damage type shows this every time. A byte sum misses pairs of changes that cancel arithmetically. A CRC treats the page as one long binary polynomial and keeps the remainder after dividing by a fixed polynomial; a standard result (not in the book) is that a CRC with an r-bit remainder catches every burst of length ≤ r, so CRC-32 catches every burst up to 32 bits, and longer random damage slips through with probability about 2−32. The pooled table shows this pattern on simulated pages.

  
Beyond the book: page checksums in real engines
  • PostgreSQL has a 2-byte pd_checksum field in every page header; the PostgreSQL 18 initdb docs say data checksums are enabled by default (--no-data-checksums turns them off).
  • MySQL InnoDB: innodb_checksum_algorithm defaults to crc32, and pages are 16 KiB by default (innodb_page_size = 16384; 4K–64K allowed) (MySQL 8.4 reference manual).

  
Papers cited here
  • [KOOPMAN15] Koopman, Driscoll, Hall. "Selection of Cyclic Redundancy Code and Checksum Algorithms to Ensure Critical Data Integrity". U.S. DOT Federal Aviation Administration, 2015. What it gives you: how XOR, sum, Fletcher, Adler and CRCs compare in error-detection power, and how to pick a polynomial. The practical guide behind the "checksums are weak" claim.
  • [STONE98] Stone, Greenwald, Partridge, Hughes. "Performance of checksums and CRCs over real data". IEEE/ACM Transactions on Networking 6, no. 5 (October 1998): 529–543. What it gives you: evidence that real data is not random, so weak checksums fail more often in practice than theory on random data suggests.

Check yourself
answer before you open

  
1. A 4-byte int 0x0000012C is written little-endian and read big-endian. What value comes back, and why does a single byte never have this problem?
Bytes on disk: 2C 01 00 00. Read big-endian that's 0x2C010000 = 738,263,040. Endianness is about the order of bytes inside a multi-byte value; one byte has no order (section 04).

  
2. Why is the float32 for 0.1 not exactly 0.1, and what decides how close it gets?
0.1 has no finite binary fraction, so the 23 fraction bits (plus the hidden 1) hold the nearest representable value, 0.100000001490116… More fraction bits (double: 52) get closer, never exact (section 04).

  
3. Name two advantages of Pascal strings over null-terminated strings, and one limit of the book's uint16 size.
Length in constant time; you can slice exactly size bytes into a string constructor (and they can hold 0x00 bytes). A uint16 size caps the string at 65,535 bytes (section 05).

  
4. flags = 0b0000_0101. Write the operations to clear HAS_OVERFLOW_PAGES and to test IS_LEAF_MASK. What is flags afterwards?
flags &= ~0x04 → 0b0000_0001; (flags & 0x01) != 0 → true. Masks must be powers of two so each touches one bit (section 06).

  
5. In the employee layout, why does reading last_name need first_name_length, and what does storing offset + length buy?
last_name starts right after first_name, so its start = 16 + first_name_length. With offset + length in the fixed area, each variable field can be found directly, without summing earlier lengths, at the cost of extra bytes per field (section 07).

  
6. What two problems of Bayer's triplet page does the slotted page solve, and what overhead does it add?
Middle inserts relocating records, and no support for variable-size records. It adds one offset per record (2 bytes in a page up to 64 KiB) plus a header (sections 08–09).

  
7. With 64-byte segments, how many bytes does a 130-byte record waste? Why can't you just rewrite the page freely to reclaim space?
130 mod 64 = 2, so 64 − 2 = 62 bytes wasted (3 segments). Records can't move freely because outside pointers may use their offsets; slotted pages solve this with slot IDs (section 09).

  
8. A key-value cell has key "Ron". At what byte offset does the data record start, and why can the header fields use precomputed offsets?
9 + key_size = 9 + 3 = 12. flags (1 B), key_size (4 B) and value_size (4 B) are fixed-size and grouped first, so they're always at 0, 1 and 5 (section 10).

  
9. Why do cells store a child page ID rather than a file offset, and why can in-page cell offsets be only 2 bytes?
Pages are fixed-size and managed by the page cache, so an ID maps to an offset by a lookup/multiplication and stays small. In-page offsets only count up to the page size, which fits 16 bits for pages up to 64 KiB (section 10).

  
10. Insert Tom, Leslie, Ron into an empty slotted page. Give the physical order of the cells and the order of the offsets.
Cells in insertion order from the end of the page: Tom, Leslie, Ron (Ron nearest the free space). Offsets in key order: Leslie, Ron, Tom; Ron's offset is inserted in the middle and Tom's is shifted right (section 11).

  
11. Free segments of 9 B (at offset 84) and 4 B (at 100). Where do first fit and best fit put a 4-byte cell, and what's left over?
First fit: the 9-byte segment (first in the list), leaving 5 B. Best fit: the 4-byte segment, leaving 0. First fit risks leftovers too small to use (section 12).

  
12. A page has enough free bytes in total but not enough consecutive bytes. What happens, and why is it safe for other pages' pointers?
Defragment: read the live cells and rewrite them packed, updating offsets in the slots. Other pages refer to this page's records by page ID + slot ID, not by in-page offset, so nothing outside changes. If even that isn't enough, use an overflow page (section 12).

  
13. Give the three places a file's format version can live, with the book's example for two of them.
In the file name (Cassandra: na for 4.0, ma for 3.0), in a separate file (PostgreSQL's PG_VERSION), or in a header encoded in a never-changing format, sometimes with magic numbers (section 13).

  
14. Why does an XOR-of-bytes checksum always miss two flips in the same bit position of different bytes, while CRC-32 catches every burst up to 32 bits? And why shouldn't either be used against tampering?
XOR keeps one parity bit per column; two flips in a column cancel. A CRC is a polynomial remainder, and an r-bit CRC catches every burst of length ≤ r (a standard result). Both are easy for an attacker to recompute after changing data; tamper detection needs a cryptographic hash (section 14).

  
15. Why put checksums per page in the header instead of one per file?
Reads touch a few pages, not the whole file, so per-page checksums can be verified on every read, each covers a small piece of data, and corruption condemns one page instead of the whole file (section 14).
