Implementing B-Trees: from the textbook tree to real pages

Chapter 2 gave you the B-Tree as an algorithm and Chapter 3 gave you bytes, cells and slotted pages. This chapter is the glue: what goes in a page header, where the "extra" pointer lives, what to do with values bigger than a page, how a search walks sorted pointers to unsorted cells, how a split finds its way back up, and the tricks (rebalancing, right-only appends, bulk loading, compression, vacuum) that real engines add. Every simulation on this page runs the small JavaScript B-Tree printed in the plates, on made-up keys. Numbers marked "modelled" or "simulated" come from that code, not from the book or from a real database.

The one convention this page uses

The simulations use a B+-Tree style (my choice, not something the book fixes): keys live in the leaves; when a leaf splits, the first key of the new right leaf is copied up as the separator; when an internal node splits, its middle key moves up. A node's capacity is counted in keys. A child pointer i covers keys with Ki−1 ≤ key < Ki, as in the book (pdf p118).

01 · PAGE HEADER

The label on every page

pdf p112

Every page starts with a header: a small block of metadata used for navigation, maintenance and optimisations. Petrov lists what it usually holds:

  • flags describing the page's contents and layout (leaf or internal, for example);
  • the number of cells in the page;
  • lower and upper offsets that mark where the empty space starts and ends. New cell offsets are appended at the lower end, new cell data at the upper end;
  • other useful metadata.

His examples: PostgreSQL stores the page size and layout version in the header. MySQL InnoDB's page header holds the number of heap records, the level, and other implementation-specific values. SQLite's holds the number of cells and a rightmost pointer (section 04).

Picture it

A warehouse shelf with a clipboard at the front. Boxes (cells) are stacked from the back wall forward; the index cards that say where each box is (offsets) are pinned from the front backward. The clipboard says "cards end at line 40, boxes start at line 300". Anyone can see the free gap from the clipboard alone, without walking the shelf.

headercell offsets (grow →)cells (grow ←)
What's happening behind it

The two offsets turn "how much room is left?" into one subtraction: free = upper − lower. An insert needs record size + one offset entry bytes. It writes the record just below upper (so upper moves left), appends an offset at lower (so lower moves right), and the page is full when they would cross. The cell count is just (lower − header) ÷ offset size, but storing it saves a calculation on every visit. Flags tell the reader how to interpret the rest of the bytes before it touches them: leaf cells and internal cells have different layouts (Chapter 3).

Worked example (modelled)

PostgreSQL-like page: 8,192 bytes, a 24-byte header, 4-byte item ids. Each 100-byte record costs 100 + 4 = 104 bytes, so (8,192 − 24) ÷ 104 = 78.5, which means 78 records fit. Halve the record to 50 bytes and the offset overhead grows from 4% to 7% of each record's cost: (8,168 ÷ 54) = 151 records. Try it with the PostgreSQL-like preset and 100 or 50 bytes. (Real PostgreSQL also spends bytes on tuple headers, alignment padding and, in index pages, a "special space" at the end; this model leaves those out.)

Beyond the book: real headers

PostgreSQL (verified in the docs, storage-page-layout): the 24-byte PageHeaderData holds pd_lsn (8 B, WAL position of the last change), pd_checksum (2 B), pd_flags (2 B), pd_lower and pd_upper (2 B each: start and end of free space), pd_special (2 B: start of the access method's special space), pd_pagesize_version (2 B) and pd_prune_xid (4 B). Item identifiers are 4 bytes each; the default page is 8 kB. In B-tree indexes the special space holds the left and right sibling links (section 03).

SQLite (file format): a B-tree page header is 8 bytes on leaf pages and 12 bytes on interior pages; the extra 4 bytes are the right-most child pointer. Cell pointers are 2-byte offsets.

02 · MAGIC NUMBERS

A 4-byte "is this really a page?" check

pdf p113

A value often placed in the file or page header is a magic number: a multibyte block holding a constant. It can say "this block is a page", say what kind of page it is, or identify its version. Magic numbers are used for validation and sanity checks [GIAMPAOLO98]. The logic: it is very unlikely that the bytes at a random offset happen to equal the magic number, so if they do match, the offset is probably right. Petrov's example: on write, put 50 41 47 45 (hex for the ASCII text PAGE) into the header; on read, compare the first four bytes of the header with that sequence to check the page was loaded and aligned correctly.

Picture it

Each page begins with the same stamp, like the "%PDF" at the start of every PDF file. If you open a file at the wrong position and don't see the stamp, you know immediately that you are reading from the middle of something, before you trust any of the numbers that follow.

The dump shows a toy file of three 64-byte pages (simulated). Each page starts with 50 41 47 45, then a 2-byte page id, a flags byte and a cell count. Slide the offset: only 0, 64 and 128 pass. Tick the box to see a damaged page fail at the correct offset.

What's happening behind it

The check is one 32-bit comparison, so it costs nothing next to the disk read. If the bytes were uniformly random, a false match would happen with probability 1 ÷ 232 = 1 in 4,294,967,296 ≈ 2.3 × 10−10 (my calculation, assuming random bytes; real data is not random, so "PAGE" could appear inside a text value). That's why it is a sanity check for gross mistakes such as a wrong offset, a wrong file, or a page of the wrong kind. It does not detect a flipped bit in the middle of the page; that is what checksums are for.

Beyond the book
  • SQLite's file starts with the 16-byte string "SQLite format 3" plus a NUL byte (file format).
  • PostgreSQL pages carry a 2-byte pd_checksum (filled when data checksums are enabled, see section 01). Magic number = "right kind of block?"; checksum = "are these bytes intact?". Before → after: without either, a misaligned or torn read is silently interpreted as data; a magic number catches the first, a checksum the second.
Reference

[GIAMPAOLO98] Giampaolo, Dominic. 1998. Practical File System Design with the Be File System. Morgan Kaufmann. A file-system designer's book; it is where the "use magic numbers for sanity checks" habit is discussed. Worth it if you want to see the same page/block problems from the file-system side.

03 · SIBLING LINKS

Walk sideways instead of up and down

pdf p114–115 · Fig 4-1

Some implementations store forward and backward links to the left and right sibling pages. They let you find a neighbour without climbing back to the parent. Without them (Fig 4-1a), you have to go through the parent, and this can climb all the way to the root, because a parent can only point to its own children. With the links in the header (Fig 4-1b), you just follow them to the previous or next node on the same level.

The cost: links make splits and merges more complex because the sibling offsets must be updated too. Example from the book: when a node that is not the rightmost splits, its right sibling's backward pointer (which pointed to the node that split) must be re-bound to the newly created node. And because that update happens in the sibling node, not in the node being split or merged, it may need extra locking. Petrov returns to this in "Blink-Trees" (Chapter 5).

Picture it

Houses on a street. With sibling links, you walk next door. Without them, you must go back to the street junction (the parent), and if your house is the last one on that block, back to the main road (the grandparent), then down the next block's road to its first house.

What's happening behind it

Going from leaf i to leaf i+1 through parents means climbing to their lowest common ancestor and coming back down the same number of levels. Stepping from a leaf that is not its parent's last child costs 2 node visits (up to the parent, down to the next leaf); stepping from a parent's last child costs 4 (up to the grandparent and back down two levels), and so on for each extra level climbed. A range scan does this for every leaf it crosses. With sibling links, every step is exactly one visit. The price is paid on writes: a split now touches three nodes (the old node, the new node, and the old right sibling).

// split of node A (not rightmost) into A and A2, with double links
A2.next = A.next;  A2.prev = A;
A.next.prev = A2;  // the re-bind the book describes: a write to the SIBLING page
A.next = A2;
Measured on a model: average visits per "next leaf" step

Model: a full tree with fh−1 leaves; visits = up-hops + down-hops. For f = 3, h = 3 there are 9 leaves and 8 steps; 6 steps climb one level (2 visits) and 2 steps climb two levels (4 visits): (6×2 + 2×4) ÷ 8 = 2.5 visits vs 1. With real fanouts in the hundreds the average falls to just over 2, because few leaves are the last child. The bigger win is concurrency, not the count (Chapter 5).

Beyond the book: where it's used
  • PostgreSQL: B-tree index pages keep left and right sibling links in the page's special space (docs). Its nbtree README describes Lehman & Yao right-links: if the search key is greater than a page's high key, the page "must've been split concurrently", so the search follows the right-link (README).
  • WiredTiger (MongoDB) is the book's counter-example: it walks leaves through parent pointers instead (section 08).
Reference papers

Introduces right-links + high keys so readers can survive a concurrent split without locks on the way down. The basis of PostgreSQL's nbtree. Read it before Chapter 5's Blink-Trees.
  • [MILLER78] Miller, R., and L. Snyder. 1978. "Multiple access to B-trees." Conference on Information Sciences and Systems, Johns Hopkins University. Early work on concurrent access, cited with LEHMAN81 for the deadlock risk of sibling pointers (section 08).

04 · RIGHTMOST POINTERS

N keys, N + 1 pointers: where does the extra one live?

pdf p116–117 · Fig 4-2, 4-3

Separator keys split the tree into subtrees and guide navigation, so there is always one more child pointer than there are keys. That's the "+1" from "Counting Keys" in Chapter 2. In many implementations a node looks like Fig 4-2: each separator key is stored in a cell together with a child pointer, and the last pointer is stored separately because it has no key to pair with (compare with Fig 2-10). That extra pointer can live in the page header, as SQLite does.

When the rightmost child splits and a new cell is appended to its parent, the rightmost pointer must be reassigned (Fig 4-3). After the split, the cell appended to the parent holds the promoted key and points to the node that was split; the pointer to the new node replaces the old rightmost pointer. SQLite describes and implements a similar approach (the book's footnote points to its balance_deeper function).

Picture it

A row of numbered fence posts with rails between them: three posts (keys) make four gaps (pointers) if you count the open ground after the last post. Petrov's layout puts "the gap before post i" on post i's label, and writes "everything after the last post" on the gate (the header).

step 1/3
What's happening behind it

Each cell is a (pointer, key) pair: the pointer next to Ki covers keys below Ki (and at or above Ki−1). Keys at or above the last key go to the header pointer. When the rightmost child splits into a left half and a new right half, the promoted key becomes the new last separator: its cell takes over the old child (the left half, everything below the promoted key), and the header pointer moves to the new right node (everything from the promoted key up). Nothing else in the parent moves, which is why this path is cheap.

// parent: cells[] = (childPtr, key) pairs; header.rightmost = last pointer
function onRightmostChildSplit(parent, splitNode, promotedKey, newNode) {
  parent.cells.push({ ptr: splitNode, key: promotedKey }); // new last cell → left half
  parent.header.rightmost = newNode;                      // header → new right half
}
Beyond the book

SQLite: interior b-tree pages have a 12-byte header instead of 8; the extra 4 bytes at offset 8 are the page number of the right-most child (file format). That's exactly the "rightmost pointer in the header" of Fig 4-2.

05 · NODE HIGH KEYS

Give the last pointer a key too: the upper bound

pdf p118–119 · Fig 4-4, 4-5

A slightly different approach: store the rightmost pointer in a cell together with the node's high key, the highest possible key that can be present in the subtree under the current node. PostgreSQL uses this; the structure is called a Blink-Tree.

The notation: a node has N keys Ki and N + 1 pointers Pi. In each subtree, keys are bounded by Ki−1 ≤ Ks < Ki. K0 = −∞ is implicit and not stored. Blink-Trees add a key KN+1 to each node: the upper bound for the subtree that PN points to, and so the upper bound for everything under the current node (Fig 4-4). Now pointers can be stored pairwise: every cell has a pointer, which removes edge cases around the rightmost pointer. Fig 4-5 shows how the search space is split: up to +∞ without a high key, up to K3 with one.

Picture it

Two shops' opening-hours signs. One says "last entry: whenever". The other says "last entry: 6 pm". If you arrive at 7 pm, the first shop lets you in and you search for nothing; the second tells you at the door that you're in the wrong place, so go next door.

What's happening behind it

Without a high key the last pointer's range is open-ended: the node itself cannot tell whether a key belongs anywhere under it. With a high key the node knows its whole range [low, high). That costs one extra key per node, and buys two things. (1) Uniform cells: every cell is (key, pointer), so there is no special header slot to keep in sync. (2) Self-checking during concurrency: if a reader arrives at a node and its key is ≥ the high key, the node must have been split while the reader was on its way down, and the rest of the keys are to the right. That's the Blink-Tree move-right rule (Chapter 5).

Worked example

Node keys 20 and 40, high key 60. Search 47: both layouts follow P2 (40 ≤ 47 < +∞ or < 60). Search 70: layout (a) still follows P2 and searches a subtree that cannot hold 70. Layout (b) sees 70 ≥ 60 and knows at once the key is not under this node. Slide to 70 above.

Beyond the book

PostgreSQL's nbtree README: each page carries a high key that is "an upper bound on the keys that are allowed on that page"; a search key greater than it means a concurrent split happened, so the scan moves right (README).

Reference paper

[LEHMAN81] (see section 03). The high key plus the right-link is the core of their algorithm.

06 · OVERFLOW PAGES

When a value is bigger than its share of a page

pdf p120–122 · Fig 4-6

Node size and fanout are fixed; they don't change at runtime. No single value is ideal: if values vary in size and some are large, only a few fit in a page; if values are tiny, reserved space is wasted. The B-Tree algorithm says a node holds a certain number of items, so with variable sizes a node can be "not full" by count while its fixed-size page has no space left. Resizing the page means copying already written data to a new region, which is often impractical.

The fix: build a node from several linked pages. Example from the book: the default page size is 4 K; after a few inserts the data has grown past 4 K. Instead of arbitrary sizes, nodes grow in 4 K increments: allocate a 4 K extension page and link it from the original. The extensions are overflow pages; the original is the primary page.

  • Most implementations store only a fixed number of payload bytes in the node itself and spill the rest. That limit is max_payload_size = node size ÷ fanout. Then a page can never be left with no free space: it always has room for at least max_payload_size bytes.
  • If an inserted payload is larger than max_payload_size, check whether the node already has an overflow page with enough space. If so, the extra bytes go there; if not, allocate a new overflow page.
  • The first overflow page's ID is stored in the primary page's header. More overflow pages are chained: each stores the next one's ID in its header. Several pages may have to be traversed to reach a payload's overflow part.
  • Overflow pages need bookkeeping: they fragment like primary pages, their space must be reclaimable, and they must be discarded when no longer needed.
  • Keys usually have high cardinality, so keeping a part of a key in the primary page makes sense: most comparisons can be decided on that trimmed part.
  • Data records do need their overflow parts to be found and returned to the user, but that's infrequent. If all records are oversize, consider specialised blob storage.
Picture it

An office mailbox wall where each person gets one pigeonhole of fixed width. A parcel that doesn't fit leaves a slip in the pigeonhole ("rest in the back room, shelf 3"). The pigeonhole wall never jams, and most people only ever need their pigeonhole.

What's happening behind it

Capping each record's in-page share at node size ÷ fanout makes the count-based B-Tree rule and the byte-based page agree again: fanout records × max_payload_size = one node. The overflow chain is a singly linked list, so reaching the payload on the 3rd overflow page means reading the primary page and overflow pages 1, 2 and 3. In the simulation, overflow pages are shared by the node's records, as in Fig 4-6 (two records continue on the same overflow page); I assume a 24-byte primary header and a 4-byte "next page" header on each overflow page.

Worked example (modelled)

4,096-byte node, fanout 8: max_payload_size = 4,096 ÷ 8 = 512 bytes. A 1,500-byte record keeps 512 bytes in the primary page and spills 988. An overflow page has 4,096 − 4 = 4,092 usable bytes, so four such records spill 3,952 bytes into one page and the fifth spills across into a second. Returning that fifth record reads the primary page plus two overflow pages. The simulation opens in exactly this state: five 1,500-byte records with the defaults.

SQLite (file format), with U = usable page size: a table-leaf payload stays fully on the page if it is at most X = U − 35 bytes; an index payload if at most X = ((U − 12) × 64 ÷ 255) − 23. When it spills, at least M = ((U − 12) × 32 ÷ 255) − 23 bytes stay local. Each overflow page starts with a 4-byte next-page number (0 on the last page). For the node size you picked:

07 · BINARY SEARCH · BINARY SEARCH WITH INDIRECTION POINTERS

Search the sorted pointers, compare the unsorted cells

pdf p123–124 · Fig 4-7

Inside a node, the searched key is located with binary search (Chapter 2's lookup algorithm). Binary search works only on sorted data, which is why keeping keys in order (the sorted invariant) is essential.

The algorithm takes a sorted array and a key and returns a number. A positive result means the key was found, and the number is its position. A negative result means the key is absent, and it encodes the insertion point: the index of the first element greater than the key. Its absolute value is where the key can be inserted to keep the order; you insert by shifting the elements from that point one position over [SEDGEWICK11]. On higher levels most searches are not exact matches; what matters is the direction: find the first value greater than the searched key and follow the matching child link.

With indirection pointers: cells in a B-Tree page are stored in insertion order, and only the cell offsets keep the logical (sorted) order. So binary search picks the middle offset, follows it to its cell, compares that cell's key with the searched key, and goes left or right, repeating until it finds the key or the insertion point (Fig 4-7).

Picture it

A library's card catalogue is alphabetical, but the books are shelved in the order they arrived. To find a title, you open the catalogue in the middle, walk to the shelf the card points to, read the spine, and decide whether to look earlier or later in the catalogue. Every comparison costs one trip to a shelf.

// the code the stepper runs. offsets[] is sorted by key; cells[] is in insertion order
function binarySearchCells(offsets, cells, key) {
  let lo = 0, hi = offsets.length - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >>> 1;
    const cellKey = cells[offsets[mid]].key;   // follow the indirection pointer
    if (cellKey < key) lo = mid + 1;
    else if (cellKey > key) hi = mid - 1;
    else return mid;                           // found: its position
  }
  return -(lo + 1);                            // absent: insertion point = lo
}
What's happening behind it

Each round halves the range of offsets, so n cells need at most ⌈log2(n + 1)⌉ comparisons. Each comparison costs a jump from the offset array to a cell somewhere else in the page (a likely CPU cache miss), which is the price of the indirection. The benefit: inserting a cell never moves other cells, only a few small offsets, so keeping order is cheap.

A detail the book glosses over (not in the book): "positive = found, negative = insertion point" is ambiguous when the answer is position 0, because there is no −0. Java's Arrays.binarySearch and the code above solve it by returning −(insertionPoint) − 1, so absent keys are always ≤ −1. Decode with insertionPoint = −result − 1.

Worked example + calculator

12 cells, sorted keys 3, 7, 15, 23, 34, 42, 50, 61, 70, 77, 88, 99. Search 61: compare 42 (go right), 70 (go left), 50 (go right), 61: found at position 7 after 4 comparisons, each one a hop to a cell. Search 55 (absent): the same four comparisons, then lo (7) passes hi (6): insertion point 7, returned as −8. Linear scan would have needed 8 comparisons.

08 · PROPAGATING SPLITS AND MERGES

Finding the way back up: parent pointers

pdf p125

Splits and merges can propagate to higher levels (Chapter 2), so we must be able to walk from the splitting leaf, or from a pair of merging leaves, back to the root. One way: nodes keep parent pointers. Because a lower-level page is always paged in by following a reference from a higher level, these pointers don't need to be persisted on disk: they can be filled in when the page is loaded.

Like sibling pointers, parent pointers must be updated whenever the parent changes: every time a separator key with its page identifier is moved from one node to another, i.e. during splits, merges or rebalancing of the parent.

Some implementations, for example WiredTiger, use parent pointers for leaf traversal to avoid deadlocks that can happen with sibling pointers [MILLER78], [LEHMAN81]. Instead of following sibling links, the algorithm goes through the parent, much like Fig 4-1a: follow the next pointer in the parent and descend. When it reaches the end of the parent after visiting all the siblings that share it, it continues upward recursively, possibly to the root, and back down to the leaf level.

Picture it

Every employee's badge says who their manager is. Useful, until a team is split in two: then HR has to re-print the badges of everyone who moved to the new team. That reprint is the hidden cost of parent pointers.

parent pointer had to be (re)written by the last insertleaf that received the key
What's happening behind it

A leaf split creates one new node, which needs its parent pointer set. An internal split is worse: every child that moves to the new right node now has a different parent. With fanout f that's about f ÷ 2 children, and each of them is a separate page whose in-memory header must be updated (and loaded, if it isn't already). A root split rewrites two more. The simulation counts these writes exactly by comparing every node's parent before and after the insert. With real fanouts of hundreds, an internal split means hundreds of pointer updates, which is why the breadcrumb approach (next section) is popular.

Worked example

Capacity 3 keys: an internal node that overflows has 4 keys and 5 children. It keeps 2 keys and 3 children; 1 key moves up; the new right node gets 1 key and 2 children, whose 2 parent pointers must be rewritten. The new right node itself needs its pointer set too (it hangs under the old parent), and the new leaf from the leaf split needs one. That is 4 writes in total, or 3 when the new leaf is itself one of the children that moved (its pointer is then written once, already pointing at the new node). The readout counts each node whose parent changed once. Click "Insert" until you see an internal split and check the readout.

Beyond the book: why sibling walks can deadlock

If one thread walks leaves left to right holding a latch on the current leaf while acquiring the next, and another thread (a reverse scan, or a merge) latches right to left, each can hold what the other needs. Going through the parent keeps every latch acquisition top-down, a single global order, which rules out that cycle. PostgreSQL takes the other route: it keeps sibling links; a reader holds a page lock only while it examines that page, inserters couple locks only when moving right, and the nbtree README notes that backward scans need extra care.

09 · BREADCRUMBS

Remember the path on the way down, use it on the way up

pdf p126–127 · Fig 4-8

Instead of storing and maintaining parent pointers, keep track of the nodes you traversed on the way to the target leaf, and follow that chain in reverse if inserts cause cascading splits, or deletes cause merges.

  • An operation that may change the structure (insert or delete) first descends from the root to the leaf to find the target node and the insertion point.
  • We don't know in advance whether it will split or merge (not until the leaf is found), so we collect breadcrumbs on the way: references to the nodes followed from the root.
  • The natural data structure is a stack, kept in memory. PostgreSQL calls it BTStack (the book's footnote 2 points to databass.dev/links/21).
  • Fig 4-8: each breadcrumb holds the visited node and the index of the child pointer followed. If the leaf splits, pop the top entry to get its immediate parent. If the parent has room, append the new cell at the cell index from the breadcrumb (assuming the index is still valid). Otherwise split the parent as well, and repeat until the stack is empty and we've reached the root, or a level didn't split.
Picture it

Hansel and Gretel. You don't need a map with "way home" arrows painted on every tree (parent pointers); you drop crumbs on the way in, and pick them up in reverse order on the way out. Crumbs cost nothing when you never need to go back.

step 0/0
on the breadcrumb stacknode being worked on
What's happening behind it

The stack has exactly one entry per level, so it costs height small records of memory, and nothing at all on disk. Each entry stores which pointer we followed, so when a split pushes a separator up, we already know where it goes in the parent: right after that pointer. No search of the parent is needed. The catch in the book's phrase "assuming the index is still valid": if other threads changed the parent between our descent and our split, the remembered index can be stale, and the implementation must re-find the right position (or the right parent).

// descent (from the insert() this page runs)
const stack = []; let n = T.root;
while (!n.leaf) {
  const i = upperBound(n.keys, k);   // first separator > k
  stack.push({ node: n, idx: i });  // breadcrumb: node + child index
  n = n.kids[i];
}
// ...insert into leaf n; if it overflows, split and then:
function attach(T, stack, left, sep, right) {
  if (!stack.length) { T.root = mkNode(false, [sep], [left, right]); return; } // root split: tree grows
  const { node: p, idx } = stack.pop();      // immediate parent
  p.keys.splice(idx, 0, sep); p.kids.splice(idx + 1, 0, right);
  if (p.keys.length > T.cap) splitInternalAndAttach(T, stack, p); // may cascade
}
Worked example (default tree, insert 41)

Root [13, 51]: 41 is between 13 and 51, so follow pointer 1 and push (root, 1). Node [23, 31, 37]: 41 ≥ 37, follow pointer 3 and push. Leaf [37, 40, 45] becomes [37, 40, 41, 45], over the capacity of 3. Split into [37, 40] and [41, 45]; pop → parent [23, 31, 37]; insert 41 at index 3 → [23, 31, 37, 41], over capacity. Split it: 37 moves up; pop → root; insert 37 at index 1 → [13, 37, 51]. The root had room, so the cascade stops with one entry used from each level. Run it: the root is now full (3 keys). Then insert 42, 43, 44, 46, 47 and 48 one at a time. The last insert splits leaf [45, 46, 47], then its parent [41, 43, 45], then the root itself, and the tree grows from height 3 to 4 with the new root [45] (checked with this page's code).

Beyond the book

PostgreSQL's nbtree README says the stack built during descent is used to find parents, but it "does not help" when an inserter must go above the level that was the root when its descent began (the root split concurrently). Then it re-descends the tree to the right level and moves right as needed; downlinks are matched by block number, not by key (README). That is the "index still valid?" caveat handled for real.

10 · REBALANCING

Postpone the split: shift keys to a neighbour, or split two into three

pdf p128–129 · Fig 4-9

Some implementations postpone splits and merges to amortise their cost: they rebalance elements within a level, moving them from more occupied nodes to less occupied ones for as long as possible before finally splitting or merging. This improves node occupancy and may reduce the number of levels, at a potentially higher maintenance cost.

  • Load balancing can happen during inserts and deletes [GRAEFE11]. On insert, instead of splitting an overflowing node, move some elements to a sibling. On delete, instead of merging, move elements from a neighbour so the node stays at least half full.
  • B*-Trees keep distributing between neighbours until both are full [KNUTH98]. Then, instead of splitting one node into two half-empty ones, they split two nodes into three, each two-thirds full. SQLite uses this variant.
  • This raises average occupancy by postponing splits, but needs extra tracking and balancing logic. Higher utilisation also means faster searches: the tree is shorter, so fewer pages are read on the way to a leaf.
  • Fig 4-9: elements move from the fuller left sibling to the emptier right one. Because this changes the min/max range of both siblings, the separator key and pointer in the parent must be updated.
  • SQLite implements a "balance-siblings" algorithm close to this. Balancing adds code complexity, but because its use is isolated, it can be added later as an optimisation.
Picture it

Packing books into boxes. Plain splitting: when a box is full, open a new box and move half the books into it. Rebalancing: first check whether the box next to it has room and slide some books over. B*: when both neighbouring boxes are full, repack the two into three boxes, each two-thirds full. Fewer half-empty boxes, more lifting.

Worked example (my numbers, same idea as Fig 4-9)

Parent [18] over leaves [10, 13, 16] and [18], capacity 3. Insert 12. Plain split: [10, 12] | [13, 16], separator 13 goes up, parent [13, 18], three leaves. Rebalance: the right sibling has room; spread the five keys as [10, 12, 13] | [16, 18] and change the parent's separator from 18 to 16; still two leaves. B* with both siblings full ([10, 13, 16] and [18, 20, 22]): seven keys become [10, 12, 13] | [16, 18] | [20, 22] and the parent's single separator 18 is replaced by 16 and 20.

Measured on simulated inserts: occupancy vs work

Each bar pools 6 runs with different random key orders (simulated, using the same insert() code as the step-through; the range shows the lowest and highest run). "Keys moved" counts keys shifted between siblings by rebalancing, the extra maintenance work the book warns about.

What's happening behind it

With random keys, a plain-splitting B-Tree settles at roughly 69–70% full: every split makes two half-full nodes, which then fill up to 100% before splitting again, so the average sits between. Sharing with a neighbour means a node only splits when its neighbourhood is full, so the average climbs to the mid-80s in this simulation, and B*'s two-thirds-full splits push it a little higher. Fuller leaves → fewer leaves → (sometimes) one level less, and fewer pages read per lookup and per range scan. The bill: every rebalance reads and rewrites a sibling and updates the parent, so a write touches three pages instead of one most of the time.

  • InnoDB, the delete side: if a page's fill drops below MERGE_THRESHOLD (50% by default), InnoDB tries to merge it with a neighbour (MySQL docs).

11 · RIGHT-ONLY APPENDS

Auto-increment keys: every insert hits the rightmost leaf

pdf p130

Many databases use auto-incremented, monotonically increasing primary keys. Then all inserts land at the end of the index, in the rightmost leaf, and most splits happen on the rightmost node of each level. Also, as long as updates and deletes are rare next to appends, non-leaf pages are less fragmented than with random keys. (Taken word for word, the book's sentence says the ratio of appends to updates and deletes is low; read in context, the intended meaning is that updates and deletes are the rare ones.)

  • PostgreSQL "fastpath": if the new key is strictly greater than the first key in the rightmost page, and that page has room, the entry is inserted straight into the cached rightmost leaf, skipping the whole read path from the root.
  • SQLite "quickbalance": if the entry is inserted at the far right end and the target node is full (the new entry becomes the largest key in the tree), then instead of rebalancing or splitting, it allocates a new rightmost node and adds its pointer to the parent. The new page starts nearly empty (instead of half empty after a split), but it will very likely fill up soon.
Picture it

A ledger book. When the last page fills, a normal B-Tree tears it in half and continues on a half-empty page, leaving a trail of half-empty pages behind forever (nobody will write in the past). Quickbalance just turns to a fresh page and leaves the full one full. The fastpath is keeping your finger on the last page instead of opening the book from the front each time.

What's happening behind it

With ascending keys a middle split leaves the left half at 50% and nothing will ever be inserted there again, so the whole leaf level ends up half empty: twice the pages, twice the I/O for a range scan, a bigger cache footprint. Quickbalance (or a split that leaves the left page nearly full) fixes the occupancy. The fastpath fixes the CPU and buffer-pool cost: instead of reading height pages per insert, most inserts touch only the cached leaf; only the insert that fills it pays for a full descent. With random keys both tricks almost never trigger, and the tree behaves like section 10's plain splits (≈ 70%).

Worked example (simulated, 16 keys per leaf, 1,000 ascending inserts)

Middle split: 124 leaves at 50% fill. Quickbalance: 63 leaves at 99% fill, half the pages. 90%-left split: 72 leaves at 87% fill. Node reads: about 2,840 without the fastpath (a full descent per insert) vs about 350 with it, roughly 8× fewer, because only about one insert in eight with middle splits (one in sixteen with quickbalance) needs to descend. These come from this page's code; real gains depend on page size and caching.

Beyond the book: the same idea in production
  • PostgreSQL: B-tree fillfactor defaults to 90 and applies to leaf pages during initial index builds and "when extending the index at the right (adding new largest key values)" (CREATE INDEX). The fastpath caches the last page a backend inserted into if it was the rightmost leaf (nbtree README).
  • InnoDB leaves 1/16 of a clustered-index page free for future growth: with sequential inserts pages end up about 15/16 full; with random inserts, anywhere from 1/2 to 15/16 (MySQL docs). Before → after in one sentence: random UUID primary keys cost you page fill and cache space that sequential keys get for free.

12 · BULK LOADING

Building a tree from sorted data: bottom-up, no splits

pdf p131

If the data is already sorted (a bulk load, or rebuilding a tree, e.g. to defragment it), the right-only-append idea goes further. All items go to the rightmost position, so we can avoid splits and merges altogether and compose the tree from the bottom up: write it out level by level, or write higher-level nodes as soon as there are enough pointers to already-written lower-level nodes.

  • One approach: write the sorted data to the leaf level page-wise (not element by element). After each leaf is written, propagate its first key to the parent, and build the higher levels with the normal algorithm [RAMAKRISHNAN03]. Since keys arrive in order, every split is on the rightmost node.
  • Because B-Trees are always built from the leaf level up, the whole leaf level can be written before any higher node is composed, so all child pointers are at hand when the higher levels are built.
  • Main benefits: no splits or merges on disk, and only a minimal part of the tree (the parents of the leaf being filled) has to be in memory during construction.
  • Immutable B-Trees are built the same way, but need no spare space for later modifications because every operation on them is final: all pages can be completely filled, improving occupancy and performance.
Picture it

Building a sorted filing cabinet from a sorted pile of papers. You don't insert each paper and reorganise drawers as they overflow; you fill drawer after drawer in order, and every time you finish a drawer you write its first label on the cabinet's index card.

step 1 
// streaming bulk load: open[l] is the node currently being filled at level l
function addChild(l, child) {
  let n = open[l];
  if (n && n.kids.length === perNode) { open[l] = null; addChild(l + 1, n); n = null; } // full: hand it up
  if (!n) n = open[l] = mkNode(false);
  if (n.kids.length) n.keys.push(minKey(child));  // the child's first key becomes a separator
  n.kids.push(child);
}
for (let i = 0; i < keys.length; i += perLeaf) addChild(1, mkNode(true, keys.slice(i, i + perLeaf)));
// at the end, close the open nodes bottom-up; the highest one is the root
What's happening behind it

Each leaf is written once, full (or at the fill you choose), and never touched again. Each internal node is written once, when it's full or the input ends. In memory you only hold the "right spine": one open node per level. That's height pages, a few KB, even for a billion-row index. Inserting the same sorted keys one at a time instead does a descent per key and a split every time the rightmost leaf fills, and (with middle splits) leaves every leaf half empty. The readout compares the two on the same keys.

Worked example (simulated, capacity 3 keys)

30 sorted keys at 100% fill: 10 leaves of 3 keys, 3 internal nodes plus a root: 14 pages written, height 3, zero splits. Inserting the same 30 keys one at a time with middle splits: 19 splits, 15 half-full leaves, height 4. At 60 keys: 28 pages vs 40 splits and 30 leaves.

Beyond the book
  • InnoDB builds or rebuilds indexes with a "sorted index build" (a bulk load); innodb_fill_factor sets how full each page is made, and at 100 it still leaves 1/16 of clustered-index pages free (MySQL docs).
  • PostgreSQL CREATE INDEX sorts and fills leaf pages to the fillfactor (default 90) (docs). That's why REINDEX shrinks a bloated index: it's a bulk load.

13 · COMPRESSION

Smaller pages, but disk blocks don't shrink with them

pdf p132–133 · Fig 4-10

Storing raw data can mean significant overhead, and many databases offer compression. The trade-off is between access speed and compression ratio: higher ratios shrink data, so one access fetches more, but compressing and decompressing costs RAM and CPU.

  • Whole-file compression gives better ratios but has limited use: the whole file must be recompressed on an update. Compressing an entire index file is impractical and hard to do efficiently, because to reach one page you must access the whole file (or the section holding compression metadata) to locate the compressed section, decompress it, and make it available. Finer granularity suits larger datasets.
  • Page-wise compression fits fixed-size pages: pages are compressed and decompressed independently, together with loading and flushing. But a compressed page may occupy only part of a disk block, and since transfers happen in whole blocks, extra bytes may be paged in [RAY95]. Fig 4-10: (a) a compressed page smaller than a block also pulls in bytes of another page; (b) a page that spans blocks forces an additional block read.
  • Data-only compression, either row-wise (whole records) or column-wise (each column separately): page management and compression are decoupled.
  • Most open-source databases Petrov reviewed have pluggable compression using libraries such as Snappy, zLib, lz4 and others. Results depend on the dataset and goals, so the book doesn't compare them; benchmarks such as the Squash Compression Benchmark evaluate algorithms on different block sizes using four metrics: memory overhead, compression speed, decompression speed, and compression ratio. Weigh these when choosing a library.
Picture it

Vacuum-packing clothes to fit more in a suitcase, but the airline only accepts whole bags. A pack that's half a bag still costs a bag; a pack slightly bigger than a bag costs two. And you have to unpack before you can wear anything.

What's happening behind it

Two ways to place compressed pages, both with a cost. Packed: no wasted disk space, but a page usually straddles block boundaries, so reading it pulls in parts of its neighbours (Fig 4-10a and b). Padded to whole blocks: each page starts on a block boundary, but the tail of its last block is wasted disk space, and a 16 KB page compressed 2.3× (7.1 KB) still costs two 4 KB blocks, saving only half the I/O you hoped for. The readout averages over 200 consecutive pages (a model, not a measurement of any engine).

Worked example (modelled)

16 KB page, 4 KB blocks, ratio 2.3×: compressed size 16,384 ÷ 2.3 ≈ 7,124 bytes. Padded: 2 blocks = 8,192 bytes per read and per page on disk (vs 4 blocks uncompressed: I/O halved, 13% of each read is padding). Packed: about 2.7 blocks per page read on average, because most pages cross three blocks, but disk space is exactly 7,124 bytes per page. Try ratio 4.0: a 4,096-byte page fits one block exactly when padded.

Reference

[RAY95] Ray, Gautam, Jayant Haritsa, and S. Seshadri. 1995. "Database Compression: A Performance Enhancement Tool." COMAD. An early study arguing that compression is a performance tool (less I/O), not just a space saver, and looking at granularity.

14 · VACUUM AND MAINTENANCE

Live cells, garbage cells, and space you can't use

pdf p134–135 · Fig 4-11

Besides user-facing operations, other processes run in parallel with queries to maintain storage integrity, reclaim space, reduce overhead and keep pages in order. Doing this in the background saves time and avoids paying for cleanup during inserts, updates and deletes.

Slotted pages (Chapter 3) need this maintenance. Splits and merges of internal nodes, or inserts, updates and deletes on leaves, can leave a page with enough logical space but not enough contiguous space: it is fragmented. Fig 4-11: the free space is split between two deleted (garbage) records and the gap between the header/cell pointers and the cells.

B-Trees are navigated from the root. Records you can reach by following pointers down from the root are live (addressable). Records you can't reach are garbage: nothing references them, they can't be read or interpreted, so their contents are as good as nullified. In a page, cells that still have an offset pointing at them are addressable; removed or overwritten ones are not. Zero-filling garbage is often skipped for performance, since the space will be overwritten by new data anyway.

Picture it

A parking lot where removed cars leave their painted bays behind. Three free single bays scattered between parked cars don't fit a bus, even though their total length would. Someone has to repaint the lot (compact it) before the bus can park.

cell offsetslive cell (has an offset)garbage cell (no offset)
What's happening behind it

"Free space" means two different numbers. Logical free = page size − header − offsets − live cells. Contiguous free = upper − lower, the only space a new cell can be written into without moving anything. Every delete or out-of-place update raises the first and leaves the second unchanged; the gap between them is fragmentation. A cell is garbage simply because no offset points to it. That's why "deleting" is just removing a 2–4 byte offset, and why the old bytes are still physically there until something overwrites them.

15 · FRAGMENTATION CAUSED BY UPDATES AND DELETES

How a page ends up full of holes

pdf p136–137
  • Deletes on the leaf level only remove the cell's offset from the header; the cell itself stays. It is no longer addressable, won't appear in results, and nothing needs to be nullified or moved.
  • Splits only trim offsets: cells whose offsets were cut off (they moved to the new page) are unreachable here, and get overwritten when new data arrives or collected when vacuum runs.
  • Because deletes neither relocate the remaining cells nor physically remove the target, freed bytes end up scattered across the page: it is fragmented and needs defragmentation. A write usually needs one contiguous block of free bytes, so to gather the fragments the page must be rewritten.
  • Inserts leave tuples in insertion order. That matters less, but naturally sorted tuples help cache prefetch during sequential reads.
  • Updates matter mostly on the leaf level, because internal keys only guide navigation and define subtree boundaries. Updates are per key and generally cause no structural change, apart from creating overflow pages. On leaves, an update doesn't change cell order and tries to avoid rewriting the page, so several versions of a cell may be stored, only one of them addressable.
Note from the book: garbage kept on purpose (MVCC)

Some databases rely on garbage collection and leave removed and updated cells in place for multiversion concurrency control. The old cells stay accessible to concurrently running transactions until the update completes, and can be collected once no other thread uses them. Some databases track ghost records, which are collected as soon as every transaction that may have seen them has completed [WEIKUM01].

cell offsetslive cellgarbage
What's happening behind it

Watch the two free-space numbers. Delete: logical free goes up by the cell size + offset; contiguous free goes up only by the offset. Update: the new version is written as a new cell at upper, the offset is re-pointed to it, and the old version becomes garbage: one update costs the old cell's bytes until compaction. Split: half the offsets vanish in one go, leaving half the page as garbage. When an insert fails although logical free is enough, the page is fragmented: either compact it now (synchronous, the "on write" option) or let it split or overflow unnecessarily.

Worked example (toy 512-byte page, 24-byte header, 4-byte offsets)

Nine 40–60 byte cells fill the page until only 2 contiguous bytes remain. Delete two cells (100 bytes between them): logical free becomes 110 bytes, but contiguous free is only 10 (the two freed offsets). A 60-byte insert fails as "fragmented". Compacting reclaims the 100 garbage bytes into one 110-byte gap and the insert succeeds. (These are the numbers from the test of this page's code.)

16 · PAGE DEFRAGMENTATION

Compaction, vacuum, and the freelist

pdf p138 · footnote 3 p140

The process that reclaims space and rewrites pages is called compaction, vacuum, or just maintenance. A page can be rewritten synchronously on write when it lacks free physical space (to avoid creating unnecessary overflow pages), but compaction usually means a separate, asynchronous process that walks through pages, collects garbage and rewrites their contents.

  • It reclaims the space of dead cells and rewrites cells in their logical (key) order.
  • Rewritten pages may be relocated to new positions in the file. Unused in-memory pages go back to the page cache.
  • IDs of newly available on-disk pages go on the free page list (a freelist). This list must be persisted, so it survives crashes and restarts and free space is not lost or leaked.
  • Footnote 3: SQLite, for example, keeps a list of unused pages in which trunk pages form a linked list and hold the addresses of freed pages.
Picture it

A night cleaning crew in an office. During the day people just push old papers aside (deletes). At night the crew tidies each desk (compaction), clears out desks nobody uses anymore, and writes their numbers on the "free desks" whiteboard at the entrance (freelist). If the whiteboard gets wiped in a power cut, those desks sit empty and unused forever: leaked.

live bytesgarbagevacuum position
What's happening behind it

Vacuum does two separate jobs. Inside a page it is the compaction from section 15: drop garbage, write live cells back in key order, restore one contiguous free gap. Across the file it finds pages with nothing live left and returns them: the file doesn't shrink, but the next allocation reuses a freed page instead of growing the file. The freelist itself is metadata that must be written durably (and logged) like any other page; untick "freelist persisted", vacuum, then crash: the freed pages are neither in the tree nor in the list, so nothing will ever reuse them.

Beyond the book
  • SQLite freelist (file format): the database header stores the first trunk page at offset 32 and the total freelist page count at offset 36. Each trunk page holds the next trunk page number, a count L, and L page numbers of free "leaf" pages, which themselves contain no information.
  • PostgreSQL nbtree (README): a page is deleted only when completely empty, in two stages (unlinked from its parent, then from its siblings), and cannot be recycled immediately: it is stamped with the next transaction id and reused only once that is visible to everyone, because a concurrent scan might still be heading to it. Since PostgreSQL 14, VACUUM can also put newly deleted pages into the free space map at the end of its index scan.

Check yourself

answer before you open
1. A page has 900 bytes of logical free space but an insert of a 200-byte cell fails. How?

The free space is fragmented: most of it is garbage cells scattered between live ones, and the contiguous gap (upper − lower) is under 204 bytes. The page needs compaction, not a split (sections 14–15).

2. Why can parent pointers live only in memory, while sibling links usually live on disk?

You can only reach a child page by following a pointer from its parent, so the parent is known when the child is loaded and the pointer can be filled in then. A sibling link is used to reach a page you didn't come from, so it has to be stored (sections 03, 08).

3. An internal node with fanout 400 splits. What does that cost with parent pointers, and with breadcrumbs?

Parent pointers: about 200 children move to the new node, so about 200 pages need their parent pointer updated (loaded if not cached). Breadcrumbs: nothing; the path is in an in-memory stack, one entry per level (sections 08–09).

4. A Blink-Tree reader lands on a node with high key 60 while searching for 70. What happened and what does it do?

The node was split concurrently after the reader read the parent; keys ≥ 60 now live in the right sibling. It follows the sibling (right) link instead of restarting (section 05; Chapter 5 Blink-Trees).

5. Node size 8,192 bytes, fanout 16. What is max_payload_size, and why does it guarantee a page never runs out of room for a record?

8,192 ÷ 16 = 512 bytes. Each record keeps at most 512 bytes in the node, so 16 records (the B-Tree's count limit) always fit in the node by bytes too; anything beyond 512 bytes spills to overflow pages (section 06).

6. Binary search on [7, 15, 23] returns 0 for key 7. What should it return for key 3, and why not "−0"?

Insertion point 0. "Negative means absent" can't express −0, so the common encoding returns −(0) − 1 = −1. Decode with insertionPoint = −r − 1. The book says "negative gives the insertion point" without this detail (section 07).

7. With indirection pointers, how many cell reads does a binary search over 255 cells need at most, and why are they expensive?

⌈log2(256)⌉ = 8 comparisons, each a hop from the offset array to a cell stored in insertion order somewhere else in the page, typically a CPU cache miss (section 07).

8. Breadcrumbs store a child index per level. Why does the book add "assuming the index is still valid"?

Between the descent and the split, another operation may have changed the parent (inserted or moved separators, or split it), so the remembered index or even the remembered parent can be stale. Real engines re-locate the downlink (PostgreSQL matches by block number and moves right) (section 09).

9. Random inserts give about 70% full leaves with plain splits. What does B* change, and what does it cost?

It shares keys with neighbours until both are full, then splits two nodes into three at two-thirds each, so occupancy rises (mid-80s in this page's simulation) and the tree can be shorter. Cost: reading and rewriting siblings and parent separators on many inserts, plus more complex code (section 10).

10. Your table uses an auto-increment id. Why might the index be only half full, and what fixes it?

Middle splits of the rightmost leaf leave a 50% page behind that never receives another key. Quickbalance (start a fresh rightmost page) or a split that leaves the left page ~90% full fixes it (PostgreSQL fillfactor 90 on right-edge splits; InnoDB ends near 15/16). The fastpath additionally skips the root-to-leaf descent (section 11).

11. Why does bulk loading need only "height" pages of memory, however big the input is?

Leaves are written once and never revisited; the only unfinished nodes are the rightmost open node on each level (the parents of the leaf being filled). Everything to their left is complete and already on disk (section 12).

12. A 16 KB page compresses to 5 KB with 4 KB blocks. Padded layout: how many blocks per read and how much padding? Packed layout: what's the catch?

Padded: 2 blocks (8 KB) per read, 3 KB padding per page. Packed: no wasted space, but pages straddle block boundaries, so a read pulls in bytes of neighbouring pages and often an extra block (Fig 4-10, section 13).

13. Vacuum freed 50 pages, then the server crashed before the freelist was written. What happens?

Those pages are no longer reachable from the tree and not on any free list: leaked. The file keeps growing for new allocations even though space exists. That's why the book says the freelist must be persisted (section 16).

14. Updates on a leaf "try to avoid page rewrite". What does that leave behind, and which feature deliberately keeps it?

Multiple versions of the same cell, only one addressable; the rest are garbage until vacuum. MVCC databases keep old versions on purpose while concurrent transactions may still read them (ghost records, collected once no transaction can see them) (section 15).
