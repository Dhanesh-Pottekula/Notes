01 · CHAPTER OPENING

Crashed or slow? The yardsticks of a detector

pdf p314–315

The chapter opens with the old riddle about a tree falling in an empty forest: if nobody is there to observe it, did anything happen? That is the failure-detection problem in one line. A system can only react to a failure it has noticed, and it should notice in time: until it does, clients and peers keep sending work to a process that will never answer, which adds latency and lowers availability.

  • Why it's hard: in an asynchronous system (no assumptions about how long steps or messages take) you can't tell a crashed process from one that is just very slow. Ch.8's FLP impossibility result is the related, formal version of this problem.
  • Words: dead, failed, crashed mean the process has stopped executing steps completely. Unresponsive, faulty, slow describe a suspected process: it might be dead, it might not.
  • Where failures happen: at the link level (messages lost or delivered slowly) or the process level (crash, or running slowly). From outside, slowness may look exactly like failure.
  • The unavoidable trade-off: suspect too early and you declare live processes dead (false positives); wait too long, giving the process the benefit of the doubt, and real failures stay undetected for longer (false negatives).
  • Definition: a failure detector is a local subsystem of each process that identifies failed or unreachable processes so the algorithm can exclude them, which guarantees liveness while preserving safety.
  • Liveness = something intended must eventually happen (if a process fails, the detector must detect it). Safety = nothing unintended happens (if the detector says a process is dead, it really was dead) [LAMPORT77] [RAYNAL99] [FREILING11].
  • Practical payoff and cost: excluding failed processes avoids wasted work and stops errors propagating into cascading failures; but excluding a process that is only suspected (and maybe alive) reduces availability.
  • Completeness: every non-faulty member eventually notices the failure, and the algorithm can make progress and reach its final result.
  • Efficiency: how fast the failure is identified. Accuracy: whether it was identified precisely; a detector is inaccurate if it accuses a live process or misses an existing failure.
  • Efficiency and accuracy behave like a tunable knob: faster usually means less precise, more precise usually means slower. It is provably impossible to have a detector that is both accurate and efficient, and detectors are allowed to make mistakes (false positives) [CHANDRA96].
  • Failure detectors are a prerequisite and integral part of many consensus and atomic broadcast algorithms (later chapters).
  • Most systems build detectors on heartbeats: simple, and with strong completeness. All algorithms in the chapter assume no Byzantine failures: nobody lies about its own state or its neighbours'.
Picture it

You phone a friend who always picks up. After 10 rings you start to worry; after 30 you call their family. Hang up after 3 rings and you'll "lose" friends who were in the shower (false positive). Wait an hour and you're useless if something really happened (false negative). Every detector in this chapter is a smarter way of choosing when to stop ringing, or a way to ask other people to ring too.

The timeout knob: wrong suspicions vs time to detect a real crash (modelled)

What's happening behind it

The model (mine, not the book's): a live process sends a heartbeat every I ms; each one is delayed by normal jitter σ, so the gap between two arrivals is about Normal(I, √2·σ). With a small probability a heartbeat is also held up by a long pause (garbage collection, a full queue), drawn from an exponential distribution. The top panel shows log10 of the chance that one gap exceeds the timeout, which is a wrong suspicion. The bottom panel shows how long a real crash goes unnoticed: the crash lands somewhere in a heartbeat cycle, so on average the detector fires T − I/2 after it, and at worst T. Pure jitter makes false positives vanish fast as you raise T; the rare long pauses create a long tail that only a much bigger timeout covers. That tail is why real deployments use the adaptive detectors later in the chapter.

Beyond the book: the classic classification
  • Chandra and Toueg [CHANDRA96] split each property in two. Strong completeness: every crashed process is eventually suspected by every correct process; weak: by some correct process. Strong accuracy: no correct process is ever suspected; weak: some correct process is never suspected. "Eventual" versions only require accuracy after some unknown time.
  • Combinations give the named classes: P (perfect: strong completeness + strong accuracy), ◇P (eventually perfect), S, ◇S, W, ◇W. In a truly asynchronous system you can't implement P; a timeout detector whose timeout keeps growing after each mistake is the usual way to approximate ◇P in a partially synchronous one.
  • The book's "efficiency" is what the research literature calls detection time; its "accuracy" maps to how often and how long a correct process is wrongly suspected. The summary (plate 8) calls the same trade-off "accuracy vs completeness": completeness in finite time is exactly what a short timeout buys.
// The decision every heartbeat-based detector makes, in one function
function suspect(now: number, lastHeard: number, timeoutMs: number): boolean {
  return now - lastHeard > timeoutMs;   // short timeout → fast but wrong more often
}

02 · HEARTBEATS AND PINGS

Ask "are you alive?" and start a clock

pdf p316–317 · Fig 9-1, 9-2

There are two periodic ways to learn about a remote process:

  • Ping: you send it a message and expect a response within a set time.
  • Heartbeat: the process itself keeps telling its peers "I'm still running".

The book uses pings for its examples and notes heartbeats give similar results. Each process keeps a list of the other processes (alive, dead and suspected) with the last response time of each. A process that doesn't answer a ping for too long is marked suspected. Figure 9-1 is the healthy case: P1 asks P2 "alive?", P2 acknowledges, and each ack arrives before the next question. Figure 9-2 is the troubling case: the acks are delayed and arrive after the next ping has already gone out, so P1 may mark a perfectly active P2 as down.

Many detectors are just heartbeats plus timeouts. Example: Akka has a deadline failure detector, which reports a failure when a process hasn't registered a heartbeat within a fixed interval. Two downsides: its precision depends on choosing the ping frequency and timeout carefully, and it only sees the process from one place, not how other processes see it (that's what plate 4 fixes).

Picture it

A teacher calling the register. Silence after a name doesn't tell you whether the pupil is absent or just didn't hear; if the teacher moves on to the next name while the first pupil's late "here!" is still on its way, the late answer gets credited to nothing and the pupil is marked absent.

event 0
What's happening behind it

The detector only stores "when did I last hear from P2?". Any ack, even one answering an older ping, resets that time. Suspicion fires the moment now − lastHeard passes the deadline. So in the slow-ack scenario (which pins the round trip to at least 1.4× the interval) nothing is wrong as long as acks keep arriving at the ping rate, except at startup if the deadline is shorter than the first round trip; the deadline only bites when a gap between two acks is longer than it. The "one ack delayed 4×" scenario shows a live process wrongly suspected and then cleared when its late ack lands; the crash scenario shows the detection delay: time of last ack + deadline. Precision depends entirely on picking interval and deadline well, which is the book's first downside.

class DeadlineDetector {
  private last = new Map<string, number>();        // process → last response time
  constructor(private deadlineMs: number) {}
  heard(p: string, now: number) { this.last.set(p, now); }       // ack or heartbeat
  state(p: string, now: number): 'alive' | 'suspected' {
    const t = this.last.get(p) ?? 0;
    return now - t > this.deadlineMs ? 'suspected' : 'alive';
  }
}
Beyond the book: documented defaults
  • Docker HEALTHCHECK: --interval=30s, --timeout=30s, --retries=3, --start-period=0s. A container becomes unhealthy after 3 consecutive failed checks: a deadline detector with "3 strikes" built in.
  • etcd (Raft): followers expect a leader heartbeat every 100 ms and start an election after 1000 ms of silence; the docs say the election timeout should be at least 10× the round-trip time. Raft's election timeout is a deadline failure detector for the leader.
Connects to
  • Plate 1's chart: the deadline here is the "timeout" knob there.
  • Plate 5: φ-accrual keeps the same "last heard" input but replaces the fixed deadline with a threshold that adapts to observed arrival times. Akka ships both.
03 · TIMEOUT-FREE FAILURE DETECTOR

Count heartbeats along paths, never start a clock

pdf p318

Some algorithms don't use timeouts at all. Heartbeat, a timeout-free failure detector [AGUILERA97], only counts heartbeats; the application decides who has failed by looking at its vector of heartbeat counters. Because there are no timeouts, it works under asynchronous-system assumptions.

  • Assumptions: any two correct processes are connected by a fair path, made only of fair links (a message sent infinitely often over the link is received infinitely often); and every process knows all the other processes.
  • State: each process has a list of neighbours and a counter for each process.
  • Sending: processes send heartbeat messages to their neighbours. Each message carries the path it has travelled. The first message holds the original sender plus a unique identifier so the same message isn't broadcast twice.
  • Receiving: increment the counter for every process in the path, then forward the heartbeat to every neighbour not in the path, appending yourself. Propagation stops once every known process is already in the path.
  • Benefit: heartbeats travel through different processes and the paths aggregate neighbours' information, so a process can (correctly) be seen as alive even when the direct link to it is broken.
  • The counters form a global, normalised view: they show how heartbeats propagate relative to each other, so processes can be compared.
  • Shortcoming: interpreting the counters is tricky. You need a threshold that gives reliable results; pick it badly and live processes get falsely suspected.
Picture it

A chain letter that everyone signs before passing it on. You never wait for anyone; you just tally how many letters you've seen with each person's signature on them. Someone whose tally keeps rising is alive, even if they never write to you directly. Someone whose tally froze has stopped signing. The hard part is saying how far behind a tally has to fall before you give up on that person.

Step through rounds of path-carrying heartbeats

round 0
What's happening behind it

Each round every live process starts a heartbeat with path [itself] to each neighbour, and every message received last round is counted and forwarded. Table cell (row P, column Q) is P's counter for Q. With the P1–P3 link cut, P1's counter for P3 still climbs because P3's heartbeats reach P1 via P2, P4 and P5. Crash P4 (tick the box mid-run) and every row's P4 column freezes while the others keep growing. Notice the counters for different processes grow at different speeds (more paths = more increments), which is why a raw "counter difference" threshold is hard to choose. Here the interpretation is "no increase for N rounds", and that quietly reintroduces a timeout: the book's warning made concrete. Note the message count: every heartbeat floods along every simple path, which is expensive on large graphs.

type Msg = { id: string; path: number[]; to: number };
function onHeartbeat(p: number, m: Msg, cnt: number[][], send: (m: Msg) => void) {
  for (const q of m.path) cnt[p][q]++;                 // everyone on the path is alive
  for (const n of neighbours(p))
    if (linkUp(p, n) && !m.path.includes(n))           // stop when all are on the path
      send({ id: m.id, path: [...m.path, p], to: n });
}
function originate(p: number, send: (m: Msg) => void) {
  for (const n of neighbours(p)) if (linkUp(p, n)) send({ id: uid(), path: [p], to: n });
}

  • Plate 6: gossip heartbeat tables keep a counter per process too, but spread whole tables to one random peer instead of flooding paths, and add a local timestamp so a timeout can be applied.
Papers behind this plate

04 · OUTSOURCED HEARTBEATS

Ask your neighbours to ping for you (SWIM)

pdf p319 · Fig 9-3

SWIM, the Scalable Weakly Consistent Infection-style Process Group Membership Protocol [GUPTA01], uses outsourced heartbeats: it improves reliability by also using what the process's neighbours can see. A process doesn't need to know every other process, only a subset of connected peers.

Figure 9-3: P1 pings P2. P2 doesn't answer, so P1 picks several random members (P3 and P4). They each send a heartbeat to P2 and, if P2 answers, forward the acknowledgement back to P1. This covers both direct and indirect reachability: with P1, P2 and P3 you can check P3 from the point of view of both P1 and P2.

  • Responsibility for the verdict is spread across the group, which makes detection more reliable.
  • No broadcast to a wide group of peers is needed.
  • The outsourced requests can be sent in parallel, so more evidence about a suspect is gathered quickly and the decision is more accurate.
Picture it

Your call to a colleague doesn't connect. Before reporting them missing you ask two other people in different buildings to try. If either gets through, the problem was your phone line, not your colleague.

How much do helpers cut wrong suspicions? (modelled)

What's happening behind it

The model (mine): every message is lost independently with probability p; the target is alive. The direct check fails if the ping or the ack is lost: 1 − (1−p)². Each helper path needs four messages (ping-req, ping, ack, forwarded ack), so it fails with 1 − (1−p)⁴, and the process is wrongly suspected only if the direct check and all k helper paths fail: [1 − (1−p)²]·[1 − (1−p)⁴]k. At 1% loss that is about 2·10⁻² with no helpers, 7.8·10⁻⁴ with one, and 1.2·10⁻⁶ with three. Cost per probe: 2 messages when the target answers, at most 2 + 4k when it doesn't, no matter how big the group is. The model ignores correlated loss (a congested rack drops many messages at once), which is the main reason real systems add a suspicion phase before declaring death.

async function probe(target: Node, members: Node[], k: number): Promise<'alive' | 'suspect'> {
  if (await ping(target, PROTOCOL_TIMEOUT)) return 'alive';            // direct
  const helpers = randomSample(members.filter(m => m !== target), k);
  const acks = helpers.map(h => pingReq(h, target, PROTOCOL_TIMEOUT)); // in parallel
  return (await anyTrue(acks)) ? 'alive' : 'suspect';                  // indirect
}
Beyond the book
  • The bibliography key [GUPTA01] points to Gupta, Chandra & Goldszmidt, "On scalable and efficient distributed failure detectors" (PODC 2001), which analyses randomised pinging. The protocol named SWIM is in a separate paper: Das, Gupta & Motivala, "SWIM: Scalable Weakly-consistent Infection-style Process Group Membership Protocol", DSN 2002 (not in the book's bibliography). That paper adds a suspect state (a suspected member can refute it before being declared dead) and spreads membership changes by piggybacking them on ping traffic.
  • In SWIM each member pings one random member per period, so a crashed member is first pinged by somebody within a period with probability 1 − (1 − 1/(N−1))N−1, which tends to 1 − 1/e ≈ 63%; expected time to first detection is about e/(e−1) ≈ 1.58 periods, independent of N. The readout computes it for your N.
  • HashiCorp memberlist (used by Consul and Serf) is documented as based on SWIM, with extensions called Lifeguard to make it more robust when the local node itself is slow.

05 · PHI-ACCRUAL FAILURE DETECTOR

Not "up or down" but "how sure am I?"

pdf p320–321

Instead of a binary up/down verdict, the φ-accrual detector [HAYASHIBARA04] outputs a value on a continuous scale that captures how likely it is that the monitored process has crashed. It keeps a sliding window of the arrival times of the most recent heartbeats from each peer, uses them to estimate when the next heartbeat should arrive, compares that estimate with what actually happens, and computes the suspicion level φ: how certain it is about the failure, given current network conditions. When φ reaches a threshold, the node is marked down. Because the window tracks recent behaviour, the scale adapts to changing network conditions.

The book splits the detector into three subsystems:

Monitoring→Interpretation→Action
collect liveness data: pings, heartbeats or sampled request/responsedecide whether to mark the process suspecteda callback run when the process is marked suspected
  • The samples are assumed to follow a normal distribution and kept in a fixed-size window: new arrivals go in, the oldest fall out.
  • The mean and variance of the window give the distribution; from it you get the probability that the next message arrives within t time units of the previous one.
  • From that, φ expresses how likely a correct decision is; put the other way, how likely it is that a heartbeat will still arrive and contradict the verdict.
  • Developed by researchers at the Japan Advanced Institute of Science and Technology; used in many systems, for example Cassandra and Akka (which also has the deadline detector of plate 2).
Picture it

A friend who texts "home safe" about 20 minutes after leaving, give or take 2. At minute 22 you're not worried; at 26 you're uneasy; at 35 you're nearly certain something's wrong. Your unease is φ, and it rises much faster for a punctual friend than for one who arrives anywhere between 10 and 60 minutes. The threshold is when you pick up the phone.

φ over one minute of simulated heartbeats (1 per second)

What's happening behind it

For the time Δ since the last heartbeat, the normal model computes Plater(Δ) = 1 − F(Δ), the chance a live process's next heartbeat would arrive even later than this, using the window's mean μ and standard deviation σ. Then φ = −log10 Plater (formula from the paper; the book gives no formula). φ = 1 means a 10% chance the verdict "dead" is a mistake, φ = 2 means 1%, φ = 8 means one in 10⁸. Because σ comes from the window, a calm network (small σ) makes φ shoot up within a few hundred ms of a missed beat, while a jittery one stretches the scale: that's the adaptivity. The hiccup shows the price: one long gap spikes φ (maybe above threshold, a false positive) and also widens σ for the next window samples. The exponential model only uses the mean, φ = Δ / (μ · ln 10), so it rises slowly and linearly: much more tolerant, much slower to convict.

Worked example: compute φ yourself

By hand, with μ = 1000 ms and σ = 100 ms: after 1300 ms of silence, z = (1300 − 1000)/100 = 3, Plater ≈ 0.00135, φ ≈ 2.87. After 1500 ms, z = 5, Plater ≈ 2.9·10⁻⁷, φ ≈ 6.54. φ crosses 8 at about 1562 ms. With the exponential model and μ = 1000 ms, φ = 8 needs about 18.4 s of silence.

function phi(deltaMs: number, window: number[], minStd = 100, model: 'normal' | 'exp' = 'normal') {
  const mean = avg(window);
  if (model === 'exp') return deltaMs / (mean * Math.LN10);           // = −log10(e^(−Δ/μ))
  const std = Math.max(stdDev(window), minStd);
  const pLater = 1 - normalCdf((deltaMs - mean) / std);              // chance a live node is still this late
  return -Math.log10(pLater);
}
// interpretation + action
if (phi(now - lastArrival, window) >= threshold) onSuspect(peer);

06 · GOSSIP AND FAILURE DETECTION

Everyone keeps a heartbeat table and passes it on

pdf p322–323 · Fig 9-4

Another way to avoid trusting a single node's view is a gossip-style failure detection service [VANRENESSE98], which uses gossip (Ch.12) to collect and spread the state of neighbouring processes.

  • Each member keeps a list of other members with their heartbeat counters and a timestamp of when each counter last went up.
  • Periodically each member increments its own counter and sends its list to a random neighbour. The receiver merges it with its own list, updating other members' counters.
  • Members also periodically scan the list; if a counter hasn't been updated for long enough, that member is considered failed. Choose this timeout carefully to keep false positives unlikely.
  • How often members must talk to each other (the worst-case bandwidth) is capped and grows at most linearly with the number of processes.

Figure 9-4 has three processes: (a) all three talk and update timestamps; (b) P3 can't reach P1, but its timestamp t6 still reaches P1 through P2; (c) P3 crashes, stops sending updates, and the others detect it as failed. So the scheme catches both crashed nodes and nodes that no member can reach. The verdict is reliable because it aggregates many nodes' views; a broken link between two hosts doesn't matter because heartbeats flow around it. The cost is more messages; the benefit is more reliable spreading of information.

Picture it

An office noticeboard copied by hand: every few minutes you tick your own name and swap boards with a random colleague, keeping the higher tick count for each name. Anyone whose tick count hasn't moved on your board for a long while is presumably gone, even if you never spoke to them.

Step through Fig 9-4 (3 processes, one gossip per tick)

tick 0
What's happening behind it

Each row holds (counter, local time it last increased). Merge rule: for each member keep the larger counter; if yours went up, stamp it with your current time. Clocks are never compared across machines, only local "how long since this number moved", which is why no clock sync is needed. In (b) the P3 row on P1's table keeps advancing via P2. In (c) P3's counter freezes everywhere and, T_fail ticks later, each survivor greys it out on its own. Van Renesse et al. also keep a failed member in the list for a further cleanup period, so a stale copy arriving via gossip doesn't bring it back to life (not in the book).

type Row = { hb: number; ts: number };               // counter + local time it last grew
function tick(self: string, table: Map<string, Row>, now: number) {
  const me = table.get(self)!; me.hb++; me.ts = now;
  sendTo(randomNeighbour(), snapshot(table));         // whole table, one peer
}
function merge(table: Map<string, Row>, incoming: Map<string, number>, now: number) {
  for (const [p, hb] of incoming) {
    const r = table.get(p);
    if (!r || hb > r.hb) table.set(p, { hb, ts: now });   // newer evidence of life
  }
}
const failed = (r: Row, now: number) => now - r.ts > T_FAIL;

How many gossip rounds until everyone hears a new heartbeat? (simulated, pooled)

What's happening behind it

Push gossip: every node that already has the new counter sends its table to one random other node per round. The simulation averages 60 runs per group size, for N = 2 to 1024 (x-axis: log2 N). The rounds grow like log2 N + ln N (Pittel's 1987 result for random rumour spreading, not in the book), so doubling the cluster costs about 1.7 extra rounds. That is how T_fail is chosen in practice: a few times the expected spreading time, so a live member's counter has almost surely reached everyone before anyone gives up on it.

07 · REVERSING FAILURE DETECTION PROBLEM STATEMENT

FUSE: one failure becomes everyone's failure

pdf p324–325 · Fig 9-5

Spreading news of a failure isn't always possible, and telling every member can be expensive. FUSE (failure notification service) [DUNAGAN04] focuses on reliable and cheap failure propagation that works even under network partitions.

  • All active processes are arranged in groups. If a group becomes unavailable, all participants detect it: every single-process failure is converted into, and spread as, a group failure. This works under any pattern of disconnects, partitions and node failures.
  • Group members periodically ping each other. If a member can't answer (crash, partition or link failure), the member that sent the ping stops answering pings itself.
  • Figure 9-5, four processes: (a) all alive and talking; (b) P2 crashes and stops answering; (c) P4 detects P2's failure and stops answering too; (d) eventually P1 and P3 notice that their peers don't respond, and the failure has spread to the whole group. (The printed text of step d names "P1 and P2" as the silent ones; the figure shows P2 and P4 crossed out, with P1 and P3 noticing, which is what this page follows.)
  • Failures thus travel from their source to every participant, as members one by one stop responding. The absence of communication is the propagation channel.
  • Advantage: every member is guaranteed to learn of the group failure and can react. Downside: a link failure that cuts off one process also turns into a group failure, though depending on the use case that can be what you want. Applications can define for themselves what counts as a propagated failure.
Picture it

A rope team of climbers. If one falls and the rope goes slack, the person who feels it stops and tugs the rope too, and soon the whole team has stopped. Nobody needs to shout over the wind: going still is the message.

What's happening behind it

Each round, every still-responsive member pings one other member (round-robin through the group). If the ping fails for any reason, the pinger turns silent: it keeps living but stops answering pings, so whoever pings it next turns silent too. Silence spreads along the ping graph until the whole group is down, and every member knows it, because each one either saw a failed ping or was the one that went silent. In the link-only variant no process crashed, yet the whole group still fails: the book's "downside, or advantage". The application then rebuilds a new group from the members that are still alive, which is FUSE's model: a group is a contract that is either intact for everyone or broken for everyone.

class FuseMember {
  responsive = true;
  onPing(): boolean { return this.responsive; }        // silence = "the group has failed"
  async round(peer: FuseMember) {
    if (!this.responsive) return;
    const ok = await pingWithTimeout(peer);
    if (!ok) { this.responsive = false; this.onGroupFailure(); }   // convert, then propagate by silence
  }
  onGroupFailure() { /* app callback: tear down state tied to this group */ }
}

08 · SUMMARY · FURTHER READING

What to remember

pdf p326
  • Failure detectors are an essential part of any distributed system.
  • FLP says no protocol can guarantee consensus in an asynchronous system. Failure detectors augment the model, making consensus solvable by trading accuracy against completeness.
  • [CHANDRA96] showed that consensus is solvable even with a failure detector that makes an infinite number of mistakes: a key result proving their usefulness.
  • The algorithms differ in how information travels: direct communication (pings, SWIM), broadcast or gossip (timeout-free heartbeat, gossip tables), or quiescence, the absence of communication (FUSE).
  • And in how they decide: heartbeats or pings, hard deadlines, or continuous scales (φ). Each has its own upside: simplicity, accuracy, or precision.

Beyond the book: what "infinitely many mistakes" means

[CHANDRA96] solve consensus with a ◇S detector (eventually some correct process is never suspected) when a majority of processes is correct. Such a detector may wrongly suspect processes infinitely often; it only needs one correct process to eventually stop being suspected by everyone. A follow-up paper, Chandra, Hadzilacos & Toueg, "The weakest failure detector for solving consensus" (JACM 43(4), 1996, not in the book), shows ◇W (equivalent to ◇S) is the weakest detector that makes consensus solvable. In Raft and Paxos terms: the leader-election timeout may fire wrongly many times, as long as eventually a leader stays unsuspected long enough to finish.

  • Small cluster, one coordinator (leader-based DB): leader heartbeat + election timeout (Raft). Set the heartbeat near RTT and the timeout ≥ 10× RTT, as etcd advises.
  • Large peer-to-peer membership (hundreds to thousands of nodes): SWIM-style probing with suspicion, or gossip tables. Per-node load stays constant or linear in table size.

Check yourself

answer before you open
1. Why can't an asynchronous system ever be sure a silent process has crashed?

With no bound on message delay or processing speed, any silence could still end with a late reply. Crashed and very slow look identical from outside (plate 1; FLP in Ch.8).

2. State liveness and safety for a failure detector, in one line each.

Liveness: a failed process will eventually be detected. Safety: a process marked dead really was dead. A practical detector gives up strict safety (false positives are allowed) to keep liveness (plate 1).

3. You halve the timeout of a deadline detector. Which property improves and which gets worse?

Efficiency (faster detection) improves; accuracy gets worse (more live processes wrongly suspected). The book says you can't have both at once (plate 1).

4. In Fig 9-2 the acks arrive after the next ping is sent. Does a deadline detector necessarily suspect P2?

No. It only tracks the last time it heard anything; if acks keep arriving at the ping rate, every gap is still under the deadline. It suspects only when one gap between acks exceeds the deadline (plate 2 simulator).

5. The P1–P3 link is down. How can the timeout-free Heartbeat algorithm still show P3 as alive at P1?

P3's heartbeats travel along other paths (P3→P2→P1, etc.); P1 increments the counters of every process named in each path it receives (plate 3).

6. What is the weakness of the timeout-free detector the book points out?

Turning counter vectors into a verdict needs a threshold, and a poor one falsely suspects live processes. In practice "hasn't grown for a while" brings a timeout back (plate 3).

7. In SWIM, P1's ping to P2 fails but P3 gets an ack from P2. What should P1 conclude, and what did it learn?

P2 is alive; the problem is on the P1–P2 path. That's indirect reachability: the verdict uses neighbours' views, not just P1's (plate 4).

8. With 5% independent message loss, roughly how much does going from 0 to 2 helpers cut SWIM's false-suspicion probability (in this page's model)?

From about 9.8·10⁻² to 3.4·10⁻³, roughly 30× fewer wrong suspicions, for at most 8 extra messages per failed probe (plate 4 calculator).

9. What does φ = 3 mean, and why does the same threshold behave differently on a calm and a jittery network?

About a 1-in-1000 chance that a live process's heartbeat would still be this late, so declaring it dead would be wrong once in a thousand times. φ is computed from the window's mean and spread, so on a calm network (small σ) it climbs much faster after a missed beat than on a jittery one (plate 5).

10. Name the three subsystems of a φ-accrual detector.

Monitoring (collect heartbeats, pings or request/response samples), Interpretation (decide whether to suspect), Action (callback when suspected) (plate 5).

11. In gossip failure detection, why is it safe that nodes' clocks are not synchronised?

Each node only stamps rows with its own local time when a counter grows, and compares against its own clock. Counters, not timestamps, are what's exchanged (plate 6).

12. Gossip bandwidth "grows at most linearly". Linearly in what, and why?

In the number of processes: each period a member sends one message to one neighbour, and that message carries one row per member (plate 6).

13. FUSE turns a single broken link into a whole-group failure. When is that a feature?

When the group represents something that must be all-or-nothing, like a session or the participants of one operation: everyone is guaranteed to learn it's gone and can clean up, even across a partition (plate 7).

14. How can consensus be solvable with a detector that makes infinitely many mistakes?

The algorithm stays safe whatever the detector says; it only needs the detector, eventually, to stop suspecting at least one correct process so that process can lead to a decision ([CHANDRA96], plate 8).
