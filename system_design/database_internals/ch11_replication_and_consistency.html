01 · CHAPTER OPENING

Why keep several copies, and what that costs

pdf p340–341

Before consensus and atomic commitment (Chapters 13–14), Petrov adds the last missing piece: consistency models. They explain what a client may see (visibility) and how the system behaves when there are several copies of the same data.

Fault tolerance means a system keeps working correctly even when some of its components fail. It's hard to build, and harder to bolt onto an existing system. The main goal is to remove every single point of failure and make the mission-critical parts redundant. Usually the user never notices the redundancy.

The way to keep working when a machine dies is to keep multiple copies of the data, so another machine can take over (failover). There are two styles:

  • Single source of truth (for example primary/replica databases): failover is explicit. A replica is promoted to become the new master.
  • No explicit reconfiguration: the system stays consistent by collecting responses from several participants on every read and write (the quorum idea of section 18).

Data replication is how we add that redundancy: keep several copies in the system. But updating many copies atomically is a problem equivalent to consensus [MILOSEVIC11], so doing it for every single operation can be very expensive. The chapter therefore looks for cheaper, more flexible ways to make the data look consistent to users while letting the copies drift apart a little.

Replication matters most in multi-datacenter deployments. Geo-replication does two jobs: it raises availability (the system survives losing one or more whole datacenters), and it lowers latency by putting a copy physically close to the client.

When a record changes, its copies must change too. For replication we care about three events, all started by the client: the write, the replica update and the read. Sometimes replicas are updated after the client already got its "write done" answer. Even then, the client must be able to observe operations in a well-defined order. That order is exactly what the rest of the chapter defines.

Picture it

A shop keeps its price list in three branches. Head office phones every branch when a price changes. If the shopper is told "price updated" the moment head office writes it down, but branch C hasn't picked up the phone yet, a shopper at branch C still sees the old price. Nothing is "broken"; the question is only which answers we promise are allowed. That promise is the consistency model.

Step through: write, replica update, read

What's happening behind it

Two numbers decide what a reader may see: when the client gets its acknowledgement, and when each replica applies the change. If the ack comes after every replica applied it (sync), any replica gives the new value, but the write waited for the slowest copy and fails if any copy is down. If the ack comes first (async), the write is fast and survives a dead replica, but there's a window in which a read from a lagging copy returns the old value. Consistency models are the vocabulary for which of those windows are acceptable.

Beyond the book: the same choice in real systems

PostgreSQL streaming replication is asynchronous by default; with synchronous_standby_names set and synchronous_commit on, a commit waits for the named standbys. MySQL has the same split between asynchronous and semi-synchronous replication. That is the "sync / async" switch in the stepper above.

02 · ACHIEVING AVAILABILITY

Failures happen; the system must look as if they didn't

pdf p342

Chapter 8 listed the fallacies of distributed computing: in the real world nodes aren't always alive and can't always talk to each other. Still, intermittent failures shouldn't hurt availability: from the user's point of view, the system as a whole must keep working as if nothing happened.

Availability matters enormously. Teams aim for high availability, try to minimise downtime and brag about uptime. Software now carries bank transfers, communication and travel. For a company, downtime means lost customers or money: nobody can shop in an online store that's down, or move money when the bank's site doesn't answer.

To be highly available, the system must handle the failure or unavailability of one or more participants gracefully. That needs redundancy and replication. And the moment we add redundancy we inherit two new problems: keeping several copies in sync, and building recovery mechanisms.

Picture it

A spare tyre makes the car "available" after a puncture, but only if the spare is inflated. Replicas are spare tyres for data: each one helps only if it's kept up to date, and keeping it up to date is the work this chapter is about.

How much do replicas buy? (modelled, not in the book)

What's happening behind it

If each node is independently up with probability p, the chance that at least K of N are up is Σ C(N,i)·pⁱ·(1−p)^(N−i) for i from K to N. With p = 99%: one node gives 99% (about 3.65 days down a year); "any 1 of 3" gives 99.9999%; "2 of 3" (a majority) gives about 99.97%; "all 3" drops to about 97%. That last line is the hidden cost of synchronous "update every copy": each extra copy you must wait for lowers availability. Real failures are not independent (shared racks, power, deploys, bugs), so treat these as upper bounds.

03 · INFAMOUS CAP

CAP: during a partition, pick consistency or availability

pdf p343–344

Availability is the ability to answer every request successfully. The theoretical definition only asks for an eventual response; real systems obviously shouldn't take forever.

Ideally every operation would be consistent, and "consistent" here means atomic or linearizable (section 10): the history can be written as a sequence of instantaneous operations that keeps the original order. Linearizability makes a distributed system behave as if it ran on one machine.

We'd like both, while tolerating network partitions: the network splits into parts whose processes can't talk to each other, so some messages between them never arrive. Availability demands that every non-failing node returns a result; consistency demands linearizable results. Eric Brewer's CAP conjecture [BREWER00] is about the trade-off between Consistency, Availability and Partition tolerance.

The availability requirement is impossible to meet in an asynchronous system, and no system can guarantee both availability and consistency when the network is partitioned [GILBERT02]. What we can build is strong consistency with best-effort availability, or availability with best-effort consistency [GILBERT12]. "Best effort" means: when everything works, the system won't break its guarantees on purpose, but it may weaken or violate them during a partition.

So CAP is a continuum, with two ends:

  • CP (consistent and partition tolerant): prefers to fail requests rather than serve possibly inconsistent data. Example: a consensus algorithm that needs a majority to make progress. Always consistent, possibly unavailable during a partition.
  • AP (available and partition tolerant): loosens consistency and may serve inconsistent values. Example: a database that accepts writes and serves reads as long as even one replica is up. It may lose data or return inconsistent results.

PACELC [ABADI12] extends CAP: if there is a Partition, choose between Availability and Consistency; Else, even when everything runs normally, choose between Latency and Consistency. (The PDF spells it "PACELEC"; the standard name is PACELC.)

Picture it

Two branch offices lose the phone line between them. A customer at branch B asks for their balance. Branch B can say "sorry, can't confirm right now" (CP), or read out the balance it last heard of, which may be out of date (AP). There is no third option that is both always-answering and always-right while the line is down.

What's happening behind it

In CP mode a write needs 3 of 5 acknowledgements. The side holding 3 or more nodes keeps working; the minority side refuses. Two majorities can't exist at once, so the two sides can never accept conflicting writes. In AP mode both sides accept writes; after healing, the replicas hold two different "latest" values and something (last-write-wins, vector clocks, CRDTs: sections 15 and 20) has to reconcile them, possibly dropping one write. PACELC's point shows in the second calculator: even with no partition, waiting for a copy in another datacenter costs a full round trip on every consistent write, while an "ack locally, replicate later" write costs only the local time.

Beyond the book: where real systems sit

etcd (Raft) is a classic CP store: its docs say key-value operations are linearizable by default, which means each such request goes through Raft consensus; it also offers serializable reads that skip consensus and may return stale data. DynamoDB reads are eventually consistent by default; a ConsistentRead=true read returns the latest data and costs twice as much (the docs price eventually consistent reads at half). Both are the PACELC "else" choice turned into an API flag. Sources: etcd.io API guarantees; AWS DynamoDB "Read consistency" docs.

04 · USE CAP CAREFULLY

What CAP does and doesn't say

pdf p345–346

CAP talks about network partitions, not node crashes or other failures such as crash-recovery. A node cut off from the cluster can still answer, and may answer with inconsistent data. A crashed node doesn't answer at all. Two consequences:

  • You don't need any node to be down to have consistency problems. All nodes can be up, with only the links between them broken, because CAP expects every non-failed node to answer correctly no matter how many others are down.
  • Real life is messier: there are many failure scenarios, some of which can be simulated as network partitions.

CAP is often drawn as a triangle, as if a knob gave you a little more of each of the three. In fact you can trade consistency for availability, but partition tolerance is not something you can realistically tune or give up [HALE10]: partitions happen whether you like it or not.

CAP is useful for explaining distributed systems and reasoning about failures, but there's a fine line between "giving up consistency" and "serving unpredictable results". Databases that claim to be on the availability side can still serve consistent results from replicas when used correctly, as long as enough replicas are alive. (The book's footnote: this refers to quorum reads and writes in eventually consistent stores, section 18.) CAP is a rule of thumb, not the whole truth.

Picture it

A crashed node is a shop with its shutters down: you can't buy anything, but you also can't buy the wrong thing. A partitioned node is a shop whose phone line to the warehouse is cut: the doors are open and the shopkeeper will happily sell you an item that may already be gone. CAP is about the second shop.

What's happening behind it

The impossibility proof needs a node that is up and must answer, yet can't learn about a write made on the other side. A crash removes the "must answer" obligation, so it never forces the dilemma. That's also why "we're CA" makes no sense for a distributed system: you can't promise that partitions won't happen, only decide how to behave when they do.

05 · HARVEST AND YIELD

Softer dials than CAP: harvest and yield

pdf p347

CAP treats both properties only in their strongest forms: linearizability, and eventually answering every request. That forces a hard either/or. Many applications can live with weaker forms. Fox and Brewer [FOX99] proposed two tunable metrics:

  • Harvest: how complete a query's answer is. If a query should return 100 rows but can only fetch 99 because some nodes are unavailable, that can still beat failing and returning nothing.
  • Yield: the number of requests completed successfully compared with the number attempted. It's not the same as uptime: a busy node isn't down, but it can still fail to answer some requests.

This turns an absolute trade-off into a relative one. We can trade harvest for yield and let some requests return incomplete data. One way to raise yield is to answer only from the partitions that are available: if the nodes holding some users' records are down, keep serving the other users. Or require critical data to be returned whole while allowing gaps elsewhere. Defining, measuring and consciously choosing between harvest and yield makes systems more resilient.

Picture it

A search engine with 10 index shards loses one. It can return "error" for every search (yield drops, harvest stays perfect) or return results from the 9 live shards (yield stays perfect, each answer is about 90% complete). For a web search the second is clearly better; for a bank statement the first is.

Harvest vs yield calculator (modelled)

What's happening behind it

If a query fans out to k of S shards (picked at random) and d shards are down, the chance that it touches no dead shard is C(S−d, k) / C(S, k). "All or nothing" turns that into yield; "partial answers" keeps yield at 100% and pays in harvest, on average (S−d)/S of the rows. Set k = 1 (one user's data lives on one shard) and both policies look alike: only the users on dead shards are hurt, which is the book's "keep serving other users" example. Fan-out queries are where the choice really matters.

06 · SHARED MEMORY

Registers, overlapping operations, and three kinds of register

pdf p348–349 · Fig 11-1

To a client, a distributed store behaves as if it were shared storage on one machine: all the message passing between nodes is hidden. That creates the illusion of shared memory.

A single unit of storage you can read or write is a register. Shared memory in a distributed database can be seen as an array of registers.

Every operation is identified by two events: its invocation (start) and its completion (end). An operation has failed if the process that invoked it crashes before it completes. If both events of one operation happen before the other operation is invoked, the first precedes the second and the two are sequential. Otherwise they are concurrent. Figure 11-1 shows three cases for processes P1 and P2:

  • a) P2's operation starts after P1's has finished: sequential.
  • b) The two overlap: concurrent.
  • c) P2's operation starts after P1's starts and finishes before P1's finishes: concurrent too.

Try it: drag the two operations

Many readers and writers can use a register at once, and reads and writes are not instantaneous: they take time. When operations by different processes overlap they aren't serial, and depending on how the register behaves they can be ordered differently and give different results. So we distinguish three register types:

  • Safe: a read that overlaps a write may return any value in the register's range. Not very practical, but it can describe an asynchronous system that imposes no order. A binary safe register can seem to flicker between its two values during a concurrent write.
  • Regular: a read may return only the value of the most recent completed write, or the value of a write that overlaps the read. There's some notion of order, but a new value isn't visible to all readers at the same moment (for example a master that accepts writes and replicates them to workers that serve reads).
  • Atomic: guarantees linearizability. Every write has a single moment before which all reads return the old value and after which all reads return the new one. Atomicity is a fundamental property that makes the system's state easy to reason about.
Picture it

A scoreboard being repainted from 0 to 1. Safe: while the painter works, a passer-by may read any digit at all, half-painted strokes and all. Regular: the passer-by reads 0 or 1, but two passers-by (or one passer-by twice) may see 1 and then 0 while the paint is still wet. Atomic: there is one instant when the board flips; after anyone has seen 1, nobody sees 0 again.

Same history, three registers (a write 0 → 1 overlapped by five reads)

What's happening behind it

The three types differ only in what a read may return while a write is in flight. Reads that don't overlap any write return the last completed value in all three. Safe gives no promise at all during overlap. Regular narrows it to "old or new" but each read decides on its own, which is why a sequence of overlapping reads can go new, old, new. Atomic adds one rule: the switch from old to new happens once, for everybody. Roll the regular register a few times and look for a 1 followed by a 0: that "new-then-old" inversion is exactly what atomic forbids.

// how to build it: the sequential / concurrent test from Fig 11-1
type Op = { start: number; end: number };            // invocation, completion
const precedes   = (a: Op, b: Op) => a.end < b.start;  // a completes before b is invoked
const sequential = (a: Op, b: Op) => precedes(a, b) || precedes(b, a);
const concurrent = (a: Op, b: Op) => !sequential(a, b);

07 · ORDERING

Without one clock, "what happened first" is ambiguous

pdf p350–351

Looking at a sequence of events we have an intuition about their order. In a distributed system it's not that easy: it's hard to know exactly when something happened and to make that known instantly across the cluster. Every participant has its own view of the state. So every operation is described by its invocation and completion events, which bound it.

The model: processes run read(register) and write(register, value). Each process runs its own operations sequentially (one must complete before the next starts). Combining all processes' sequences gives a global history, in which operations from different processes can be concurrent.

Reads have no side effects; writes change the register. Thinking in reads and writes tells us when data becomes readable after a write. Take the book's example: Process 1 runs write(x, 1), while Process 2 runs read(x) twice. What do the reads return? Several histories are possible:

  • the write completes before both reads;
  • the write is interleaved between the two reads;
  • both reads complete before the write.

Even with one copy of the data there's no simple answer; with replicas, and with more readers and writers, there are many more combinations. With a single process we could force a strict order; with many it's harder. The difficulties fall into two groups: operations may overlap, and the effects of non-overlapping calls may not be visible immediately. To describe outcomes without ambiguity we need consistency models. The chapter discusses distributed consistency in the language of shared memory and concurrent systems because most definitions carry over, but most algorithms from concurrent programming can't be reused directly: communication patterns, performance and reliability are too different.

The three histories of the book's example

Picture it

You and a friend text the same group. Your phone shows your message first, theirs shows theirs first. Both phones are "right" about when they received each message; there's simply no shared clock that settles which was sent first. Consistency models are the rules about which of these different pictures a system is allowed to show.

What's happening behind it

With one writer and one reader doing two reads, the possible read results are (∅, ∅), (∅, 1) and (1, 1), but never (1, ∅) for a single register that honours its own order. Already that last restriction is a consistency rule (monotonic reads). With replicas, (1, ∅) can happen: the first read hits an updated copy and the second a lagging one. Every model in the rest of the chapter is a list of which of these combinations it forbids.

08 · CONSISTENCY MODELS

A consistency model is a contract that prunes histories

pdf p352–353

Because register operations may overlap, we need clear rules for what happens when several clients read or modify different copies at once or within a short time. There's no single right answer: it depends on the application. These rules are studied as consistency models.

Think of a consistency model as a contract between participants: what each replica must do to deliver the promised semantics, and what users may expect from reads and writes. It describes which returned values clients may see despite multiple copies and concurrent access. This section covers single-operation models (not multi-operation transactions).

Each model says how far the system's behaviour is from what we'd find natural. It separates all possible histories of interleaved operations from the histories a given model permits, which makes reasoning about visibility much simpler.

Two ways to look at it: from the state side (which state invariants are acceptable, which relationships between copies on different replicas are allowed), or from the operation side (an outside view of the store: which orders of operations are allowed) [TANENBAUM06] [AGUILERA16].

Without a global clock it's hard to give distributed operations a precise, deterministic order. Petrov compares it to special relativity for data: every participant has its own view of state and time. In theory we could take a system-wide lock for every change; in practice that's far too slow. So we use rules, definitions and restrictions that limit the possible histories.

Consistency models add a dimension to CAP: besides consistency and availability we now weigh synchronization costs [ATTIYA94]: latency, extra CPU cycles, disk I/O to persist recovery information, waiting time, network I/O, and anything else avoidable by not synchronizing. The plan: first look at visibility and propagation. Back in the concurrent read/write example, we can cut down the possible histories either by placing dependent writes after one another, or by defining a point at which the new value propagates. The models are described as processes (clients) issuing reads and writes against a database that may have many replicas.

How many histories are there to prune? (not in the book)

Picture it

A sports league rulebook. "All possible games" includes players picking up the ball and running off the pitch. The rulebook (the model) doesn't make any single game predictable, but it narrows what can happen enough that referees (your code) can judge it. Stronger models are stricter rulebooks: easier to referee, slower to play.

What's happening behind it

If each of P processes runs m operations in order, the number of ways to merge them into one sequence is (P·m)! / (m!)^P, before we even consider overlaps or replicas. That number explodes (3 processes × 4 operations already gives 34,650), which is why we reason about rules rather than listing outcomes. Every rule you add (real-time order, same-origin order, causal order) removes whole families of these merges, and every rule costs synchronization to enforce.

09 · STRICT CONSISTENCY

Strict consistency: perfect, and physically impossible

pdf p354

Strict consistency is complete replication transparency: any write by any process is instantly visible to every later read by any process. It assumes a global clock: if write(x, 1) happened at instant t1, then every read(x) at any instant t2 > t1 returns 1.

It's only a theoretical model. It can't be implemented, because physics and the way distributed systems work limit how fast things can happen [SINHA97].

Picture it

A light switch in Mumbai and a bulb in New York that must glow the very instant the switch is flicked. Any wire, however good, needs time for the signal to travel. Strict consistency asks for the bulb to glow before the signal can arrive.

The speed-of-light floor (modelled, not in the book)

What's happening behind it

Light in optical fibre travels at roughly 200,000 km/s, about 5 µs per km. Distances above are approximate great-circle figures and real cables are longer. For any gap smaller than the one-way delay, a read on the far replica cannot know about the write, yet strict consistency requires it to return the new value. Even if the network were infinitely fast, there's no perfectly shared clock to say which instant is "after t1" on both machines. Every practical model in the chapter replaces "instantly" with something achievable: "somewhere between the start and the end of the operation" (linearizability), "in an order everyone agrees on" (sequential), and so on.

10 · LINEARIZABILITY

Linearizability: one copy, one timeline, real time respected

pdf p355–356 · Fig 11-2

Linearizability is the strongest single-object, single-operation consistency model. A write's effect becomes visible to all readers exactly once, at some moment between the write's start and end, and no client can see the state changes or side effects of partial (still in flight) or incomplete (interrupted) writes [LEE15].

Concurrent operations are represented as one of the possible sequential histories for which the visibility rules hold. There's some indeterminism: more than one ordering may be valid [HERLIHY90]. If two operations overlap, they may take effect in either order. Every read that happens after a write completes sees that write's effect. And once one read returns a value, all later reads return a value at least as recent [BAILIS14a].

Concurrent events have some freedom in the global order, but they can't be reordered arbitrarily. An operation's result can't take effect before the operation starts (that would need an oracle that predicts the future), and it must take effect before it completes (otherwise there'd be no linearization point).

Linearizability respects both each process's local order and the real-time order of operations across processes, and defines a total order of events. That order must be consistent: every read returns the latest value written before it, or the value of a write that overlaps it. Linearizable writes also imply mutual exclusion: of two concurrent writes, only one can go first. Operations aren't instantaneous and may overlap, but their effects become visible as if they were sequential: nothing happens instantly, yet everything appears atomic.

The book's example (Figure 11-2). P1 runs write(x, 1), P2 runs write(x, 2), P3 runs read(x) three times. x starts as ∅.

  • a) The first read can return 1, 2 or ∅: both writes are still in flight, so the read can be ordered before both, between them, or after both.
  • b) The second read can return only 1 or 2: the first write has completed, the second hasn't returned yet.
  • c) The third read can return only 2, "since the second write is ordered after the first".

Picture it

A single scoreboard in a stadium, updated by several people. Each update may take a few seconds to walk up the ladder, but the digits change at one instant during that climb. Everybody in the stadium sees the same board. Once you've seen 2, you'll never see an older number unless someone writes it again.

What's happening behind it

The checker tries every order of the five operations that respects real time ("if A finished before B started, A comes first") and replays them against a single register. A read's allowed set is the union of what it sees across all valid orders. This brute-force search is how tools like Jepsen's Knossos check histories (not in the book); it's exponential in the number of concurrent operations, which is why real checkers prune aggressively.

// how to build it: brute-force linearizability check for one register
function linearizable(ops: Op[]): boolean {          // Op = {kind:'w'|'r', v?, ret?, start, end}
  const used = ops.map(() => false);
  const go = (placed: number, cur: unknown): boolean => {
    if (placed === ops.length) return true;
    for (let i = 0; i < ops.length; i++) {
      if (used[i]) continue;
      // real-time rule: everything that ended before ops[i] began must already be placed
      if (ops.some((o, j) => !used[j] && j !== i && o.end < ops[i].start)) continue;
      if (ops[i].kind === 'r' && ops[i].ret !== cur) continue;   // read must see current value
      used[i] = true;
      if (go(placed + 1, ops[i].kind === 'w' ? ops[i].v : cur)) return true;
      used[i] = false;
    }
    return false;
  };
  return go(0, undefined /* ∅ */);
}

11 · LINEARIZATION POINT

The linearization point, and the CAS/ABA trap

pdf p356–358 · Fig 11-3 · Fig 11-4

A key trait of linearizability is visibility: once an operation completes, everyone must see it, and the system can't go back in time by reverting it or hiding it from some participants. Linearizability forbids stale reads and requires reads to be monotonic.

It's best explained with atomic (uninterruptible, indivisible) operations. Operations needn't be instantaneous (nothing is), but their effects must become visible at one moment, creating the illusion that they were. That moment is the linearization point. After a write's linearization point, every process sees either that value or a later one (if more writes are ordered after it). A visible value stays stable until the next one becomes visible, and the register must not alternate between the two most recent states.

The linearization point is a cutoff after which effects are visible. It can be implemented with locks around a critical section, atomic read/write, or read-modify-write primitives. Figure 11-3: linearizability assumes hard time bounds and real time, so effects must become visible between t1 (request issued) and t2 (response received). Figure 11-4: the linearization point splits the history into before (old value visible) and after (new value visible).

Move the linearization point

Note on atomic primitives. Most languages offer atomic write and compare-and-swap (CAS). An atomic write ignores the current value; CAS moves from one value to the next only if the previous value is unchanged [HERLIHY94]. Read-modify-write with CAS is trickier than plain check-and-set because of the ABA problem [DECHEV10]: if CAS expects A, it will succeed even if two other writers changed the value to B and back to A in between. Seeing A doesn't prove nothing changed since your read.

Step through the ABA problem

Picture it

A train ticket gate. You may push through at any moment while the light is green (between t1 and t2), but the turnstile turns exactly once. Before it turns you're outside; after, you're inside, and nobody can see you halfway. ABA is a different trap: you leave your coffee on a desk, someone drinks it and buys an identical cup, and when you return "it's the same cup" by every check you can make.

What's happening behind it

Reads also have linearization points. In the slider, each read is assumed to take effect at its midpoint: reads whose point lies before the write's point see old, after see new. A point outside [t1, t2] is illegal: before t1 the system would need to know the future, after t2 the client has already been told "done" while others can still see the old value. For ABA, the usual fix (not in the book) is to compare a version together with the value, for example a counter packed next to a pointer (Java's AtomicStampedReference), so A-with-version-1 differs from A-with-version-3.

12 · COST OF LINEARIZABILITY

What linearizability costs, and RIFL

pdf p358–359

Many systems today avoid linearizability. Even CPUs don't give linearizable access to main memory by default, because synchronization instructions are expensive and slow and cause cross-node CPU traffic and cache invalidations. It can be built from low-level primitives [MCKENNEY05a] [MCKENNEY05b].

In concurrent programming, CAS gives you linearizability. Many algorithms prepare a result and then publish it by swapping a pointer with CAS. Example: a concurrent queue that creates a linked-list node, then atomically appends it to the tail [KHANCHANDANI18].

In distributed systems linearizability needs coordination and ordering. It can be built with consensus: clients send messages to a replicated store, and the consensus module makes sure applied operations are consistent and identical across the cluster. Each write appears instantaneous, exactly once, somewhere between its invocation and completion [HOWARD14].

Linearizability is a local property and composes: combining linearizable histories gives a linearizable history [HERLIHY90]. A system whose objects are all linearizable is linearizable. Very useful, but its scope is one object: operations that touch two independent linearizable objects still need extra synchronization.

Sidebar: Reusable Infrastructure for Linearizability (RIFL)

RIFL makes remote procedure calls linearizable [LEE15]. Every message is identified by the client ID plus a client-local, monotonically increasing sequence number. Client IDs come from leases issued by a system-wide service; they make IDs unique and break ties between sequence numbers. A client with an expired lease can't commit: it must get a new lease and retry.

The problem it solves: if the server crashes before acknowledging, the client may retry an operation that was already applied. Client C1 writes V1 and gets no ack; meanwhile C2 writes V2; C1 retries and writes V1 again, and C2's write is lost. RIFL prevents re-execution: on a retry it returns a completion object saying the operation already ran, with its result. Completion objects are stored durably with the data records, but live differently: until the client promises not to retry, or until the server detects the client crashed (then all its completion objects can be removed). Creating the completion object must be atomic with the record mutation. Clients renew leases periodically to show they're alive; a client that fails to renew is marked crashed and its lease data is garbage-collected. Leases have limited lifetimes so a dead client's operations don't stay in the log forever. RIFL's advantage: since an RPC can't run more than once, an operation becomes linearizable by making its result visible atomically, and most of the mechanism is independent of the storage system underneath.

Network retries give at-least-once delivery. Linearizability needs exactly-once effects. Its linearizable reads also need confirmation that the leader is still the leader (a quorum round or a lease), unless you accept stale reads.

type Key = `${string}:${number}`;                                      // clientId:seq
function handle(req: { clientId: string; seq: number; lease: Lease; op: Op }) {
  if (leaseExpired(req.lease)) return { error: 'EXPIRED_LEASE' };       // must get a new lease, retry from scratch
  const done = completions.get(`${req.clientId}:${req.seq}`);
  if (done) return done.result;                                         // retry: do NOT re-apply
  return atomically(() => {                                             // one durable step:
    const result = apply(req.op);                                       //   mutate the record
    completions.put(`${req.clientId}:${req.seq}`, { result });          //   and record completion
    return result;
  });
}

13 · SEQUENTIAL CONSISTENCY

Sequential consistency: everyone agrees on one order, not on the clock

pdf p360–362 · Fig 11-5

Linearizability may be too expensive; we can relax it and keep strong guarantees. Sequential consistency orders operations as if they ran in some sequential order, while each process's own operations keep the order in which that process performed them.

Processes may see other processes' operations in an order consistent with their own history, but that view can be arbitrarily stale globally [KINGSBURY18a]. The order between processes is undefined: there's no shared notion of time.

It was first defined for multiprocessors [LAMPORT79]: requests to the same memory cell were queued in FIFO arrival order, overlapping writes to independent cells had no global order, and a read fetched either the cell's value or the latest value from the queue if the queue wasn't empty. Operations can be ordered in different ways (by arrival, or arbitrarily if two writes arrive together), but all processes observe them in the same order.

Each process issues reads and writes in its program's order, which is intuitive: any single-threaded program runs step by step. Writes from one process appear in the order that process submitted them. Writes from different sources may be ordered arbitrarily, but that order is the same for every reader.

Note: not the same as linearizability. Both require a global order, but linearizability makes it agree with real time; sequential consistency only keeps same-origin writes in order [VIOTTI16]. Also, linearizable histories compose; sequentially consistent schedules don't [ATTIYA94].

Figure 11-5. P1 writes 1, then (in wall-clock time) P2 writes 2. Yet 1 may be ordered after 2. P3 reads 2 then 1; P4 reads 2 then 1 too, and P4 can still read 2 at the moment P3 already reads 1. Both orders 1 → 2 and 2 → 1 would be valid, as long as all readers see the same one; here both saw "first 2, then 1" [TANENBAUM14].

Stale reads come from, for example, replica divergence: writes reach replicas in the same order but at different times. The main difference from linearizability is the lack of globally enforced time bounds. Under linearizability, when write W₁ completes, every reader can see a value at least as recent as W₁'s, and after a read R₁ returns, later reads return R₁'s value or newer. Sequential consistency lets a result become visible after its operation completes, as long as the order is consistent from every processor's point of view. Same-origin writes can't jump over each other, and the order must be the same for all readers.

Like linearizability, sequential consistency isn't guaranteed by modern CPUs by default: the processor reorders instructions, so memory barriers (fences) are needed to make writes visible to other threads in order [DREPPER07] [GEORGOPOULOS16].

14 · CAUSAL CONSISTENCY

Causal consistency: order only what depends on what

pdf p363–365 · Fig 11-6 · 11-7 · 11-8

(The section opens with a film quote about cause and effect.) A global order of all operations is often unnecessary, but we may still need to order some of them. Under causal consistency, all processes must see causally related operations in the same order. Concurrent writes with no causal link may be seen in different orders by different processes.

Figure 11-6: P1 and P2 make writes that aren't causally related. Their results reach readers at different times and out of order: P3 sees 1 then 2, while P4 sees 2 then 1.

Figure 11-7: causally related writes. Besides the value, each write now carries a logical clock value. P1 writes write(x, ∅, 1) → t1 (starting from the initial value ∅). P2 then writes write(x, t1, 2), declaring that it's logically ordered after t1, so the operations may only propagate in the order the logical clock sets. Even if the later write travels faster, it isn't made visible until all its dependencies have arrived, and the order is rebuilt from the logical timestamps. A happened-before relationship is set up logically, without physical clocks, and every process agrees on it.

Figure 11-8: the same causally related writes reach P3 and P4 in their logical order, so both see 1 then 2. Compare P3 and P4's histories with Figure 11-6.

Think of an online forum: you post, someone reads it and replies, a third person reads the reply and continues. Threads can branch: you might answer one reply and continue that chain, so some threads share only a few messages and there may be no single history of all messages.

A causally consistent system gives the application session guarantees: its view of the database matches its own actions, even if it reads and writes against different, possibly inconsistent servers [TERRY94]. They are monotonic reads, monotonic writes, read-your-writes and writes-follow-reads (section 16).

Causal consistency can be built with logical clocks [LAMPORT78] by sending context metadata with each message that summarises which operations logically precede it. A server's update carries the latest context. An operation is processed only when all operations preceding it have been applied; messages whose context doesn't match yet are buffered on the server because it's too early to deliver them.

Causal delivery: messages arriving out of order

Three causally chained messages: M1(∅, t1), M2(M1, t2), M3(M2, t3). The network delivers them in a random order.

Two well-known projects implement causal consistency: COPS (Clusters of Order-Preserving Servers) [LLOYD11] and Eiger [LLOYD13]. Both use a library (a front-end server that users connect to) that tracks dependencies. COPS tracks them through key versions; Eiger tracks operation order instead (its operations can depend on operations on other nodes, for example in multi-partition transactions). Neither exposes out-of-order operations the way eventually consistent stores might. Instead they detect and handle conflicts: COPS by checking key order and using application-specific functions, Eiger with last-write-wins.

Picture it

A group chat where "Yes, let's do it!" must never appear before the question "Dinner at 8?" it answers. Two unrelated messages ("Nice weather" and "Running late") may show in either order on different phones. Causal consistency is exactly that rule.

What's happening behind it

Each write carries the IDs of the writes it depends on. A replica applies a write only when its dependency set is already applied; otherwise it parks it. Without the buffer, a replica that receives M3 first applies it and exposes a reply to a message nobody can see yet. With the buffer, the visible order is always a prefix of the causal chain. The cost is metadata on every write and a wait when a dependency is slow.

15 · VECTOR CLOCKS

Vector clocks: detecting "before", "after" and "at the same time"

pdf p365–367 · Fig 11-9

Causal order lets a system rebuild the sequence of events even when messages arrive out of order: fill gaps and hold back results while messages are missing. If {M1(∅, t1), M2(M1, t2), M3(M2, t3)} each name their dependency and arrive out of order, the process buffers them until it has all dependencies and can restore their causal order [KINGSBURY18b]. Many databases, for example Dynamo [DECANDIA07] and Riak [SHEEHY10a], use vector clocks [LAMPORT78] [MATTERN88] to set causal order.

A vector clock gives a partial order between events and detects and resolves divergence between event chains. It lets us simulate common time and global state, and treat asynchronous events as synchronous. Each process keeps a vector of logical clocks, one per process. Every clock starts at its initial value and is incremented each time a new event happens (for example a write). When a process receives another's vector, it updates each entry to the maximum of its own and the received value (the highest value the sender has ever seen).

For conflict resolution: on a write, first check whether the key already has a value locally. If it does, append a new version to the version vector and record the causal link between the two writes. If not, start a new chain of events with a single version.

Earlier, with registers and wall-clock order, replica divergence first came up under sequential consistency. Since only writes to the same memory location must be ordered, independent values can't conflict [LAMPORT79]. But to gain availability and performance, replicas must be allowed to diverge not only by serving stale reads but also by accepting conflicting writes, creating two independent chains of events. Figure 11-9: one replica sees history 1, 5, 7, 8; the other reports 1, 5, 3. Riak lets users see and resolve such divergent histories [DAILY13].

Note. Causal consistency means storing causal history, garbage-collecting it, and asking the user to reconcile divergent histories on conflict. Vector clocks tell you a conflict happened, not how to resolve it, because resolution is often application-specific. That's why some eventually consistent databases, for example Apache Cassandra, don't order operations causally and use last-write-wins instead [ELLIS13].

Picture it

Each process keeps a scorecard with one column per process: "how many of your writes have I heard about". If my card is ≥ yours in every column, I've seen everything you've seen, so I'm after you. If each of us is ahead in some column, we wrote without hearing from each other: concurrent.

What's happening behind it

Compare two vectors entry by entry. If every entry of V ≤ the matching entry of U and at least one is smaller, V happened before U. If neither dominates, the events are concurrent. In Figure 11-9 the write of 8 has vector [4, 0] and the write of 3 has [2, 1]: 4 > 2 but 0 < 1, so neither dominates and the store holds a conflict. LWW resolves it by wall-clock timestamp, which silently drops one write (and depends on clocks being roughly in sync); siblings keep both and push the merge to the application, which is correct but more work.

// how to build it: vector clocks
type VC = Record<string, number>;
const tick  = (v: VC, me: string): VC => ({ ...v, [me]: (v[me] ?? 0) + 1 });          // local event
const merge = (a: VC, b: VC): VC => { const o = { ...a };                             // on receive
  for (const k in b) o[k] = Math.max(o[k] ?? 0, b[k]); return o; };
function compare(a: VC, b: VC): 'before' | 'after' | 'equal' | 'concurrent' {
  let lt = false, gt = false;
  for (const k of new Set([...Object.keys(a), ...Object.keys(b)])) {
    if ((a[k] ?? 0) < (b[k] ?? 0)) lt = true;
    if ((a[k] ?? 0) > (b[k] ?? 0)) gt = true;
  }
  return lt && gt ? 'concurrent' : lt ? 'before' : gt ? 'after' : 'equal';
}

16 · SESSION MODELS

Session models: what one client is promised

pdf p368–369

Thinking in terms of how values propagate helps database developers keep invariants, but some things are easier from the client's side: how does one client observe the system while it reads and writes? Session models [VIOTTI16] (also called client-centric consistency models [TANENBAUM06]) answer that. The earlier models explain ordering among concurrent clients; these focus on one client. We still assume each client's operations are sequential, and make no assumptions about operations left incomplete because the client crashed or lost its connection.

Clients can often connect to any available replica. If a recent write to one replica hasn't reached another, the client may not see its own change. The four guarantees:

  • Read-own-writes: every read after a write, on the same or another replica, sees the updated value. read(x) right after write(x, V) returns V.
  • Monotonic reads: once read(x) has seen V, later reads see V or something newer.
  • Monotonic writes: values from the same client appear in the order the client wrote them. If write(x, V2) came after write(x, V1) in the session, everyone sees V1 first, then V2. Without it, old data can be resurrected, losing data.
  • Writes-follow-reads (session causality): writes are ordered after the writes seen by earlier reads. If write(x, V2) follows a read(x) that returned V1, then V2 is ordered after write(x, V1).

Warning: session models say nothing about operations from different clients or different logical sessions [TANENBAUM14]. They describe order from one process's view, but the guarantees must hold for every process: if P1 can read its own writes, so must P2.

Monotonic reads + monotonic writes + read-own-writes together give Pipelined RAM (PRAM) consistency [LIPTON88] [BRZEZINSKI03], also called FIFO consistency: writes from one process propagate in the order that process made them. Unlike sequential consistency, writes from different processes may be seen in different orders. Client-centric properties are desirable, and developers use them in most cases to validate their systems and make them easier to use.

Session simulator: 3 replicas, async replication (simulated, pooled over 4,000 sessions)

How the simulator works (modelled)

A client writes V1 to a random replica at time 0; the other two get it after an exponential delay with the mean lag you set. It then reads three times, one gap apart, and writes V2 at the first gap. "Random replica" sends each request anywhere. "Sticky" always uses the replica it wrote to. "Session token" sends the highest version the client has seen; a replica that's behind waits until it catches up (we report the average wait). Monotonic writes: replicas apply V1 and V2 in arrival order unless they keep per-client sequence numbers; a replica that ends with V1 has resurrected old data.

Picture it

You update your profile photo, refresh, and see the old photo (read-own-writes broken). You refresh again and see the new one, then the old one again (monotonic reads broken). You rename a file twice and a colleague ends up with the first name (monotonic writes broken). You read a comment, reply to it, and someone sees your reply with no comment above it (writes-follow-reads broken).

What's happening behind it

Every session guarantee is fixable by carrying a little state: the replica you used (stickiness), or the version you've seen (a token / logical clock). Stickiness costs availability when that replica dies; tokens cost waiting time when the replica you hit is behind. Ordering writes per client (sequence numbers) prevents resurrection. That's why many systems give these guarantees cheaply even though their global model is only eventual.

17 · EVENTUAL CONSISTENCY

Eventual consistency: if writes stop, copies converge

pdf p370

Synchronization is expensive in multiprocessor programming and in distributed systems alike, so we can relax guarantees and let nodes diverge (sequential consistency already lets reads see writes at different speeds). Under eventual consistency, updates propagate asynchronously. Formally: if no new updates are made to a data item, eventually all accesses return the latest written value [VOGELS09]. On conflict, "latest" may change, because values from diverged replicas are reconciled with a conflict-resolution strategy such as last-write-wins or vector clocks (section 15).

"Eventually" sets no time bound. A delivery service that only promised "eventually" wouldn't sound reliable, yet in practice this works well, and many databases today are described as eventually consistent.

How fast is "eventually"? (simulated, 400 runs pooled)

Picture it

Gossip in a village. Nobody can tell you the exact hour everyone will know, but if nothing new happens, by next week everyone knows the same story. Eventual consistency is a promise about the story settling, not about how soon.

What's happening behind it

One write reaches the first replica at time 0 and each other replica after an exponential delay. The curve is the share of replicas that already have it; a read from a random replica at time t is stale with probability 1 minus that share. With a 30 ms mean and 5 replicas, a read 20 ms after the ack is stale about 40% of the time (4 of 5 replicas hold back an exponential, e−20/30 ≈ 0.51, × 4/5). This is the "Probabilistically Bounded Staleness" view: "eventually" in practice means a distribution of milliseconds you can measure.

Beyond the book: measured numbers

Bailis et al. (PBS, PVLDB 5(8), 2012) modelled Dynamo-style stores with production latency data and report in the abstract that eventually consistent configurations often return consistent data within tens of milliseconds. DynamoDB's docs say global tables in the default multi-Region eventual mode usually replicate item changes within about a second, and offer a multi-Region strong mode that replicates synchronously before the write returns. Sources: arxiv.org/abs/1204.6082; AWS DynamoDB "Read consistency".

18 · TUNABLE CONSISTENCY

N, W, R: dial consistency per request, and the quorum rule

pdf p371–372

Eventually consistent systems are sometimes described in CAP terms: trade availability for consistency or back. On the server side they usually implement tunable consistency with three numbers:

  • Replication factor N: how many nodes store a copy.
  • Write consistency W: how many nodes must acknowledge a write for it to succeed.
  • Read consistency R: how many nodes must answer a read for it to succeed.

If R + W > N, the system can guarantee returning the most recent written value, because the read set and the write set always overlap. Example: N = 3, W = 2, R = 2 tolerates the failure of just one node. Two of three must acknowledge a write; ideally the write is also replicated asynchronously to the third, and if the third is down, anti-entropy (Chapter 12) eventually brings it up to date. A read needs two of three replicas available to answer consistently; any pair includes at least one node with the newest record for the key.

Tip: the coordinator sends a write to all N nodes but waits only for W (or W − 1 if the coordinator is itself a replica); the rest can finish asynchronously or fail. A read must collect at least R responses. Some databases use speculative execution: they send extra read requests so that if one of the original requests fails or is slow, a speculative response can count toward R instead.

Write-heavy systems sometimes choose W = 1, R = N: writes are acknowledged by one node, but reads need every replica (even possibly failed ones) to be available. The mirror case W = N, R = 1 lets any single node serve the latest value, as long as writes succeed only after reaching all replicas. Raising R or W raises latency and the number of nodes that must be up; lowering them improves availability at the cost of consistency.

Sidebar: quorums

A consistency level of ⌊N/2⌋ + 1 nodes is a quorum, a majority. With 2f + 1 nodes, live nodes keep accepting reads and writes while up to f nodes are unavailable; the system tolerates at most f failures. It can't survive losing a majority: with three replicas and two down, only one node can answer, which is not enough for read or write consistency.

Quorum reads and writes don't guarantee monotonicity when a write is incomplete. If a write fails after reaching one replica of three, a quorum read may return either that incomplete value or the old one, depending on which replicas it contacts. Later reads don't have to contact the same replicas, so the values they return can alternate. To get monotonic reads (at a cost in availability) you need blocking read repair (Ch.12, "Read Repair").

What's happening behind it

Overlap is guaranteed by counting: two sets of sizes W and R taken from N items share at least W + R − N items. Latency is set by the W-th (or R-th) fastest replica, not the slowest, so a quorum hides one slow node. In the calculator, replica latencies are modelled as independent exponentials with the mean you set; the expected k-th fastest of N is mean · Σ 1/i for i = N−k+1 … N. When R + W ≤ N (a "partial quorum") a read can miss the write entirely; if the write reached exactly W replicas and the read picks R at random, the chance of missing it is C(N−W, R) / C(N, R). That number is from Bailis et al.'s PBS analysis (not in the book) and ignores the asynchronous copies that usually make it smaller.

19 · WITNESS REPLICAS

Witness replicas: majority safety without storing every copy

pdf p373–374

Quorum reads improve availability: with some nodes down, the system still serves reads and writes. Because any two majorities share at least one node, any quorum read sees the latest completed quorum write. But replication with majorities costs storage: replication factor five means five copies.

Witness replicas reduce that. Split replicas into copy and witness subsets. Copy replicas hold the records as before. In normal operation witnesses only store a record that the write happened. Copies can run short: with three copy and two witness replicas, if two copies go down, the quorum is one copy and two witnesses. On write timeouts or copy failures, witnesses can be upgraded to store the record temporarily in place of the failed copies. When the originals recover, upgraded replicas revert, or the recovered replicas become witnesses.

Example from the book. Three nodes, two copies and one witness: [1c, 2c, 3w]. A write arrives while 2c is temporarily down, so the record is stored on 1c and, temporarily, on witness 3w. When 2c returns, repair brings it up to date and the redundant copy is removed from the witness. For reads, suppose the record is on 1c and 3w but not on 2c. Any two replicas form a quorum, so whichever pair is up, [1c, 2c], [1c, 3w] or [2c, 3w], we can serve consistent results. Reading from [1c, 2c], we fetch the newest record from 1c and can replicate it to 2c, which lacks it. If only [2c, 3w] are up, the newest record comes from 3w; to restore the original layout, it's replicated to 2c and removed from the witness.

In general, n copy and m witness replicas give the same availability as n + m copies, provided two rules hold: reads and writes use majorities (N/2 + 1 participants), and at least one replica in the quorum is a copy. It works because data is always on a copy or a witness: copies are repaired after failures, and witnesses hold the data in the meantime. Witnesses cut storage costs while keeping consistency invariants. Implementations include Spanner [CORBETT12] and Apache Cassandra.

What's happening behind it

20 · STRONG EVENTUAL CONSISTENCY AND CRDTs

CRDTs: data types that merge in any order

pdf p375–378

Between strong models (linearizability, serializability) and weak eventual consistency there's a middle ground: strong eventual consistency. Updates may reach servers late or out of order, but once all updates have arrived, conflicts can be resolved and the updates merged into the same valid state everywhere [GOMES17].

Under some conditions we can keep extra state with each operation so diverged states can be reconciled (merged) afterwards. The best-known example is Conflict-Free Replicated Data Types (CRDTs) [SHAPIRO11a], implemented for example in Redis [BIYIKOGLU13]. CRDTs are data structures that rule out conflicts and let operations be applied in any order without changing the result. In a cluster of replicated counters, each node can increment independently even while partitioned; when the network heals, the results are reconciled and no operation from the partition is lost. That suits eventually consistent systems: replicas run operations locally without coordination, operations reach other replicas eventually (maybe out of order), and the full state can be rebuilt from local states or operation sequences.

The simplest kind is the operation-based Commutative Replicated Data Type (CmRDT). Its operations must be:

  • Side-effect free: their application does not change the system state.
  • Commutative: argument order doesn't matter, x • y = y • x; merging x with y equals merging y with x.
  • Causally ordered: delivery depends on a precondition ensuring the system has reached a state the operation can be applied to.

Grow-only counter (the book's worked example). Each server keeps a vector of the last known counter values of every participant, starting at zero; it may only change its own slot. merge(state1, state2) takes the maximum per slot. The value is the sum of all slots. Since each server updates only its own independent slot, no coordination is needed.

The book's G-Counter example, step by step

A Positive-Negative Counter (PN-Counter) supports increments and decrements with two vectors: P for increments and N for decrements. In large systems, to avoid shipping huge vectors, super-peers replicate counter states and cut down constant peer-to-peer chatter [SHAPIRO11b].

PN-Counter playground: increment and decrement during a partition

Registers. The simplest is the last-write-wins (LWW) register: each value carries a unique, globally ordered timestamp; on conflict only the value with the larger timestamp is kept. Its merge (pick the largest timestamp) is commutative too. If values must not be discarded, use a multi-value register: it stores every written value and lets the application pick (with application-specific merge logic).

Sets. A grow-only set (G-Set): each node appends elements to its local state; adding elements always gives a valid set and merging two sets (union) is commutative. Two sets support adds and removes: an addition set and a removal set, with the invariant that only values already in the addition set may be put in the removal set. The current state is the addition set minus the removal set [SHAPIRO11b].

Two-set (add set + remove set) playground

A more complex example is a conflict-free replicated JSON data type: insertions, deletions and assignments on deeply nested JSON documents with lists and maps. Its merge runs on the client side and doesn't need operations to arrive in any particular order [KLEPPMANN14]. CRDTs offer many possibilities, and more data stores use them to provide Strong Eventual Consistency (SEC), a powerful tool for building fault-tolerant distributed systems.

Picture it

Three tally sheets for counting visitors at three gates. Each gatekeeper only ever writes in their own column. When sheets are compared, you copy across the bigger number in each column; you can compare in any order, twice, or late, and the total always comes out the same. A shared single number ("current count = 41") would instead need everyone to agree who wrote last.

What's happening behind it

Max-per-slot merge is commutative (order doesn't matter), associative (grouping doesn't matter) and idempotent (merging the same state twice changes nothing). Those three properties are why replicas converge however gossip delivers states. The book introduces the counter under the operation-based (CmRDT) heading, but the example it walks through ships and merges whole state vectors, which is the state-based (CvRDT) form (this classification is from [SHAPIRO11b], not stated in the book). The two-set's catch (not in the book): once an element is in the removal set it stays removed forever, because the removal "tombstone" can't be undone; re-adding needs a richer type such as an observed-remove set.

// how to build it: G-Counter and PN-Counter (state-based)
type G = number[];                                           // one slot per node
const inc   = (g: G, me: number): G => g.map((v, i) => (i === me ? v + 1 : v));
const mergeG = (a: G, b: G): G => a.map((v, i) => Math.max(v, b[i]));   // commutative, associative, idempotent
const valueG = (g: G) => g.reduce((s, v) => s + v, 0);
type PN = { P: G; N: G };
const mergePN = (a: PN, b: PN): PN => ({ P: mergeG(a.P, b.P), N: mergeG(a.N, b.N) });
const valuePN = (x: PN) => valueG(x.P) - valueG(x.N);

21 · SUMMARY

The ladder of models, and how to choose

pdf p379–380

Fault-tolerant systems use replication to stay available when some processes fail or don't respond, and keeping copies in sync needs extra coordination. The single-operation models, from most to least guaranteed (the book stresses these are recap definitions; see the full ones above):

  • Linearizability: operations appear to apply instantaneously, and real-time order is kept.
  • Sequential consistency: effects propagate in some total order consistent with each process's own order.
  • Causal consistency: causally related operations are seen in the same order by everyone.
  • PRAM/FIFO consistency: effects appear in the order each process made them; writes from different processes may be seen in different orders.

Session models: read-own-writes (reads reflect your earlier writes), monotonic reads (never see something older than you've seen), monotonic writes (your writes reach others in your order), writes-follow-reads (your writes are ordered after the writes your earlier reads saw).

Knowing these lets you understand what the systems under you guarantee and use them correctly. Consistency models are rules for one system only: stacking a system with weaker guarantees on top of one with stronger guarantees, or ignoring the guarantees of the systems underneath, can cause unrecoverable inconsistencies and data loss. Finally: eventual and tunable consistency, quorums that use majorities to serve consistent data, and witness replicas that cut storage costs.

When to pick which (practical guide, not in the book)
  • Locks, leader election, unique usernames, money balances: linearizable (consensus store or a single primary with synchronous replicas).
  • Feeds, comments, chat: causal or session guarantees; a reply must not appear before its parent, but a global order is waste.
  • Counters, likes, carts, presence: CRDTs, so partitions never lose increments.
  • Caches, analytics, product catalogues: eventual with tunable quorums; use R + W > N for the few reads that must be fresh.
  • Always check the layer below: a "read-your-writes" cache over an async replica is the stacking trap the book warns about.
Picture it

A staircase. Each step down removes one promise (real time, then a single shared order, then order for unrelated writes, then any order at all) and gives back latency and availability. CRDTs are a side ramp: they give up on ordering but make it not matter.

What's happening behind it

Each step down the ladder removes a synchronization point. Linearizable needs agreement before acknowledging. Sequential needs agreement on order, but not before acknowledging. Causal needs only dependency tracking. PRAM needs only per-writer sequence numbers. Eventual needs nothing up front and pays later in conflict resolution. That's the "synchronization costs" axis from section 8 made concrete.

Check yourself

answer before you open
1. Why is "update every replica atomically on every write" usually avoided?

Because atomically updating several copies is equivalent to consensus [MILOSEVIC11], which costs coordination on every operation. The chapter looks for cheaper models that let replicas diverge a little while still looking consistent to users (section 1).

2. A node is up and serving, but cut off from the rest of the cluster. Why does CAP care about this case and not about a crashed node?

A crashed node can't answer, so it can't answer wrongly. A partitioned node is alive and CAP requires every non-failed node to respond, which forces the choice: refuse (CP) or serve possibly stale data (AP). Consistency problems need no node to be down at all (section 4).

3. What does PACELC add to CAP, and where do you pay for it every day?

"Else": with no partition you still choose between latency and consistency. Waiting for a remote copy before acknowledging adds a round trip to every consistent write; DynamoDB's strongly consistent reads, which cost twice as much as eventual ones, are an everyday version (section 3).

4. A search across 20 shards loses 2 shards. Explain the harvest/yield choice in numbers.

All-or-nothing keeps harvest at 100% but every query that touches a dead shard fails (if every query touches all 20, yield drops to 0%). Partial answers keep yield near 100% with about 18/20 = 90% harvest. Which is right depends on whether incomplete data is acceptable for that request (section 5).

5. A register returns 1, then 0, while a write of 1 is still in progress. Which register types allow this?

Safe and regular registers allow it (regular: each overlapping read may return old or new independently). An atomic register forbids it: once a read has returned the new value, no later read returns the old one (section 6).

6. In Figure 11-2, why can the second read return 1 or 2 but not ∅?

Write 1 has completed before the second read starts, so it must be ordered before that read; write 2 still overlaps the read, so it may or may not have taken effect. (The book also says the third read can only return 2; that holds when write 1 is ordered first. Since the two writes overlap, a strict checker also allows the order write 2, write 1 (section 10).)

7. Where may a linearization point lie, and why not outside that range?

Between the invocation (t1) and the completion (t2). Before t1 would need an oracle that knows a future request; after t2 the caller has been told "done" while others could still see the old value (section 11).

8. How does RIFL turn a retried write into an exactly-once write, and what does it cost in RAMCloud?

Each request carries (client ID from a lease, sequence number). The server stores a completion object atomically with the mutation; a retry finds it and returns the stored result instead of re-applying. The RIFL paper reports +530 ns on a 13.5 µs durable write, about 4% (section 12, numbers beyond the book).

9. P3 reads 2 then 1, and P4 reads 1 then 2, for two unrelated writes. Which models allow this?

Causal and PRAM allow it (the writes are concurrent, from different processes). Sequential consistency forbids it, because all readers must see one order. Linearizability forbids it too (section 13, try it in the checker).

10. Vectors [4, 0] and [2, 1]: what's the relation, and what does Cassandra do differently from Riak here?

Concurrent: neither dominates. Riak can keep both as siblings for the application to merge; Cassandra doesn't track causality and keeps the value with the higher timestamp (last-write-wins), silently dropping the other (section 15).

11. Which three session guarantees together give PRAM, and which one is left out?

Monotonic reads + monotonic writes + read-own-writes give PRAM/FIFO consistency. Writes-follow-reads (session causality) is the fourth guarantee, not part of that combination (section 16).

12. N = 5. Give two (W, R) settings with guaranteed overlap, and say how many failures writes and reads each tolerate.

W = 3, R = 3: overlap ≥ 1; writes and reads each tolerate 2 down. W = 5, R = 1: overlap guaranteed; writes tolerate 0 down, reads tolerate 4. Rule: R + W > N; writes survive N − W failures, reads N − R (section 18).

13. Quorum reads and writes, R + W > N, yet a client sees v2 then v1. How, and what fixes it?

An incomplete write reached one replica; one quorum read included it, the next contacted two replicas without it. Blocking read repair (write the newest value back to a quorum before returning) restores monotonic reads at some cost in availability (section 18).

14. With 3 copy replicas and 4 witnesses, what goes wrong?

Seven voters, majority 4: the four witnesses alone form a majority that contains no copy, breaking the rule that every quorum must include a copy replica. Someone could prove a write happened but nobody in that quorum could return the data (section 19).

15. Why does a G-Counter's merge use max per slot, not sum?

Max is idempotent: receiving the same state twice changes nothing, and combined with commutativity and associativity, replicas converge however often and in whatever order states arrive. Summing would double-count repeated deliveries. Each node only writes its own slot, so max never loses an increment (section 20).
