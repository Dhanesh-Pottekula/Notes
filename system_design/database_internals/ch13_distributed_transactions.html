01 · CHAPTER OPENING

Atomic, even when the steps run on different machines

pdf p403–404

To keep a distributed system in order we need some consistency guarantee. Chapter 11's consistency models talk about one object and one operation at a time. Databases usually need more: several operations that happen atomically, as one unit.

Petrov describes an atomic transaction as a state transition: the database is in state A before the transaction and in state B after it. A transaction carries no fixed state of its own; it applies operations to records starting at some moment. That gives the system freedom: transactions can be reordered and even retried.

The core job of transaction processing is to decide which histories are allowed, that is, to model which interleavings of transactions are acceptable. A history here is a dependency graph: which transactions ran before the current one. A history is serializable if it is equivalent to (has the same dependency graph as) some history that runs the transactions one after another. Chapter 5's "Serializability" section has the details; this chapter is the distributed counterpart of Chapter 5.

On a single partition, the pessimistic (lock-based or tracking) and optimistic (try, then validate) schemes from Chapter 5 are enough. Neither solves the multipartition case, which needs coordination between servers, a distributed commit and a distributed rollback.

Petrov's example is a money transfer: you want the credit to one account and the debit from the other to happen together. Look closer and even one debit isn't a single step: read the old balance, subtract, save. Each of those is several steps again (receive the request, parse it, find the data on disk, write, acknowledge). A simple write is hundreds of small steps. So the system must first execute the transaction and only then make its results visible.

  • Transaction: a set of operations forming one atomic unit of execution.
  • Atomicity: all of its results become visible, or none do, even if it changed many rows or many tables.
  • Recoverable: if it can't finish, is aborted or times out, its effects are rolled back completely, as if it had never been tried. A partially executed, non-recoverable transaction can leave the database inconsistent.
  • Across nodes: nodes fail and recover independently, and the network can partition, yet their states must stay consistent. So atomicity covers remote operations too: changes reach all involved nodes durably, or none [LAMPSON79].
Picture it

Two bank branches in different cities. Moving ₹300 from Asha's account in Pune to Ravi's account in Delhi means Pune subtracts and Delhi adds. If Pune's clerk subtracts and then Delhi's line goes dead, ₹300 has vanished from the world. A distributed transaction protocol is the phone procedure both clerks follow so that this can't happen: nobody writes the change in ink until both have said "I can do it", and both then do it.

Try it: one transfer, two partitions, one crash

What's happening behind it

Without a protocol, each node commits its own half the moment it finishes, so a crash in between leaves the system in a state that no serial history could produce (money destroyed). With atomic commitment, a node first makes its half durable but invisible, says so, and only flips it to visible when it learns that every other node did the same. A crash then leads to "both" or "neither": either the transaction aborts everywhere, or the crashed node finishes its half from its log when it comes back. The invariant (total money) never shows a broken value to readers.

One of the first precise treatments of making updates on several machines atomic in the face of crashes; it introduced stable storage and a two-phase-style commit. Worth reading for the clean failure model.

02 · MAKING OPERATIONS APPEAR ATOMIC

Atomic commitment: a unanimous yes, or nothing

pdf p405–406, p434 fn 1

To make several operations (some remote) look atomic we need a class of algorithms called atomic commitment. The rules:

  • No disagreement. The transaction commits only if every participant votes for it; one "no" is enough to abort.
  • Failed processes must reach the same conclusion as the rest of the cohort when they come back.
  • No Byzantine tolerance. If a process lies about its state or decides arbitrarily, unanimity means nothing, so atomic commitment does not work with Byzantine failures [HADZILACOS05].
  • Participants only vote. They can't choose, influence or change the proposed transaction or propose another; they can only say whether they are willing to execute it [ROBINSON08].

Atomic commitment says nothing strict about what prepare, commit and rollback mean inside each node. Implementers decide:

  • when data counts as ready to commit, i.e. a pointer swap away from becoming public;
  • how to do the commit itself so results become visible as fast as possible;
  • how to roll back if the algorithm decides not to commit.

(Chapter 5 covered the node-local versions of these.) Users include MySQL (distributed transactions) and Kafka (producer and consumer interaction [MEHTA17]).

In a database the transaction manager runs distributed transactions: it schedules, coordinates, executes and tracks them. In a distributed setting it makes sure each node's local visibility matches what the distributed atomic operation prescribes: the transaction commits in all partitions and on all replicas.

The chapter covers two algorithms: two-phase commit, which solves the commitment problem but can't survive a failed coordinator, and three-phase commit [SKEEN83], which solves non-blocking atomic commitment and lets participants proceed even if the coordinator fails [BABAOGLU93]. Footnote 1 adds the fine print: the non-blocking guarantee assumes a highly reliable network, meaning one without partitions [ALHOUMAILY10].

Picture it

A jury that may only answer "guilty as charged" or "not". Jurors can't rewrite the charge, and one dissent means no verdict. That works only if every juror is honest: a juror who says "yes" in the room and "no" outside breaks the whole idea, which is why atomic commitment can't tolerate liars.

Try it: set each cohort's vote

What's happening behind it

The decision function is a plain AND over the votes, and a missing vote counts as "no" after a timeout. That makes the outcome easy to reason about but gives every participant a veto, including a crashed one. A liar breaks it from the inside: it votes yes, the coordinator commits, and the liar then does something else, so the "everyone did the same thing" promise is false and nobody can tell. Contrast with consensus (Chapter 14), where participants agree on a value and only a majority has to be alive.

03 · TWO-PHASE COMMIT

2PC: collect votes, then flip the switch

pdf p407–409 · Fig 13-1

2PC is the most direct protocol for multipartition atomic updates and is usually discussed for database transactions. Phase one distributes the value to decide on and collects votes. Phase two just flips the switch: it makes the result of phase one visible.

  • Coordinator (leader): holds the state, collects votes, and is the reference point for the round.
  • Cohorts: all other nodes. Usually partitions working on disjoint datasets that the transaction touches.
  • The coordinator and every cohort keep a local operation log of each step.
  • What is voted on is usually the identifier of the distributed transaction, but 2PC works in other settings too.
  • Who coordinates is not fixed by the protocol: the node that received the request, a randomly picked node, one chosen by leader election, a manually assigned one, or one fixed for the system's lifetime. The role can move to another participant for reliability or performance.

Prepare. The coordinator sends a Propose message about the new transaction. Each cohort decides whether it can commit its own part. Yes → a positive vote; otherwise it asks the coordinator to abort. All cohort decisions are persisted in the coordinator's log, and each cohort keeps a copy of its own decision locally. A cohort may refuse, for example, if a conflicting transaction already committed a different value.

Commit/abort. If even one cohort voted to abort, the coordinator sends Abort to all. Only if all voted yes does it send Commit. One rejection aborts the whole round.

At every step, coordinator and cohorts write the result to durable storage, so they can rebuild state after a local failure and forward or replay results for other participants. In databases, one 2PC round usually handles one transaction. During prepare, the transaction's contents (operations, identifiers, metadata) go from the coordinator to the cohorts, which execute it locally and leave it partially committed (also called precommitted), ready to be finalized. So by the time the transaction commits, its contents are already durable on every node [BERNSTEIN09].

Picture it

A wedding officiant (coordinator) asks each partner "do you?" (Propose). Each answers, and once one says "I do" they can't take it back (the promise). Only after hearing two "I do"s does the officiant pronounce them married (Commit). If either says no, there's no wedding (Abort) and nobody is half-married.

Step through 2PC (Figure 13-1, rebuilt)

What's happening behind it

The trick is the prepared state. Before voting yes, a cohort does all the work that could fail (take locks, check constraints, write the changes and a "prepared" record to its log and force it to disk). After that, committing can't fail: it's a pointer swap plus a log record. So the coordinator's decision really is the only thing left, and a "yes" is a promise the cohort can keep even across a crash, because the promise is on disk. The coordinator's decision record is the commit point of the whole distributed transaction: once it's durable, the outcome is fixed.

Worked example: counting a 2PC round

Three cohorts, all vote yes. Messages: 3 Propose + 3 votes + 3 Commit + 3 acks = 12, i.e. 4N. Network round trips on the critical path: 2 (propose/vote, commit/ack). Forced log writes in the simplest (presumed-nothing) form (counting convention not in the book): each cohort forces "prepared" and "committed" (2 × 3 = 6) and the coordinator forces its decision (1) = 7, i.e. 2N + 1. The client can be told "committed" as soon as the coordinator's decision is durable, which is after one round trip plus two fsyncs (the cohort's prepare and the coordinator's decision) on the critical path.

How to build it (core logic, TypeScript-style)

// coordinator: one round per transaction id
async function twoPhaseCommit(txId: string, cohorts: Cohort[], log: Log) {
  log.force({ txId, type: 'begin', cohorts: cohorts.map(c => c.id) });
  const votes = await Promise.all(cohorts.map(c =>
    c.propose(txId).catch(() => 'no')));          // timeout or crash counts as "no"
  const decision = votes.every(v => v === 'yes') ? 'commit' : 'abort';
  log.force({ txId, type: decision });            // <- commit point
  await Promise.all(cohorts.map(c => retryForever(() => c.decide(txId, decision))));
  log.append({ txId, type: 'end' });              // lets the coordinator forget txId
  return decision;
}

// cohort
function onPropose(txId: string): 'yes' | 'no' {
  if (!executeLocally(txId)) { log.force({ txId, type: 'abort' }); return 'no'; }
  log.force({ txId, type: 'prepared' });         // the promise, now durable
  return 'yes';                                   // from here on: may not abort alone
}
function onDecide(txId: string, d: 'commit' | 'abort') {
  log.force({ txId, type: d });
  d === 'commit' ? makeVisible(txId) : rollback(txId);
  releaseLocks(txId);
}
Beyond the book: 2PC in real systems
  • PostgreSQL exposes the cohort side as SQL: PREPARE TRANSACTION 'id', then COMMIT PREPARED 'id' or ROLLBACK PREPARED 'id'. It's off by default (max_prepared_transactions = 0), and a prepared transaction keeps its locks until someone resolves it, which is exactly the blocking problem of section 5. (postgresql.org/docs, "PREPARE TRANSACTION")
  • MySQL/InnoDB supports XA: XA START, XA END, XA PREPARE, XA COMMIT. MySQL also runs an internal 2PC between the binary log and InnoDB so both agree after a crash. (dev.mysql.com, "XA Transactions")
  • Kafka transactions: a transaction coordinator logs the transaction's state in an internal topic, then writes commit or abort markers into every partition the producer wrote to; consumers in read-committed mode skip aborted data. That's 2PC with the coordinator's log as the decision record [MEHTA17].
  • Sagas (Garcia-Molina & Salem, SIGMOD 1987) are the common microservice alternative: no prepare phase, each step commits locally and a failure runs compensating steps. You give up isolation (others see intermediate states) to avoid holding locks across services.

04 · COHORT FAILURES IN 2PC

A cohort fails: abort if it hadn't voted, wait if it had

pdf p410–411 · Fig 13-2

Fails during propose (Figure 13-2). The coordinator needs every vote positive, so if one cohort is unavailable it aborts the transaction. That hurts availability: one failed node can stop transactions from happening. Some systems, Spanner for example (section 9), run 2PC over Paxos groups instead of single nodes to make the protocol more available.

The central idea of 2PC is the cohort's promise: once it answers yes, it won't go back on that, so only the coordinator can abort.

Fails after voting yes. When it recovers, the cohort must learn the actual outcome before serving values correctly, because the coordinator may have aborted due to other cohorts' votes. It catches up with the coordinator's final decision, usually because the coordinator persists a decision log and replicates decision values to failed participants. Until then the cohort can't serve requests: it's in an inconsistent state.

Lost messages. There are several places where a process waits for others (the coordinator collecting votes, a cohort waiting for commit/abort). A link failure can lose a message and the wait would last forever. If the coordinator gets no reply during propose, it can time out and abort.

Picture it

A group dinner booking needs all five friends to confirm. If one doesn't answer the group chat before the deadline, the booking is cancelled (abort before the vote). If a friend said "I'm in" and then their phone died, when it comes back they can't just assume the dinner is on: they must check the group chat to see whether someone else cancelled.

Step through a cohort failure

What's happening behind it

The two cases differ by one durable record. With no "prepared" record in its log, a recovering cohort knows it never promised anything, so it can roll its part back on its own (the coordinator must have aborted, since a vote was missing). With a "prepared" record, it promised, and only the coordinator's decision tells it which way to go; it must keep the transaction's locks and refuse to serve those rows until it asks.

Measured numbers (modelled): how likely is "everyone is up"?

2PC needs all N cohorts. If each is a single node that is up with probability p (independently), a transaction touching N shards can commit with probability pN. Make each cohort a Paxos group of r replicas that needs only a majority, and a cohort is up with probability P(majority of r up). Independence and the uptime values are assumptions, not data.

05 · COORDINATOR FAILURES IN 2PC

The coordinator fails: sometimes peers know, sometimes nobody does

pdf p412–413, p434 fn 2 · Fig 13-3, 13-4

Decision made, not delivered (Figure 13-3). If a cohort gets no commit or abort in phase two, it should find out what the coordinator decided. The coordinator may have decided but failed to tell this replica. The decision can then be copied from peers' transaction logs or from a backup coordinator. Copying a commit decision is safe because decisions are unanimous: commit on one cohort means every cohort must commit.

Decision never sent (Figure 13-4). In phase one the coordinator collects votes, which are also promises to wait for its explicit commit or abort. If it fails after collecting votes but before broadcasting the result, the cohorts are uncertain: they don't know what it decided, or whether any participant (perhaps one that is also unreachable) was told [BERNSTEIN87]. The cluster is undecided, and with a permanent coordinator failure the cohorts can never learn the outcome. That is why 2PC is called a blocking atomic commitment algorithm. If the coordinator never recovers, its replacement must collect the votes again for that transaction and then decide.

Many databases use 2PC: MySQL, PostgreSQL, MongoDB and others. (Footnote 2: MongoDB's documentation says that as of v3.6 its 2PC gives only transaction-like semantics.) It's popular because it is simple (easy to reason about, implement and debug) and cheap (few messages and round trips). Good recovery mechanisms and backup coordinators reduce the chance of the failures above.

Picture it

A referee collects sealed votes, walks out of the room, and collapses in the corridor. If he had already told one player the result, the others can ask that player. If he told no one, the players sit there holding their promises: none of them may leave (release locks), and none may guess, because the referee might have written "commit" in his notebook and might have shouted it to someone in the corridor before collapsing.

Step through a coordinator failure

Try it: can an in-doubt cohort decide by asking its peers?

You are a cohort that voted yes and then heard nothing. You can reach your three peers. Set what each one tells you. (The full decision rule, often called the cooperative termination protocol, is standard textbook material, e.g. [BERNSTEIN87], not spelled out in this chapter.)

What's happening behind it

An in-doubt cohort can safely decide only if some reachable peer holds proof: "committed" proves the coordinator decided commit; "aborted" or "never voted yes" proves the decision can't have been commit. If every reachable peer is itself prepared-and-in-doubt, the only node that might know is the dead coordinator (or an unreachable peer it told), so any guess could contradict a decision already acted on. The cohort must keep its locks and wait. That is the blocking window, and its length is the coordinator's recovery time.

Measured numbers (modelled): what a blocked coordinator costs

While cohorts are in doubt they hold the transaction's locks. Every other transaction that needs those rows waits too.

Beyond the book: the standard fixes
  • Replicate the coordinator's log. If the decision record is written through consensus (a Paxos/Raft group), a new coordinator can read it: no blocking as long as a majority survives. Gray & Lamport's Paxos Commit [GRAY04] does this and notes that with no fault tolerance (F = 0) it reduces to classic 2PC. Spanner (section 9) and CockroachDB work this way.
  • Presumed abort. If the coordinator keeps no record of a transaction, the answer to "what happened?" is "abort". This saves log writes and messages for read-only and aborted transactions; [ALHOUMAILY10] surveys it and its sibling, presumed commit.
  • Operations. In PostgreSQL, a forgotten prepared transaction shows up in pg_prepared_xacts, holding locks and blocking VACUUM from cleaning old rows until someone commits or rolls it back by hand.

06 · THREE-PHASE COMMIT

3PC: add a "get ready" round and timeouts on both sides

pdf p414–415 · Fig 13-5

To make atomic commitment robust against coordinator failure and avoid undecided states, three-phase commit (3PC) adds one extra step plus timeouts on both sides, so cohorts can go on to commit or abort if the coordinator fails, depending on how far the protocol got. 3PC assumes a synchronous model and that communication failures can't happen [BABAOGLU93].

The new prepare step sits before commit/abort. It tells cohorts the vote result the coordinator gathered during propose, so the protocol can continue even if the coordinator dies. Everything else (including needing a coordinator for the round) is like 2PC. The cohort-side timeout forces a decision, and which decision depends on the step the cohort is in.

  • Propose: the coordinator sends the proposed value and collects votes. If the coordinator crashes here and the operation times out, or a cohort votes no, the transaction aborts.
  • Prepare: the coordinator announces the vote result. If all voted to commit, it sends Prepare ("get ready to commit"); otherwise Abort, and the round ends. If it can't deliver every Prepare or doesn't get every acknowledgment, cohorts may abort after a timeout, since the protocol never reached the prepared state everywhere.
  • Once all cohorts are prepared and the coordinator has all their acks, the transaction will commit even if either side fails: everyone now has the same view of the state.
  • Commit: the coordinator tells everyone the result of the prepare phase, which resets their timeout counters and finishes the transaction.
Picture it

A rocket launch. "Go / no-go poll" is propose. "All stations, we are go: arm the systems" is prepare. "Launch" is commit. If mission control goes silent during the poll, everyone stands down. If it goes silent after every station has confirmed "armed", every station knows every other station is armed too, so the countdown finishes on its own.

Step through 3PC (Figure 13-5, rebuilt)

What's happening behind it

2PC blocks because a cohort in the prepared state can't tell "nobody committed yet" from "someone already committed". 3PC adds a state between them so that two facts hold: (1) no cohort commits until every cohort is prepared, and (2) no cohort is ever "voted yes" while another has already committed. Then a cohort's own state is enough to pick a safe timeout action: still in "voted" → nobody can have committed → abort; in "prepared" → everyone voted yes → commit. The price is one more round trip, and the proof leans on timeouts meaning "the other side is dead", which is only true in a synchronous network.

// 3PC cohort timeout rule (the book's description)
function onTimeout(tx: Tx) {
  switch (tx.state) {
    case 'voted':    return abort(tx);   // never reached prepared: nobody can have committed
    case 'prepared': return commit(tx);  // everyone voted yes and knows it
    default:         return;             // already committed or aborted
  }
}

07 · COORDINATOR FAILURES IN 3PC

Non-blocking, until the network splits

pdf p416 · Fig 13-6

Every state change is coordinated: cohorts can't move to the next phase until everyone has finished the previous one, and the coordinator has to wait for the replicas. Cohorts that hear nothing before the timeout can abort, as long as they hadn't moved past the prepare phase.

2PC can't recover from coordinator failure, and cohorts may be stuck in a non-deterministic state until it returns. 3PC avoids that block and lets cohorts reach a deterministic decision.

Its worst case is a network partition (Figure 13-6). Some nodes reach the prepared state and will commit after the timeout. Others can't reach the coordinator and will abort after the timeout. The result is split brain: some commit, some abort, each following the protocol, leaving the participants inconsistent and contradicting each other.

So 3PC solves 2PC's blocking only partly, sends more messages, can produce contradictions and handles partitions badly. Petrov suggests this is probably the main reason it is rarely used in practice.

Picture it

Mission control sends "arm" and the radio link to two of the four stations is cut mid-sentence. The two that heard "arm" count down and launch on timeout. The two that didn't hear it stand down on timeout. Each did exactly what the manual says, and the rocket leaves with half its boosters.

Try it: which cohorts got Prepare before the partition?

What's happening behind it

The timeout rule turns "I heard nothing" into "the others must be in my state". In a partition that's false: a cohort that heard Prepare assumes everyone is prepared, and a cohort that didn't assumes nobody is. The full protocol in [SKEEN83] adds a termination step where surviving cohorts compare states, but cohorts on opposite sides of a partition can't compare. No timeout-based rule can tell a slow node from a dead one in an asynchronous network, which is why real systems moved to majority-based consensus (Chapter 14): a minority side simply can't decide anything.

08 · DISTRIBUTED TRANSACTIONS WITH CALVIN

Calvin: agree on the order first, then everyone runs the same script

pdf p417–419 · Fig 13-7

Another way to cut contention and shorten how long transactions hold locks: let replicas agree on the execution order and the transaction boundaries before taking any locks. If that works, a node failure no longer aborts transactions, because the other participants run the same transaction in parallel and the failed node can recover state from them.

Traditional systems use two-phase locking or optimistic concurrency control, which have no deterministic order, so nodes must coordinate to keep order. A deterministic order removes coordination from the execution phase: every replica gets the same inputs, so every replica produces the same outputs. This approach is known as Calvin [THOMSON12]; FaunaDB is a prominent implementation.

  • Sequencer: the entry point for all transactions. It fixes the order and builds a global transaction input sequence. Time is cut into epochs: the sequencer groups transactions into short windows (the paper uses 10 ms batches), and each batch is also the unit of replication, so transactions aren't shipped one by one.
  • Once a batch is replicated, the sequencer passes it to the scheduler, which runs parts of transactions in parallel while keeping the serial order the sequencer chose. Applying a transaction to a given state can only produce that transaction's changes, and the order is fixed, so replicas don't need to talk to the sequencer again.
  • Each transaction has a read set (the records it depends on) and a write set (its effects). Calvin does not natively support transactions that need extra reads to discover their read and write sets.

A worker thread, managed by the scheduler, runs four steps:

  1. Analyse the read and write sets: find which read-set records are local, and list the active participants (the nodes holding write-set records, which will modify data).
  2. Read the local part of the read set and forward those records to the active participants.
  3. If this node is an active participant, receive the records the other nodes forwarded in step 2.
  4. Execute the batch and persist results locally. No results are forwarded: the other nodes got the same inputs and compute and persist the same results themselves.

A typical deployment colocates sequencer, scheduler, workers and storage on each partition (Figure 13-7). To agree on exactly which transactions go into an epoch, sequencers use Paxos or asynchronous replication with a dedicated leader replica. A leader lowers latency but makes recovery more expensive, since nodes must reproduce the failed leader's state before continuing.

Picture it

An orchestra spread over three cities, playing together over video. Instead of conductors phoning each other before every bar ("are you ready? may I play?"), they all agree on the score in advance and press play at the same moment. Each city produces the same music without talking. If one city's player faints, the music in the other cities is unaffected, and the player can catch up from the score.

What's happening behind it

In 2PL, the order between two conflicting transactions is decided at run time by whoever grabs the lock first, which can differ between replicas, so replicas must coordinate (2PC) to end up the same. Calvin moves the decision to before execution: the sequencer's log is the serial order, and each scheduler grants locks strictly in that order. Execution can't diverge, so there's nothing to vote on at the end; a node that crashes just replays the input log. The cost: a transaction waits for its epoch to close and be replicated, and it must declare its read/write sets up front. (The Calvin paper handles "dependent" transactions with a reconnaissance read and a retry if the sets changed (not in the book).)

// deterministic lock scheduler: grant locks strictly in sequence order
function schedule(batch: Tx[], locks: LockTable) {
  for (const tx of batch)                         // batch is already in global order
    for (const key of [...tx.readSet, ...tx.writeSet].filter(isLocal))
      locks.enqueue(key, tx);                     // FIFO per key = sequencer order
  // a tx runs when it is at the head of every local queue it joined;
  // non-conflicting txs run in parallel, conflicting ones in sequencer order
}

09 · DISTRIBUTED TRANSACTIONS WITH SPANNER

Spanner: 2PC between Paxos groups, ordered by TrueTime

pdf p420–422 · Fig 13-8

Spanner [CORBETT12] is often contrasted with Calvin. Open-source implementations or derivatives include CockroachDB and YugaByte DB. Calvin gets a global order by reaching consensus on sequencers; Spanner runs two-phase commit over consensus groups, one per partition (shard). The setup is complex; the book covers only the high level.

To order transactions consistently Spanner uses TrueTime: a high-precision wall-clock API that also reports an uncertainty bound, so local operations can add artificial delays until that uncertainty has passed.

OperationLocks?Where it can run
Read-write transactionyes: pessimistic concurrency controlneeds the leader replica
Read-only transactionlock-freeany replica; the leader is needed only to read at the latest timestamp (the latest committed value in the Paxos group)
Snapshot readlock-freeany up-to-date replica; consistent because versions are immutable once written

Every record carries a timestamp equal to its transaction's commit time, so several timestamped versions of a record can exist. Architecture (Figure 13-8): each spanserver (a replica serving data) holds several tablets, each with a Paxos state machine attached. Replicas form Paxos groups, the unit of placement and replication, each with a long-lived leader (Multi-Paxos). Leaders talk to each other during multishard transactions.

Writes go through the group leader; reads can be served from the tablet on any up-to-date replica. The leader keeps a lock table (two-phase locking) and a transaction manager for multishard transactions. Operations needing synchronization (writes, reads inside a transaction) take locks from the lock table; snapshot reads go straight to the data.

For multishard transactions, group leaders run 2PC for consistency and 2PL for isolation. 2PC needs every participant, which hurts availability; Spanner fixes this by making the cohorts Paxos groups, so 2PC continues even when some group members are down. Inside a group, 2PC talks only to the leader. Paxos groups also replicate the transaction manager's state.

  1. Each participant leader takes its write locks, picks a prepare timestamp larger than any earlier transaction's, and logs a 2PC prepare record through Paxos.
  2. The coordinator collects these and picks a commit timestamp greater than every prepare timestamp, and logs a commit record through Paxos.
  3. It then waits until the chosen timestamp is in the past (clients may only see results whose timestamps are past).
  4. It sends the timestamp to the client and the leaders, which log the commit record with that timestamp in their own Paxos groups and then release the locks.

Single-shard transactions skip the transaction manager and cross-partition 2PC: the Paxos group plus the lock table already order and protect them.

Read-write transactions get external consistency: timestamps reflect the serialization order even for distributed transactions, with real-time properties equivalent to linearizability. If T1 commits before T2 starts, T1's timestamp is smaller than T2's.

In short: Paxos for consistent log replication, 2PC for cross-shard transactions, TrueTime for deterministic ordering. Multipartition transactions therefore cost more than in Calvin because of the extra 2PC round [ABADI17]. Both designs matter because both make transactions possible on partitioned data.

Picture it

Each shard is a committee (Paxos group) with a chair (leader). For a cross-committee decision, only the chairs negotiate (2PC), but each chair writes every promise into the committee's minutes (Paxos log), so if a chair faints, the vice-chair reads the minutes and carries on. TrueTime is a wristwatch that says "it's 10:00:00, give or take 4 ms"; to be sure a stamped decision is really in the past, you wait out the "give or take".

Try it: commit wait with an uncertain clock

TT.now() returns an interval [earliest, latest] guaranteed to contain true time, of width 2ε. The coordinator picks commit timestamp s = TT.now().latest and waits until TT.now().earliest > s. Paxos logging of the commit record runs at the same time (overlap: from the Spanner paper, not in the book).

Step through a multishard commit

What's happening behind it

Why the wait gives external consistency: the commit timestamp s is at least TT.now().latest when chosen, and results are released only once TT.now().earliest > s, so at release, true time is past s. Any transaction T2 that starts after that release picks its own timestamp from a later TT.now().latest, which is beyond true time, which is beyond s. So "commits before starts" implies "smaller timestamp" without any message between T1 and T2. The wait is about 2ε, which is why Google spends on GPS and atomic clocks to keep ε small. Making 2PC participants Paxos groups turns "a node failed" from "transaction blocked" into "a new leader reads the prepare record from the group's log and continues".

// commit wait (from the Spanner paper's description)
const s = Math.max(maxPrepareTs, TT.now().latest);   // commit timestamp
paxosLog(commitRecord(s));                             // runs in parallel with the wait
while (!(TT.now().earliest > s)) await tick();         // TT.after(s)
reply(client, s); notifyParticipants(s);               // participants log commit, release locks

10 · DATABASE PARTITIONING

Splitting data: ranges, hot spots, and why hash mod N hurts

pdf p423–424

Keeping every record on one node is unrealistic for most modern applications, so databases partition: they divide data logically into smaller, manageable segments.

  • Range partitioning: split the key space into ranges and let each replica set manage specific ranges. Clients (or query coordinators) route each read and write by the routing key to the right replica set. This scheme is usually called sharding: each replica set is the single source for its subset.
  • Size by load and density. Frequently accessed, read/write-heavy ranges can be split smaller to spread the load; ranges that hold more values than others can also be split. Petrov's example: with zip code as the routing key, population is uneven, so some zip ranges carry far more people and orders.
  • Rebalancing. When nodes join or leave, data must be re-partitioned. For consistent moves, relocate the data first, then update cluster metadata and start routing to the new targets. Some databases auto-shard, using placement algorithms that look at read load, write load and data volume per shard.
  • Hash partitioning. Hash the routing key and map the hash to a node ID. Hash values don't sort like the keys, so two lexicographically close keys land on different replica sets instead of the same one: less range hot-spotting.
  • hash(v) mod N is the simplest mapping. Its problem: when the cluster size changes from N to N′, most values of hash(v) mod N′ differ from the old ones, so most of the data has to move.
Picture it

Shelving library books by the first letter of the author: the "S" shelf overflows while "X" is nearly empty, so you give "S" three shelves (split hot ranges). Shelving by a scrambled code number spreads books evenly, but now finding "all authors from Sa to Sm" means visiting every shelf. And if you number shelves by "code mod 8" and buy a ninth shelf, almost every book changes shelf.

What's happening behind it

A key stays put under mod only if h mod N = h mod N′. Going from N to N + 1, that holds for about 1 in N + 1 keys, so a fraction N/(N + 1) moves: 89% for 8 → 9, 97% for 32 → 33 (derivation not in the book). Yet the ideal is to move only the 1/(N + 1) share the new node should own. Range partitioning has the opposite profile: moving a boundary moves only the keys between the old and new boundary, but sequential or skewed keys pile onto one range unless it's split.

Beyond the book: who does what
  • Range sharding with automatic splits by size and load: HBase regions, Bigtable tablets, CockroachDB ranges, TiKV regions, MongoDB ranged shard keys.
  • Hash sharding: MongoDB hashed shard keys, Redis Cluster (CRC16 of the key mod 16,384 fixed slots, and slots, not keys, move between nodes), YugabyteDB's default.
  • The fixed-slot trick (many more slots than nodes, move whole slots) is another way around the mod-N problem.

11 · CONSISTENT HASHING

Consistent hashing: put nodes on a ring, move only the neighbours' keys

pdf p425

To avoid the mass migration of mod N, databases such as Apache Cassandra and Riak use consistent hashing. Keys are hashed as before, but hash values are placed on a ring: after the largest value it wraps to the smallest. Each node takes a position on the ring and owns the range between its predecessor's position and its own.

A change to the ring affects only the immediate neighbours of the node joining or leaving, not the whole cluster. "Consistent" means that when the table is resized, with K possible keys and n nodes, on average only K/n keys move: the function's output changes as little as possible when its range changes [KARGER97].

Picture it

A round table with name cards at a few seats. Every guest sits at the first name card clockwise from where they happen to stand. Put down a new name card and only the guests standing just before it switch seats; everyone else stays where they were.

Try it: add and remove nodes on the ring

What's happening behind it

Ownership is "first node position clockwise from the key's hash", found with a binary search over the sorted node positions. A new node at position q takes only keys between its predecessor and q, all from one existing node; a removed node hands its keys to its successor. With one position per node, ranges are uneven (random gaps), so loads differ a lot; give each node many positions (virtual nodes, not in the book) and each node's load is a sum of many small random arcs, which evens out. Turn the slider up and watch max/mean load fall.

class Ring {
  private pos: number[] = []; private owner = new Map<number, string>();
  add(node: string, vnodes = 1) {
    for (let v = 0; v < vnodes; v++) { const h = hash32(node + '#' + v); this.pos.push(h); this.owner.set(h, node); }
    this.pos.sort((a, b) => a - b);
  }
  lookup(key: string): string {               // first position clockwise (>= h), wrapping around
    const h = hash32(key); let lo = 0, hi = this.pos.length;
    while (lo < hi) { const m = (lo + hi) >> 1; this.pos[m] < h ? lo = m + 1 : hi = m; }
    return this.owner.get(this.pos[lo % this.pos.length])!;
  }
}
Beyond the book: in production
  • Amazon's Dynamo paper (DeCandia et al., SOSP 2007) popularised consistent hashing with virtual nodes for a database, also using the ring to pick the N replicas of each key (the next N distinct nodes clockwise).
  • Cassandra calls positions tokens; num_tokens set the vnodes per node (256 in older releases; Cassandra 4.0 lowered the default to 16 together with a token-allocation algorithm that keeps balance with fewer tokens).

12 · DISTRIBUTED TRANSACTIONS WITH PERCOLATOR

Snapshot isolation, and Percolator's 2PC built on Bigtable

pdf p426–429 · Fig 13-9

Isolation levels are hard to reason about because of the read and write anomalies they allow. If an application doesn't need serializability, one way to avoid the write anomalies described in SQL-92 is snapshot isolation (SI).

  • All reads in a transaction see one snapshot: every value committed before the transaction's start timestamp.
  • If two concurrent transactions write the same cell (a write-write conflict), only one commits: first committer wins.
  • SI prevents read skew, which read committed allows. Petrov's example: x + y must be 100; T1 reads x; T2 rewrites both x and y and commits; T1 then reads the new y, and its old x with the new y don't add up. Under SI, T1 never sees T2's y [BERENSON95].
  • Useful properties: only repeatable reads of committed data; values consistent because they come from one timestamp; conflicting writes aborted and retried.
  • But SI histories are not serializable: only writes to the same cells conflict, so write skew is still possible. Two transactions modify disjoint values, each keeping the invariant for what it writes; both commit; together they break it.
  • SI's big advantage is efficient reads: no locks, because snapshot data can't change.

Try it: read skew under read committed vs snapshot isolation

My numbers (the book uses different ones): invariant x + y = 100, start x = 60, y = 40. T2 moves 30 from x to y.

Try it: write skew still gets through SI

My example: one customer's two accounts, a = 50 and b = 50; the bank's rule is a + b ≥ 0. T1 withdraws from a, T2 from b, each checking the rule against its own snapshot. They write different rows, so SI sees no conflict.

Percolator is a library that adds a transactional API on top of Bigtable, a good example of building transactions on an existing system. It keeps data, write metadata (where the committed data points are) and locks in different columns. To lock reliably without races in a single RPC, it uses Bigtable's conditional mutation API (read-modify-write in one remote call). Each transaction asks the timestamp oracle (a cluster-wide source of monotonically increasing timestamps) twice: for its start timestamp and at commit. Writes are buffered and committed with a client-driven two-phase commit.

  • (a) Initial state: the latest write record for each account points to its last committed data; no locks.
  • (b) Prewrite (phase 1): lock every cell the transaction writes; one lock is the primary, used for client recovery. Check for conflicts: any write by another transaction with a later timestamp, or any unreleased lock at any timestamp, aborts the transaction.
  • (c) Commit (phase 2): if all locks were taken and no conflict is possible, release the locks starting with the primary, publishing each write by replacing the lock with a write record that points to the new data.
  • Client failure: a later transaction that runs into an incomplete state should try to resolve it through the primary lock; if the primary lock was already released, the transaction's contents must be committed. One lock holder at a time plus atomic state changes mean two transactions can't operate on the same contents at once.

Step through a Percolator transaction (my own accounts and numbers)

Move ₹40 from Ravi (90) to Asha (60). Last commit: data at ts 5, write record at ts 6. The new transaction gets start ts 7 and commit ts 8.

Picture it

A shared ledger where you can only change one line at a time. To move money you first pencil in both new balances and put a sticky note on each ("busy, see Asha's note"). Asha's note is the master. Committing is peeling the master note and writing "valid from 8" in ink; that single action is the moment of truth. If you faint after that, the next person who finds the leftover note on Ravi's line follows it to Asha's line, sees the ink, and finishes the job for you.

What's happening behind it

Bigtable only gives atomic changes to a single row. Percolator gets multi-row atomicity by making one row's change (the primary's lock → write record) the commit point, and making every other row's state point at the primary. Anyone who finds a stray secondary lock can read the primary and learn the outcome. The book's wording is that the later transaction tries to release the primary lock and commit; in the Percolator paper itself, the cleaner rolls back if the primary lock is still there (after checking the owner is presumed dead) and rolls forward if the primary was already replaced by a write record (detail from the paper, not the book). The step-through follows the paper.

// Percolator, client side (sketch after the paper)
async function commit(tx: { start: number; writes: Write[] }) {
  const [primary, ...secondaries] = tx.writes;
  for (const w of tx.writes)                         // phase 1: prewrite (one conditional mutation per row)
    if (!await prewrite(w, primary, tx.start)) return abort(tx);   // later write or any lock = conflict
  const commitTs = await oracle.next();              // second oracle call
  if (!await commitPrimary(primary, tx.start, commitTs)) return abort(tx); // the commit point
  for (const w of secondaries) await commitSecondary(w, tx.start, commitTs); // may be done lazily by others
}
// prewrite(row): if write@[start, ∞) exists or lock@any exists -> fail; else lock@start, data@start

13 · COORDINATION AVOIDANCE

Skip coordination when merging can't break the rules: I-confluence and RAMP

pdf p430–432

Coordination avoidance [BAILIS14b] tries to cut the cost of serializability while keeping strong guarantees. Coordination can be skipped, with integrity constraints still kept, when operations are invariant confluent (I-confluent): any two invariant-valid but diverged database states can be merged into one valid final state. The invariants here mean consistency in the ACID sense. Since any two valid states merge into a valid state, I-confluent operations need no extra coordination, which greatly improves performance and scalability.

Besides the operation that moves the database to a new state, you define a merge function that takes two states and brings independently updated states back together. Transactions run against local versions (snapshots); any state needed from other partitions is made available locally. When a transaction commits, its changes to the local snapshot migrate to the other nodes and merge with their snapshots. A system that allows coordination avoidance must guarantee:

  • Global validity: required invariants always hold, for merged and diverged committed states, and transactions never see invalid states.
  • Availability: if the client can reach all nodes holding the state, the transaction reaches a commit decision, or aborts if committing would break an invariant.
  • Convergence: nodes keep local states independently, but with no further transactions and no indefinite partitions they must reach the same state.
  • Coordination freedom: local execution doesn't depend on operations other nodes run against their local states.

Try it: is this operation I-confluent for this invariant?

RAMP (Read-Atomic Multi-Partition) transactions [BAILIS14c] implement coordination avoidance. RAMP uses multiversion concurrency control plus metadata about in-flight operations to fetch missing updates from other nodes, so reads and writes can run concurrently. A reader that overlaps a writer of the same entry can be detected and, if needed, repaired by getting the missing information from the in-flight write's metadata in one extra round of communication. Instead of distributed locks, RAMP provides:

  • Synchronization independence: one client's transactions never stall, abort or make another client's transactions wait.
  • Partition independence: clients don't contact partitions whose values their transactions don't involve.

RAMP introduces the read atomic isolation level: transactions can't see in-progress changes from in-flight, uncommitted or aborted transactions; a transaction's updates are visible all together or not at all. That also rules out fractured reads (seeing only some of another transaction's writes). RAMP gets atomic visibility without mutual exclusion, which distributed locks usually bundle together, so transactions don't stall each other. Metadata lets transactions detect newer versions, fetch the latest and work on them. To avoid coordination, every local commit decision must also be valid globally: by the time a write is visible in one partition, the same transaction's writes on all other involved partitions are visible to readers there too.

Writes are installed with two-phase commit: prepare places writes on their partitions without making them visible; commit/abort publishes them atomically across all partitions or rolls back. Several versions of a record can coexist: the latest value, in-flight uncommitted changes, and stale versions overwritten by later transactions. Stale versions are kept only for in-progress reads and dropped once those readers finish.

Distributed transactions are hard to make fast because of the coordination needed to prevent, detect and avoid conflicts, and the bigger the system or the load, the bigger that overhead. These approaches use invariants to find where coordination can be skipped and pay the full price only when it's really needed.

Step through a fractured read and RAMP's repair

Writer T1 sets x = 1 and y = 1 (both were 0) on partitions X and Y. A reader reads x and y while T1 is half-published.

Picture it

Two friends update their shared holiday plan: one changes the hotel, the other the flight, and the two edits belong together. Someone glancing at the hotel page sees "new hotel, booked together with flight v2", checks the flight page, sees it still shows v1, and asks for v2 directly instead of waiting for anyone. Nobody blocked; the reader fixed its own view.

What's happening behind it

I-confluence asks one question: if two replicas each make a change that's valid on its own, is the merge always valid? Deposits merge by adding, and adding non-negative amounts keeps a balance ≥ 0. Withdrawals don't: each may be fine alone while the sum overdraws. Uniqueness fails if ids are chosen freely, and holds if each replica draws from its own id space. When the answer is yes, no coordination is needed at all; when it's no, only those operations need it. RAMP's metadata is the list of sibling keys each write belongs to (plus the transaction timestamp); a reader that sees a write from T1 on one partition knows exactly which version of the other keys it must also see, and fetches them by timestamp, which works because prepared versions are already stored.

Beyond the book: measured numbers

  • RAMP (SIGMOD 2014): scales linearly to 100 servers; the authors' summary reports over 7 million operations per second on 100 servers for a 95%-read workload, with under 5% overhead versus no isolation (figures from Bailis's blog summary; the paper's abstract states linear scaling and limited overhead). RAMP-Fast reads take one round trip when there is no racing writer and two when there is.
  • Facebook later layered RAMP-style atomic visibility on its TAO store (RAMP-TAO, VLDB 2021).

14 · SUMMARY + FURTHER READING

Atomic commit is simple but fragile; consensus is the way forward

pdf p433–434

The chapter covered several ways to implement distributed transactions. 2PC and 3PC are easy to understand and implement, but have shortcomings. In 2PC the coordinator (or a substitute) must be alive for the whole commitment, which significantly reduces availability. 3PC lifts that requirement in some cases but is prone to split brain under a network partition.

Modern databases often implement distributed transactions with consensus algorithms (next chapter): Calvin and Spanner both use Paxos. Consensus algorithms are more involved than atomic commitment, but they tolerate faults much better, decouple decisions from their initiators, and let participants decide on a value rather than on whether to accept a value [GRAY04].

Check yourself

answer before you open
1. Why can't single-partition concurrency control (2PL, OCC) on its own make a cross-shard transfer atomic?

Each partition can only decide for itself. Nothing stops partition A from committing its half while partition B aborts or crashes. You need a distributed commit and rollback protocol that makes all partitions reach the same outcome (sections 1–2).

2. In 2PC, what exactly does a cohort promise when it votes yes, and what must it do before sending the vote?

That it will not abort on its own; only the coordinator may abort. Before voting it must execute its part and make it durable (force a "prepared" record), so it can keep the promise even after a crash (sections 3–4).

3. A cohort crashes before voting. A different cohort crashes after voting yes. What does each do on recovery?

The first has no prepared record, so it rolls back its part (the coordinator will have aborted after a timeout). The second is in doubt: it must keep locks and not serve those rows until it learns the coordinator's decision (section 4).

4. Why is it safe for an in-doubt cohort to copy a "commit" decision from a peer?

2PC decisions are unanimous: a cohort can only have committed if the coordinator decided commit, and then every cohort must commit. Copying a decision can never contradict it (section 5).

5. Why is 2PC called blocking? Describe the exact failure.

If the coordinator fails after collecting votes and before telling anyone the result, all cohorts are prepared and none knows the outcome. Guessing could contradict a decision the coordinator logged or sent to an unreachable node, so they must wait, holding locks, until it (or a replacement that re-collects the votes) returns (section 5).

6. What does 3PC's extra phase buy, and what does a cohort do on timeout in each state?

It guarantees no one commits until everyone is prepared, so a cohort's own state tells it what is safe: timeout while only "voted" → abort; timeout while "prepared" → commit (section 6).

7. Why does 3PC's fix fail under a network partition, and why doesn't 2PC have that failure?

Cohorts that received Prepare commit on timeout; cohorts cut off before it abort on timeout: split brain. 3PC's safety depends on timeouts meaning "dead", which a partition breaks. 2PC never decides by timeout after a yes vote; it blocks instead, staying consistent (section 7).

8. Calvin avoids a commit protocol at the end of each transaction. What does it pay instead?

Transactions wait for their epoch (about 10 ms in the paper) to close and be replicated through Paxos or a leader before running, and they must declare read and write sets up front; transactions whose sets depend on reads aren't natively supported (section 8).

9. In Calvin's worker steps, which nodes execute the write logic, and why don't they send results to each other?

The active participants: nodes holding write-set records. Passive nodes only forward their local reads. Results aren't forwarded because each active node gets the same inputs and executes deterministically, so it computes the same results itself (section 8).

10. Why does Spanner's coordinator wait after choosing a commit timestamp, and roughly how long?

So that when results are released, the timestamp is certainly in the past by TrueTime's bounds. Any later transaction then gets a larger timestamp: external consistency. The wait is about 2ε (a few ms with ε ≈ 4 ms in the paper), mostly overlapped with Paxos logging (section 9).

11. How does Spanner keep 2PC available when a cohort's leader dies?

Each cohort is a Paxos group whose leader logs prepare and commit records through Paxos. A new leader reads the group's log and continues, so 2PC only stalls if a group loses its majority (sections 4, 9).

12. A cluster grows from 10 to 11 nodes. Roughly what share of keys move under hash mod N, and under consistent hashing?

mod N: about 10/11 ≈ 91%. Consistent hashing: about 1/11 ≈ 9%, all taken from the new node's ring neighbour(s) (sections 10–11).

13. Snapshot isolation prevents read skew. Give the reason, and say what it still allows.

All reads come from one snapshot at the start timestamp, so a value committed later (like T2's new y) is invisible. It still allows write skew: two transactions writing different rows, each valid on its own snapshot, together break an invariant (section 12).

14. In Percolator, what is the commit point, and how does a later transaction clean up after a crashed client?

Replacing the primary lock with a write record. A later transaction that finds a leftover secondary lock checks the primary: if it was committed, it rolls the secondary forward; if the primary lock is still there (and its owner is dead), the paper rolls back (section 12).

15. Which is I-confluent under "balance ≥ 0": deposits or withdrawals? What does RAMP's metadata let a reader do?

Deposits (merged sums of non-negative changes stay ≥ 0); withdrawals aren't, since two valid withdrawals can overdraw together. RAMP's per-write list of sibling keys and timestamp lets a reader spot a fractured read and fetch the missing version in one more round, without locks (section 13).
