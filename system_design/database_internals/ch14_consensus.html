01 · CHAPTER OPENING

What "agreeing" has to mean

pdf p435–436

The previous chapters gave us the parts: links and processes, failure models, failure detectors, leader election, consistency models. Consensus puts them together. A consensus algorithm lets several processes agree on one value. The catch is the FLP impossibility result (Chapter 8): in a completely asynchronous system you can't guarantee consensus in bounded time, because even with guaranteed delivery a process can't tell whether another process has crashed or is just slow.

Chapter 9 showed the trade-off between how accurate a failure detector is and how fast it detects. Consensus algorithms work around FLP by splitting the job: the algorithm assumes an asynchronous model and guarantees safety on its own, while an external failure detector supplies information about other processes and so provides liveness [CHANDRA96]. Because detectors are not perfectly accurate, sometimes the algorithm waits for a crash to be detected, and sometimes it restarts because a healthy process was wrongly suspected.

Processes must agree on a value proposed by one of them, even if some crash. A process is correct if it hasn't crashed and keeps executing the algorithm's steps. Consensus is very useful for putting events in an order and keeping participants consistent: processes can move from one value to the next without losing certainty about what clients observed. Formally, three properties:

  • Agreement: every correct process decides the same value. This is the everyday meaning (the dictionary definition says "unanimity"): once agreed, nobody may hold a different outcome. Like friends agreeing on a meeting place: everyone wants to meet; only the details are being settled.
  • Validity: the decided value was proposed by one of the processes. Without it consensus is trivial: everybody could output a fixed default value and be "unanimous" without being useful.
  • Termination: every correct process eventually decides. Without it the algorithm could run forever or wait forever for a crashed process to return. To be practical, the decision should also come quickly.
Picture it

Five friends texting to pick a restaurant. Agreement: nobody shows up at a different place. Validity: the place is one somebody actually suggested, not "the default restaurant" nobody asked for. Termination: you don't stay in the group chat forever because one friend's phone died.

Break the properties yourself: five toy "consensus" rules

What's happening behind it

Each rule is run against five processes P1–P5 with random proposals; the crashed ones (counted from P5 down) stop sending. "Decide 0" always terminates and always agrees but breaks validity whenever nobody proposed 0. "Decide my own" is valid and terminates but disagrees. "Wait for everyone" is valid and agrees, but one crash blocks it forever: termination fails. "Any majority, then minimum" terminates with up to 2 crashes, yet two processes can hear from different majorities and pick different minimums. Only the quorum protocol gets all three, and only while a majority (3 of 5) is alive. With 3 or more crashed it can't terminate, which is the price of never deciding wrongly. Even then, FLP says that in a truly asynchronous network an unlucky schedule could postpone the decision indefinitely; real protocols escape with timeouts and randomisation (sections 9 and 17).

02 · BROADCAST

Telling everyone, even if the sender dies halfway

pdf p437–438 · Fig 14-1

A broadcast is a communication abstraction for spreading information to a set of processes. There are many broadcast algorithms with different assumptions and guarantees; broadcast is a primitive used in many places, consensus included. Gossip dissemination (Chapter 12) is one form. Databases use broadcast for replication when one coordinator must send data to all others. Making it reliable is hard: if the coordinator crashes after sending to some nodes but not others, the system is inconsistent (some nodes saw the message, some didn't).

The simplest form is best-effort broadcast [CACHIN11]: the sender alone is responsible for delivery to every target. If it fails, nobody re-sends; if the coordinator crashes, the broadcast fails silently. A reliable broadcast must guarantee that all correct processes receive the same messages, even if the sender crashes mid-way.

A naive reliable broadcast uses a failure detector plus a fallback: every process that received the message forwards it to every other process it knows. When the source fails, the others detect it and keep broadcasting, flooding the network with N² messages (Fig 14-1), where N is the number of remaining recipients (each forwarder skips the original sender and itself). Even with the sender crashed, the rest of the system delivers, and all receivers see the same messages. The downside is the N² message count; ideally we'd use fewer.

Crash the sender mid-broadcast

Picture it

A teacher starts phoning parents about a school closure and her phone dies after two calls. Best effort: the other parents never hear. Reliable: every parent who got the news phones every other parent. Everyone is told, but each parent gets the news several times.

Messages per broadcast as the group grows

What's happening behind it

With N processes, the sender sends N−1 copies. In eager flooding each of the N−1 receivers forwards to the N−2 processes that are neither the sender nor itself, so the total is (N−1) + (N−1)(N−2) = (N−1)²: the book's "N² with N = remaining recipients". At N = 7 that's 36 messages instead of 6, and at N = 100 it's 9,801 instead of 99. The "forward only after suspicion" variant pays the N² cost only when the sender is actually suspected, but it now depends on the failure detector's speed, and a wrong suspicion triggers a useless flood. Duplicates are discarded by message ID, so delivery happens once per process.

03 · ATOMIC BROADCAST
Same messages, same order, everywhere
pdf p439

  
Flooding guarantees delivery but not order: messages arrive eventually, at unknown times. When order matters you need atomic broadcast (also called total order multicast), which guarantees both reliable delivery and total order. Reliable broadcast makes processes agree on the set of messages; atomic broadcast also makes them agree on the sequence. Two properties:

  
    
    
  • Atomicity: processes agree on the set of received messages. Either all non-failed processes deliver a message, or none do.
    • 
    
  • Order: all non-failed processes deliver messages in the same order.
    • 
  

  
So each message is delivered to all or none, and every other delivered message is ordered either before or after it.

  

    
Two clients write at once: reliable vs atomic delivery

    

    

    

    

  

  
Picture it
Two people edit the same bank balance: one deposits 100, the other adds 10% interest. If replica A applies "deposit then interest" and replica B "interest then deposit", their balances differ forever, even though both got both messages. Atomic broadcast makes everyone apply the operations in one agreed order.

  
What's happening behind it
In the reliable mode every replica applies a message the moment it arrives, so the per-replica order follows random network delays; press the button a few times and you'll regularly see replicas with different balances. In the sequencer mode (which the book introduces in section 4), messages go to one process that stamps a sequence number; replicas hold back message #2 until #1 is applied. Every replica then shows the same balance, at the cost of one extra hop and a single process that must be replaced if it fails. Total order is exactly the problem consensus solves: deciding "what is message #k?" is one consensus instance per slot.

04 · VIRTUAL SYNCHRONY
Ordered delivery to a group whose membership changes
pdf p440–441

  
Virtual synchrony is a framework for group communication using broadcast. Atomic broadcast delivers totally ordered messages to a static group; virtual synchrony delivers them to a dynamic group of peers. Processes are organised into groups; while a group exists, its members get messages in the same order. The model doesn't say which order, and implementations can exploit that for performance as long as the order is the same for every member [BIRMAN10].

  
All members share the same view of the group, and each message is tied to the group identity: processes see the same messages only while they're in the same group. When someone joins, leaves, or fails and is forced out, the view changes, announced to all members. Each message is uniquely associated with the view it came from.

  
Virtual synchrony separates receipt (a member got the message) from delivery (all members got it). A message sent in one view can only be delivered in that same view, checked by comparing the current group with the message's group. Received messages wait in a queue until the process learns delivery succeeded. Unless every member received a message before the view change, no member may consider it delivered. So all messages are sent and delivered between view changes, which gives atomic delivery: the view acts as a barrier broadcasts can't cross.

  
Some total-order algorithms use a single sequencer process to decide the order. They're easier to implement but rely on detecting the leader's failure for liveness. A sequencer helps performance: no consensus round per message, just the sequencer's local view; and it can still scale by partitioning the requests. Despite being technically sound, virtual synchrony hasn't been broadly adopted in commercial end-user systems [BIRMAN06].

What's happening behind it
Each process keeps a pending queue tagged with the view number. A message moves from pending to delivered only when the process knows all current members have it. When a failure is detected, the survivors stop sending in the old view, make sure each survivor holds the same pending messages for that view (in classic implementations this is a "flush"; the word is not in the book), deliver them, and only then install the new view. A message from view 1 that arrives during view 2 is discarded: view 1 is closed.

05 · ZOOKEEPER ATOMIC BROADCAST (ZAB)
One leader per epoch, three phases
pdf p442–444 · Fig 14-2

  
One of the most popular atomic broadcast implementations is ZAB, used by Apache ZooKeeper [HUNT10][JUNQUEIRA11], a hierarchical distributed key-value store. ZAB gives the total order and atomic delivery needed to keep replica states consistent.

  
Processes are either leader or follower. Leadership is temporary: the leader runs the algorithm's steps, broadcasts to followers and sets the event order. Clients connect to any node to write or to read the most recent values; a non-leader forwards the request to the leader.

  
To guarantee a unique leader, time is split into epochs, each with a unique, monotonically and incrementally sequenced number; each epoch has at most one leader. It starts with finding a prospective leader with any election algorithm that picks a process that's up with high probability. Since later steps guarantee safety, choosing the prospective leader is just a performance optimisation. A prospective leader can also appear because the previous one failed. It then runs three phases:

  
    
    
  • Discovery: the prospective leader learns the latest epoch each process knows and proposes a new epoch greater than any follower's. Followers reply with the ID of the latest transaction they saw in the previous epoch. After this, no process accepts broadcast proposals from earlier epochs.
    • 
    
  • Synchronization: recover from the previous leader's failure and bring lagging followers up to date. The prospective leader proposes itself as leader for the new epoch and collects acknowledgments; once it has them, it is established, and followers won't accept leadership attempts from anyone else for that epoch. The new leader makes sure followers have the same history and delivers committed proposals from earlier epochs' leaders before any new-epoch proposal.
    • 
    
  • Broadcast: active messaging. The leader receives client messages, orders them, and broadcasts: send a proposal, wait for a quorum of follower acknowledgments, then commit. It's like two-phase commit without aborts: votes are only acknowledgments, and a follower can't vote against a valid leader's proposal, though proposals from leaders of the wrong epoch must not be acknowledged. This phase lasts until the leader crashes, is partitioned, or is suspected to have crashed because of message delay.
    • 
  

  
Safety holds if followers accept proposals only from the established epoch's leader. Two processes may try to get elected, but only one can win the epoch. Processes are assumed to act in good faith. Leader and followers both use heartbeats: if the leader stops hearing from a quorum of followers it steps down and restarts election; if a follower decides the leader crashed it starts a new election.

  
Messages are totally ordered, and the leader won't send the next message until the previous one is acknowledged. Duplicate receipt is harmless if delivery order is respected. ZAB handles many concurrent client state changes since one leader receives the writes, orders them and broadcasts them. Total order also speeds recovery: in synchronization, followers report their highest committed proposal, and the leader can pick the node with the highest one as the only node to copy from. ZAB's advantages: broadcast takes only two rounds of messages, leader failure is recovered by streaming missing messages from one up-to-date process, and a long-lived leader can sequence events from its local view without extra consensus rounds.

step 0

  

  
Picture it
A ship changing captains. First the new captain asks every officer "what's the latest voyage you served on, and the last order you logged?" and declares voyage 2 (discovery). Then she copies the most complete logbook and makes every officer's logbook match it before giving any new order (synchronization). Only then does she give orders: each one is read out, acknowledged by most officers, then marked done (broadcast). Orders from the old captain's voyage are ignored.

  
What's happening behind it
Each transaction ID is a pair (epoch, counter); ZooKeeper calls it a zxid (the name isn't in the book). Comparing pairs, a higher epoch always wins, so "newest history" is just the follower with the largest zxid. That's why recovery can copy from a single node. Followers remember the highest epoch they acknowledged and reject anything older: this is the fence that stops a deposed leader. In the broadcast phase each write costs PROPOSE → ACK from a quorum → COMMIT: two message rounds, and the commit can be piggybacked on the next proposal.

  
Before: plain primary-backup
A primary pushes updates; if it dies with some backups ahead of others, there's no rule for whose history wins, and an old primary that comes back can still push stale writes.
After: ZAB
Epoch numbers fence old leaders, the new leader adopts the most complete history before accepting writes, and each write needs only a quorum ACK. Cost per write: 2 message rounds; recovery: stream from one node.

06 · PAXOS
Proposers, acceptors, learners, and numbers that never repeat
pdf p445–446

  
Atomic broadcast is equivalent to consensus in an asynchronous system with crash failures [CHANDRA96]: participants must agree on the message order and be able to learn it. So the two families look alike in motivation and implementation.

  
The best-known consensus algorithm is Paxos, introduced by Leslie Lamport in "The Part-Time Parliament" [LAMPORT98], which tells the algorithm as the legislature of the Aegean island of Paxos. In 2001 the follow-up "Paxos Made Simple" [LAMPORT01] introduced the simpler terms used today. Participants take one of three roles:

  
    
    
  • Proposers receive values from clients, create proposals to accept them, and try to collect votes from acceptors.
    • 
    
  • Acceptors vote to accept or reject proposed values. Fault tolerance needs several acceptors, but liveness needs only a quorum (majority) of their votes.
    • 
    
  • Learners act as replicas, storing the outcomes of accepted proposals.
    • 
  

  
Any participant can take any role; most implementations co-locate them, so one process is proposer, acceptor and learner at once. Every proposal has a value (from the client) and a unique, monotonically increasing proposal number. The number gives a total order of operations and establishes happened-before/after between them. It is often an (id, timestamp) pair: compare timestamps first and break ties with the (comparable) node ID.

  

    
Which proposal number wins?

    

      
      
      
      
    

    

  

  
Picture it
Ticket numbers at a deli counter, except two machines print them. To make every ticket unique you print "minute.machine" (5.2, 5.4): later minutes win, and if two tickets share a minute, the machine number decides. Nobody can ever hold the same ticket as someone else.

  
What's happening behind it
Paxos only needs proposal numbers to be unique and comparable; it doesn't need them to match real time. If two proposers could pick the same number, an acceptor couldn't tell whose promise it made, and two different values could each collect a "majority" under the same number. Pairing a counter or timestamp with a node ID makes collisions impossible. A common alternative (not in the book) is round-robin numbering: node i of N uses i, i+N, i+2N…, and after seeing a higher number it jumps to the next one of its own above it.

07 · PAXOS ALGORITHM
Two phases: win the right to propose, then get the value accepted
pdf p447–449 · Fig 14-3

  
Paxos has two phases: voting (the propose phase), where proposers compete for leadership, and replication, where the winning proposer distributes the value to acceptors. The proposer is the client's first point of contact: it gets the value to decide on and tries to collect votes from a quorum of acceptors; then acceptors tell learners the agreed value, ratifying the result. Learners raise the value's replication factor. Only one proposer can win a majority. Votes can split evenly so that nobody gets a majority in a round, forcing a restart (section 9).

  
Propose phase. The proposer sends Prepare(n) to a majority of acceptors. An acceptor answers while keeping these invariants [LAMPORT01]:

  
    
    
  • If it hasn't answered a prepare with a higher number yet, it promises never to accept a proposal with a lower number.
    • 
    
  • If it has already accepted another proposal (got Accept!(m, vaccepted)), it replies Promise(m, vaccepted), telling the proposer it already accepted proposal m.
    • 
    
  • If it has already answered a prepare with a higher number, it tells the proposer that a higher-numbered proposal exists.
    • 
    
  • An acceptor can answer several prepares, as long as each later one has a higher number.
    • 
  

  
Replication phase. With a majority of promises, the proposer sends Accept!(n, v). The value v is the one attached to the highest-numbered proposal among the replies, or any value of its own if no reply carried an earlier accepted proposal. An acceptor accepts proposal n unless it already answered Prepare(m) with m > n; if it rejects, it sends back the highest number it has seen so the proposer can catch up [LAMPORT01].

  
Once a value is accepted by even one acceptor, future proposers must decide the same value to preserve agreement: that's why acceptors return the latest value they accepted. If none has, the proposer is free to choose. A learner knows the decided value once it hears from a majority of acceptors. To learn sooner, acceptors notify learners as soon as they accept. With several learners each acceptor must notify each one, or one or more distinguished learners can relay to the rest. In short: phase 1 establishes a leader for the round and learns which value must be accepted; phase 2 broadcasts it. The base algorithm runs both phases for every value; Multi-Paxos (section 10) removes that cost.

What's happening behind it
The acceptor stores just three things on disk: the highest number it promised, and the number and value it last accepted. Safety comes from two rules working together. "Promise not to accept lower numbers" closes the window during which an old proposer could sneak a value in. "Adopt the highest-numbered accepted value you hear about" means that if any value could already have been chosen by a majority, every later proposer will re-propose exactly that value, because any majority it contacts overlaps the majority that accepted it. The cost: 2 round trips (4 message delays) and 4·(N−1) messages per decided value, plus learner notifications.

08 · QUORUMS IN PAXOS
Why "any two majorities share a member" is the whole trick
pdf p450

  
Quorums let some participants fail while the rest proceed. A quorum is the minimum number of votes needed for an operation, usually a majority. Even if participants fail or are split by a partition, at least one participant acts as an arbiter that keeps the protocol correct. Once enough participants accept a proposal, the value is guaranteed to be accepted, since any two majorities have at least one participant in common.

  
Paxos guarantees safety under any number of failures: no configuration can produce an inconsistent state. Liveness is guaranteed with up to f failed processes, which requires 2f + 1 processes in total, so that f + 1 can still proceed. Section 13 (Flexible Paxos) restates quorums so that only the quorums of the two different steps must intersect.

  
Tip from the book: quorums describe only the system's blocking properties. For safety, each step must wait for at least a quorum of replies. You may send proposals and accepts to more nodes; you just don't wait for all of them. Some systems use speculative execution (redundant requests so a node failure doesn't delay reaching the needed count), but for liveness you proceed as soon as you hear from a quorum.

In a class of 5, "3 people agree" twice can never be two completely different groups of 3: there are only 5 people, so some person is in both. That shared person remembers what the first group decided and tells the second group.

  
What's happening behind it
The calculator enumerates every pair of size-Q subsets of N acceptors and counts disjoint pairs. With Q ≥ ⌊N/2⌋+1 there are none and the minimum overlap is 2Q−N. The fault tolerance is N−Q crashed acceptors. Notice N = 4 tolerates 1 crash just like N = 3 (quorum 3 of 4): even sizes add cost without adding tolerance, which is why clusters are 3, 5 or 7. The latency model (modelled, not measured; 4,000 pooled trials per point) gives every node a round trip of 1 ms ± 0.3 ms, plus a 20 ms stall with the chance you set. Waiting for the fastest Q of N almost never sees the stall; sending to exactly Q nodes waits for the slowest of them.

09 · FAILURE SCENARIOS
When proposers and acceptors die mid-round
pdf p451–453 · Figs 14-4, 14-5, 14-6

  
Failures are where distributed algorithms get interesting. Suppose the proposer fails in phase 2 before broadcasting the value to every acceptor (the same happens if it is alive but slow or can't reach some acceptors). A new proposer can pick up and commit the value. Three cases from the book, all with proposers P1, P2 and acceptors A1, A2, A3:

  
    
    
  • Fig 14-4, old value decided. P1 completes the election with proposal 1 but crashes after sending V1 to A1 only. P2 starts round 2, gets a quorum of replies from A1 and A2, and commits the old value V1. Because the state is replicated, a proposer crash doesn't stop consensus: if even one acceptor accepted, the next proposer can carry the value forward, without the original proposer knowing. A client connected only to P1 may never learn the outcome (the book's footnote points to a real case described at databass.dev/links/68).
    • 
    
  • Fig 14-5, new value decided. Same crash, but A2 and A3 answer P2 first. P2 sees no accepted value and commits its own V2, even though A1 holds V1. That's fine: V1 never reached a majority, so it was never decided.
    • 
    
  • Fig 14-6, acceptor fails too. P1 crashes after A1 accepts V1, and A1 then crashes before telling anyone. P2's quorum doesn't include A1, so P2 commits V2. Any later proposer that does reach A1 ignores A1's value (number 1) in favour of the more recent accepted proposal (number 2).
    • 
  

  
Another failure mode: dueling proposers. Acceptors promise not to accept lower numbers but can still answer several prepares with increasing numbers. A proposer may reach its accept step and find the acceptors have promised a higher number to a rival; both keep retrying and block each other. The usual fix is a random backoff, which eventually lets one proceed while the other sleeps. Paxos tolerates acceptor failures only while enough acceptors are alive to form a majority.

10 · MULTI-PAXOS
Elect once, then replicate many values
pdf p454–455

  
Classic Paxos picks an arbitrary proposer and runs a full round, so every replicated value needs a propose phase; replication starts only after a majority answers Prepare with Promise. Multi-Paxos avoids repeating it by introducing a leader, a distinguished proposer [LAMPORT01] that reuses its recognised position. This is a crucial addition that significantly improves efficiency: with an established leader, skip the propose phase and go straight to replication (send the value, collect acknowledgments).

  
Reads. In classic Paxos a read can be done by running a Paxos round that collects values from incomplete rounds, because the last known proposer may not hold the latest data: another proposer could have changed state without it knowing. Multi-Paxos has the same issue: reading from the "known" leader after another leader was elected returns stale data and breaks linearizability. To prevent that, some implementations use leases: the leader periodically tells participants it's alive, extending its lease; participants reply and promise not to accept proposals from other leaders for the lease period [CHANDRA07]. Leases are a performance optimisation that allows reads from the leader without a quorum, not a correctness guarantee. Their safety depends on bounded clock synchrony: if clocks drift too far and the leader thinks its lease is valid while others think it expired, linearizability is lost.

  
The log. Multi-Paxos is often described as a replicated log of operations applied to some structure. The algorithm ignores the structure's meaning; it only replicates values appended to the log. Participants keep a durable log of received messages to survive crashes. To keep the log from growing forever, its contents are applied to the structure; once synchronised (a snapshot), the log can be truncated. Snapshot and log must be mutually consistent, and the snapshot change must be applied atomically with truncation [CHANDRA07].

  
Register vs log. Single-decree Paxos is a write-once register: once a value is in the slot, it can't change. Phase 1 is proposers competing for ownership of the register; phase 2 is one of them writing. Multi-Paxos is an append-only log of such registers: one value at a time, strictly ordered, never modified [RYSTSOV16]. Some algorithms instead offer collections of read-modify-write registers and share state rather than replicate a state machine: Active Disk Paxos [CHOCKLER15] and CASPaxos [RYSTSOV18].

Leases and clock drift

    

    

  

  
Picture it
Classic Paxos is holding a fresh election before every sentence of the meeting minutes. Multi-Paxos elects a secretary once, and she writes sentence after sentence, each confirmed by a nod from most of the room. A lease is the room saying "for the next 10 minutes, nobody else may take minutes", so she can read the minutes aloud without polling the room, as long as everyone's watch agrees on what "10 minutes" means.

  
What's happening behind it
Classic Paxos per value: Prepare → Promise → Accept! → Accepted = 4 message delays (2 round trips) and 4(N−1) messages. Multi-Paxos pays phase 1 once for all future slots (the leader prepares "every slot from i onward"), then each value costs Accept! → Accepted = 2 delays and 2(N−1) messages: half the latency and half the messages. The lease calculator: the leader counts L seconds on its clock, a follower counts L on its own. If the follower's clock runs faster by ε, it thinks the lease ended after L/(1+ε) real seconds and may promise a new leader while the old one still serves reads: a stale-read window of L − L/(1+ε). Subtracting a margin (the leader stops serving lease reads at L(1−ε) on its own clock) closes the window, which is why lease designs bound clock drift.

  
Before: classic Paxos per value
2 round trips per value; any proposer may start a round, so concurrent proposers duel; reads need a Paxos round.
After: Multi-Paxos
1 round trip per value from a stable leader; duels only during leader changes; leader reads served locally under a lease (if clocks are bounded).

11 · FAST PAXOS
Skip the leader hop, pay with bigger quorums and collisions
pdf p456–457 · Fig 14-7

  
Fast Paxos [LAMPORT06] cuts one round trip compared with classic Paxos by letting any proposer contact acceptors directly instead of going through the leader. The price: the quorum grows to 2f + 1 (instead of f + 1) and the total number of acceptors to 3f + 1 [JUNQUEIRA07].

  
In classic Paxos, during replication the proposer may pick any value it collected in the propose phase. Fast Paxos has two kinds of rounds: classic (as before) and fast, where acceptors may accept other values. The proposer that collected enough replies in the propose phase is called the coordinator; "proposer" means all the others. Some descriptions let clients contact acceptors directly [ZHAO15]. In a fast round, if the coordinator is free to pick its own value, it sends a special Any message instead. Acceptors may then treat any proposer's value as if it came from the coordinator in a classic round: they decide independently on values from different proposers. Fig 14-7 can make the fast round look longer, but remember that in a classic round a proposer would first have to go through the coordinator.

  
Fast rounds can collide: two or more proposers use the fast step and acceptors receive different values. The coordinator must step in and start recovery with a new round, re-running a propose phase so acceptors converge on one value. A disadvantage is more round trips and higher latency on collisions when the request rate is high. [JUNQUEIRA07] shows that because of more replicas and therefore more messages, Fast Paxos can have higher latency than classic Paxos despite fewer steps.

  

    
Quorum sizes and a collision model

    

      
      
    

    

    
    

    

  

  
Picture it
Classic: everyone hands their form to one clerk who stamps them in order. Fast: you drop your form straight into the inboxes of many clerks, saving a trip. If two people drop forms at the same moment, some clerks take one first and some the other, and a supervisor has to sort out the mess, which costs more than the trip you saved.

  
What's happening behind it
Why bigger quorums: in a fast round acceptors accept whatever arrives first, so after a collision the coordinator must be able to see, from any classic quorum, which value might have reached a fast quorum. That requires any two fast quorums and one classic quorum to share a member, which is what pushes N to 3f+1 and the fast quorum to 2f+1. The model (modelled, not measured): two requests arrive with the spacing you set; each of the N acceptors sees them with independent one-way delay 5 ms ± 3 ms; a fast round succeeds if one value reaches 2f+1 acceptors first. Latency counts a fast success as 2 one-way delays (proposer → acceptors → learner), classic via coordinator as 3, and a collision as the fast attempt plus a classic recovery (2 + 4 delays). 2,000 pooled trials per point. When requests are well spaced fast wins; when they're close together, collisions make it slower than classic.

12 · EGALITARIAN PAXOS
No single leader: order only the commands that conflict
pdf p458–461 · Fig 14-8

  
A distinguished leader makes the system fragile (when it fails, a new one must be elected before progress) and puts disproportionate load on one node.

  
Note from the book: partitioning. One way to spread leader load is to split the value range into segments, each owned by part of the system. This helps availability (failures are isolated to one partition), performance (segments don't overlap) and scalability (add partitions). But an operation across several partitions needs an atomic commitment.

  
Instead of a leader plus proposal numbers to sequence commands, use a leader per command and establish order through dependencies. This is Egalitarian Paxos, EPaxos [MORARU11]. Letting non-conflicting writes commit independently was first introduced as Generalized Paxos [LAMPORT05]; EPaxos is its first implementation. EPaxos aims for the best of both: classic Paxos has high availability (a leader per round) but more messages; Multi-Paxos has high throughput and fewer messages but a bottleneck leader.

  
EPaxos starts with a Pre-Accept phase in which a process becomes leader for a proposal. Each proposal carries dependencies (all commands that might interfere with it, not necessarily committed) and a sequence number that breaks dependency cycles, set larger than any known dependency's. The leader sends PreAccept to a fast quorum, which the book gives as ⌈3f/4⌉ replicas (see the note below). Replicas check their command logs, add any interfering proposals to the dependencies, and reply. If the leader gets replies from a fast quorum and their dependency lists agree with each other and with its own, it commits. Otherwise it merges all reported dependencies, picks a sequence number above everything seen, sends the updated command to ⌊f/2⌋ + 1 replicas (book's wording), and then commits. So: a fast path when dependencies match, and a slow path when replicas disagree and must be brought to the same dependency list.

  
Fig 14-8: P1 sends PreAccept(1, ∅); P2 and P3 have empty logs, so P1 commits. P5 then proposes sequence 2 with no dependencies, PreAccept(2, ∅). P4 doesn't know about committed proposal 1, but P3 reports the conflict and its log {1}. P5 updates its dependencies and sends Accept(2, {1}); once replicas answer it commits.

  
Commands A and B interfere only if their order matters: running A then B gives a different result from B then A. Commit means replying to the client and asynchronously sending Commit to replicas; commands execute after commit. Since dependencies are gathered during Pre-Accept, by execution time the order is fixed and no command can appear in between; a new one can only come after the highest sequence number. To execute, replicas build a dependency graph and run commands in reverse dependency order: a command runs only after all its dependencies (and theirs). Because only interfering commands depend on each other, this is rare for most workloads [MORARU13]. Like Paxos, EPaxos uses proposal numbers to stop stale messages. They consist of an epoch (cluster configuration ID, changes when nodes join or leave), a monotonically increasing node-local counter, and a replica ID. A replica that gets a lower number than one it has seen sends a negative acknowledgment with the highest number and its updated command list.

  
Beyond the book: check the quorum formulas against the paper
The EPaxos correctness report [MORARU11, CMU-PDL-13-111, §5] states the fast quorum in terms of the number of replicas N, not failures f: the simplified protocol starts with N−1, and it shows the fast quorum can be cut to ⌈3N/4⌉ when N > 3; the slow path uses ⌊N/2⌋ + 1 replicas. So the book's "⌈3f/4⌉" and "⌊f/2⌋ + 1" read correctly with N in place of f (with f = 1 the book's formula would give a quorum of 1, which can't be right). The calculator below uses the paper's N-based form.

13 · FLEXIBLE PAXOS
Quorums only have to intersect across phases
pdf p462–463

  
A quorum is usually a majority, so any two quorums intersect: some node can always break ties. Two questions: must every step contact a majority? And must all quorums intersect: the phase-1 quorum (choosing the distinguished proposer), the phase-2 quorum (deciding a value), and every execution instance (e.g. concurrent phase-2 instances)? Safety can't change: agreement must hold.

  
In Multi-Paxos, leader election is rare and the leader commits many values without re-electing. Chapter 11's tunable consistency showed that as long as R + W > N, read and write sets share a node (e.g. write to one node, read from all). The same logic works for consensus: Paxos only needs the phase-1 group (electing a leader) to overlap the phase-2 group (accepting proposals). A quorum needs only to be a non-empty group. With N participants, Q₁ nodes for the propose phase and Q₂ for the accept phase, it suffices that Q₁ + Q₂ > N. Because phase 2 is far more common, Q₂ can be as small as N/2 if Q₁ grows to match (Q₁ = N − Q₂ + 1). The book calls this an important observation for understanding consensus. The algorithm is Flexible Paxos [HOWARD16].

  
Example: with five acceptors, if winning an election needs four votes, the leader can wait for just two replies during replication. And because every two-node set overlaps every election quorum, proposals can even go to disjoint pairs of acceptors. Intuitively: whenever a new leader is elected without the current one knowing, at least one acceptor knows about the new leader. Flexible Paxos trades availability for latency: phase 2 involves fewer nodes, but elections need more nodes up. The upside: with a stable leader, replication continues through up to N − Q₂ failures.

  
Vertical Paxos also uses intersecting quorums, distinguishing read and write quorums that must intersect: a leader collects a smaller read quorum for one or more lower-numbered proposals and a larger write quorum for its own [LAMPORT09]. [LAMPSON01] distinguishes out and decision quorums (prepare and accept phases) and gives a quorum definition similar to Flexible Paxos.

Any 2 signers include at least one of the 4 who voted in the most recent election, so a deposed president's paperwork always meets someone who knows she was replaced.

14 · GENERALIZED SOLUTION TO CONSENSUS
Paxos as a table of write-once registers
pdf p464–467 · Fig 14-9

  
Paxos's roles, steps and variants are hard to track. A simpler view achieves single-decree Paxos's guarantees with a small set of concepts and rules. The book treats it briefly because it's recent [HOWARD19]: important to know, but without known implementations yet.

  
There's a client and a set of servers; each server has many registers. A register has an index, can be written once, and is in one of three states: unwritten, holding a value, or holding nil (a special empty value). Registers with the same index on different servers form a register set, which can have one or more quorums. Depending on its registers, a quorum is undecided (Any, Maybe v) or decided (None, Decided v):

  
    
    
  • Any: depending on future operations, it can still decide any value.
    • 
    
  • Maybe v: if it decides, it can only decide v.
    • 
    
  • None: it can't decide a value.
    • 
    
  • Decided v: it decided v.
    • 
  

  
The client exchanges messages with servers and keeps a state table of values and registers from which it infers quorum decisions. Rules: reading, the client may output a value only if it read it from a quorum of servers in the same register set. Writing, the client may write a value only if it got it as input or read it from a register (no inventing values); it can't write values that let different quorums of the same register set decide differently; and it can't override decisions in earlier register sets (sets up to r−1 must be None, Maybe v, or Decided v).

  
The resulting generalised Paxos [HOWARD19]: three servers [S0, S1, S2], registers [R0, R1, …], clients [C0, C1, …], each client writing only its assigned registers; majority quorums {S0,S1}, {S0,S2}, {S1,S2}. Phase 1: the client sends P1A(register). If that register is unwritten, the server sets every register below it to nil (so nobody can write earlier registers) and replies with the registers written so far. With a majority of replies, the client takes the non-empty value from the highest-indexed register, or its own value if there's none; otherwise it restarts phase 1. Phase 2: the client sends P2A(register, value) to all servers; if a majority replies, it outputs the decision, otherwise it restarts from phase 1.

  
In Fig 14-9 client C0 commits V: in step 1 its table is empty and S0, S1 reply that nothing is written; in step 2 it writes V. Then any other client can query state: quorum {S0, S1} is Decided V (the book's text prints "Decided A", which reads as a typo for V), and {S0, S2}, {S1, S2} are Maybe V for R0, so C1 picks V and no client can ever decide anything else. Thinking in terms of last known state instead of remote actors' interactions removes ambiguity; immutable state and message passing are easier to implement correctly. Parallels with Paxos: a client that sees Maybe V in an earlier register set re-commits V, just like a Paxos proposer re-proposing a value one acceptor accepted; and setting unwritten lower registers to nil plays the role of restarting with a higher proposal number.

  

    
Drive the register table yourself

    

      
      
      
      
    

    

    

  

  
Picture it
Numbered whiteboards in three rooms. Each board can be written once. Before writing board 3 you visit two rooms and cross out ("nil") every blank board below 3 so nobody can sneak an older decision in, and you note anything already written. If you saw a value, you copy that one instead of yours. A decision exists when the same board number shows the same value in two rooms.

  
What's happening behind it
The table classifies each majority quorum of each register set: all registers hold v → Decided v; any holds nil → None (it can never decide); some hold v and the rest are unwritten → Maybe v; all unwritten → Any. Try: C0 phase 1 + phase 2 on {S0,S1} (the book's example), then C1 on {S1,S2}: its phase 1 nils R0 on S2 and reads V from S1, so it must write V into R1. Or do C1's phase 1 before C0's phase 2: S0 and S1's R0 become nil, C0's phase 2 fails and C0 must restart with R2. This is Paxos's "promise" rule in register form.
