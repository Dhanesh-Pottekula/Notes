Part 1 · Tcl · about 3 weeks

Tcl from zero to the level a PV engineer needs

Every big EDA tool gives you a Tcl prompt: Innovus, Calibre (its viewer, its batch shells and its TVF rule files), PrimeTime, ICC2. Learn the language once and you can script all of them. This page teaches Tcl with layout-flavoured examples. Every example on this page was really run, and the output under it is the real output.

Why Tcl first

In physical verification you spend your day moving between tools. The commands are different in each tool, but the language around the commands is the same. foreach, if, proc, lists and regexp work the same way in Innovus as in the Calibre viewer. So this page has two halves in your head:

  • The language (this page): how to hold data, loop, make decisions, read files, write procs.
  • The tool commands (Innovus, Calibre): the special commands each tool adds on top.
How to practise without a licence. Type tclsh in any Linux or Mac terminal. That is plain Tcl with no EDA commands, and it is enough for everything on this page. Code here is written for Tcl 8.5, because some EDA tools still ship that version. Check yours with puts [info patchlevel].

The one rule: a line is a command and its words

Tcl has almost no grammar. Each line is command word word word. Before the command runs, Tcl does three kinds of replacement inside the words:

You writeTcl doesName
$nameputs the value of the variable therevariable substitution
[command ...]runs that command first and puts its result therecommand substitution
"..."makes one word; $ and [ ] still work insidesoft quoting
{...}makes one word; nothing inside is replacedhard quoting

The second puts printed the text as it is, because braces switch all replacement off. This is the whole secret of Tcl. When a script behaves strangely, ask: "which words did Tcl see, after replacement?"

Trap: comments are commands too. A # starts a comment only where a command could start. To put a comment after a command on the same line, write ;#. A comment with an unbalanced brace in it can break the whole file, because Tcl counts braces before it looks for comments.

Variables and arithmetic

set makes a variable. Everything is stored as text; expr does the maths. Always put braces around the expression. It is faster, and it protects you from surprises when a value contains spaces or brackets.

Trap: floating point. Look at the first line of output: it is not exactly 0.05. Coordinates in microns are fractions that a computer cannot store exactly. Never test two micron values with ==. Either compare with a tolerance (abs($a - $b) < 0.0005) or convert to integer database units first, the way layout tools do internally.

Strings

Report parsing is string work. These are the commands you will use every day.

Regular expressions

regexp answers "does this line look like that?" and can pull pieces out. regsub replaces. Put the pattern in braces so Tcl does not touch the backslashes.

Lists: the main data structure

A list is words separated by spaces. A bounding box {llx lly urx ury} is a list of four numbers. The result of almost every EDA query is a list. If you are fluent with lists, you are fluent in tool scripting.

Lists inside lists

A table is a list of rows, and each row is a list. lsort -index sorts by a column. This is exactly how the practice script drc_summary.tcl ranks rules.

Trap: build lists with list commands, not with quotes. set box "$llx $lly $urx $ury" works for numbers, but breaks the day a value has a space or a brace in it (an instance name with an escaped bus bit, for example). [list $a $b] and lappend always quote correctly.

Arrays and dicts: look things up by name

Use these when the question is "how many per rule?", "which cell owns this?", "have I seen this name already?". An array is the old style and is everywhere in existing EDA scripts. A dict is a value you can pass to a proc and return from it, so new code usually prefers it.

Decisions and loops

Trap: the opening brace must be on the same line. if {$n == 0} followed by { on the next line is an error, because a newline ends the command. Write if {...} { and } else { on one line.

Procs: your own commands

A proc is a named piece of script. Put anything you do twice into a proc. Variables inside a proc are local; the outside world is invisible unless you ask for it.

Reaching outside: global and upvar

Use upvar for arrays (they cannot be passed by value) and for big lists you want to change in place. Use global name only for true settings such as a debug flag.

Files and directories

Three patterns cover nearly all report work: read line by line, read everything and split, write a new file.

Errors, other programs and the environment

A script that stops at 2 a.m. with a red error and no message costs you a morning. Three tools prevent that: catch, error, and exit codes.

Exit codes are how scripts talk to each other. End a checking script with exit 1 when it found problems and exit 0 when clean. Then a Makefile, a shell if, or a regression system can react without reading your output.

Pro habits

Namespaces and a personal library

Once you have ten procs, put them in one file inside a namespace, so their names cannot clash with tool commands. Load it with source. The practice library pvlib.tcl is built this way.

{*}, subst and string map: building commands safely

Speed: the mistake that turns 5 seconds into 5 hours

A full-chip database has millions of instances. Searching a list inside a loop is slow, because each search walks the list again. Put the names into an array or dict once, then every lookup is instant.

Practice, in order

  1. Type every example on this page yourself in tclsh. Change one thing in each and predict the output before you press Enter.
  2. Write proc bbox_center {box} that returns {x y}. Add it to pvlib.tcl and add two checks to pvlib_test.tcl.
  3. Read fixtures/waivers.txt into a dict of rule → max count, skipping comments and blank lines.
  4. Rewrite the Perl drc_compare.pl in Tcl using pv::read_summary. Compare your output with the Perl output line by line.
  5. Take a real summary from your own run (never copy it outside your company) and run drc_summary.tcl on it. If the result looks wrong, the fix is one regular expression: that is the real exercise.

Then go on to Perl, or straight to the script bank if you want to see complete tools.
