Perl for reports, logs and netlists

Tcl drives the tools. Perl digests what the tools print. A sign-off run leaves behind summaries, results databases, LVS reports, logs and netlists, often millions of lines. Perl was built to read text like that and turn it into a short answer. Every example on this page was really run.

Most teams have years of Perl in their flow directory. You will read and repair Perl long before you write a new tool, so reading skill matters as much as writing skill. Python is taking over new work in many companies; the thinking on this page (patterns, hashes, state machines) carries over directly.

Start every script with these three lines. use strict forces you to declare variables, so a typo in a name is an error and not a silent empty value. use warnings tells you about suspicious code. They save more debugging time than anything else in Perl.

Three kinds of variable

The first character tells you the kind: $ one value, @ a list in order, % a lookup table.

Trap: one element of an array is a scalar. The array is @layers, but its first element is $layers[0]. The hash is %count, but one value is $count{key}. The symbol says what you get back, not what the container is.

Useful array and hash tools

<=> compares numbers, cmp compares text. Sorting counts with cmp puts 15 before 4, which is a favourite interview trap.

Regular expressions

This is the reason Perl is still on every PV engineer's machine. A pattern sits between slashes, and =~ means "test this string against it". Brackets capture pieces into $1, $2.

PieceMeaningPieceMeaning
\d \s \wdigit, space, word character\D \S \Wthe opposites
+ * ?one or more, zero or more, optional+? *?same, but take as little as possible
^ $start, end of the string\bword boundary
(...)capture into $1…(?:...)group without capturing
/iignore case/gall matches, not only the first
/xallow spaces and comments inside the pattern\Q$var\Etreat the variable's text literally (rule names contain dots)
Trap: greedy .*. .* takes as much as it can. In /(.*)\.(\w+)/ on M1.S.1, the first group becomes M1.S, not M1. Use (.*?) for "as little as possible", or better, say exactly what you mean: ([^.]+) = "characters that are not a dot".

Reading and writing files

  • '<' read, '>' write (replaces the file), '>>' append.
  • or die "...: $!" on every open. $! is the system's reason ("No such file", "Permission denied").
  • Reading line by line uses almost no memory, so it works on a 20 GB log. Reading a whole file into an array does not.
  • File tests: -e exists, -f plain file, -d directory, -s size, -M age in days.

References: tables inside tables

Real questions have two levels: "violations per rule per cell", "pins per subckt". A hash value can only be one scalar, so Perl stores a reference (an arrow pointing at another array or hash). The arrow -> follows it. This is the step from beginner to useful.

You haveMake a referenceUse it
array @a\@a or [1, 2, 3]$r->[0], @$r, scalar(@$r)
hash %h\%h or { a => 1 }$r->{a}, keys %$r
sub foo\&foo or sub { ... }$r->(args)

Notice that $by_cell{$cell}{$1} = $2 created the inner hash by itself. Perl calls this autovivification. It is convenient, and it is also why a test like if ($h{a}{b}) quietly creates $h{a}. Test the outer key first when that matters.

When a structure confuses you, print it: use Data::Dumper; print Dumper(\%by_cell);

The state machine: how to parse any report

Reports are not tables. They have sections, and the same kind of line means different things in different sections. In the DRC summary, RULECHECK lines appear once in the main section and again under each cell. The reliable method is always the same:

  1. Keep one variable that says "which section am I in?".
  2. Change it when you see a section header.
  3. Only then decide what the current line means.

The complete version is lvs_triage.pl. The results-database reader in PVReport.pm uses the same idea with a counter ("skip the next N lines of rule text").

One-liners from the shell

For a quick question you do not need a file. -n wraps your code in a "for each line" loop, -e gives the code, -a splits each line into @F, -l handles newlines, -i.bak edits a file in place and keeps a backup.

Why the ^ matters. The by-cell section repeats every failing rule on indented lines. ^RULECHECK matches only lines that start at column one, so each rule is counted once. Remove the ^ and every count doubles. One character decides whether the number in your status mail is right, so always test a parser on a file where you already know the answer.

Things that separate a tool from a throwaway script

  • Fail loudly. If the summary has no RULECHECK lines, die. A script that prints "0 violations" for an empty or truncated file is dangerous at sign-off.
  • Say where. Error messages should name the file and line: die "$file line $.: ...".
  • Data to stdout, chatter to stderr (warn), so script > out.csv stays clean.
  • Exit non-zero on problems, so flows can react.
  • Core modules only (List::Util, File::Basename, File::Find, Getopt::Long, Data::Dumper, POSIX). Compute farms rarely let you install from CPAN.
  • Big files: read line by line, compile a fixed pattern once with qr//, and test the cheap condition first.
  • Check syntax without running: perl -c script.pl. Step through with perl -d script.pl.

Practice, in order

  1. Type the examples yourself. For each regular expression, change the input line until it stops matching, so you learn what each piece guards.
  2. Extend drc_summary.pl with a --csv option using Getopt::Long.
  3. Add a by-cell mode: print each cell with its failing rules (use the hash-of-hashes example above).
  4. Write rule_group.pl: group rules by the text before the first dot (M1, M2, ANT…) and print a total per group.
  5. Extend cdl_ports.pl to also compare the number of device lines inside each subckt.
  6. Take the oldest Perl script in your team's flow directory and write one comment per block explaining what it does. Reading old code is the real job.
