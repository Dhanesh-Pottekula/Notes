Innovus scripting for a PV engineer

Innovus is the place-and-route tool, not the sign-off checker. But the layout you verify is born there, and most violations are fixed there. A PV engineer who can open the design database, ask it questions in Tcl and hand the block owner an exact instance or net is worth far more than one who can only send screenshots.

Ask your team which one the flow uses before you write anything. A quick test in a session: if info commands get_db returns a name, you are in the common UI. This page teaches the legacy dbGet first, because most existing PV helper scripts use it, and gives the get_db idea at the end.

dbGet: the mental model

The design is a tree of objects. Each object has attributes. Some attributes are plain values (a name, a box), and some are other objects (an instance's cell, a net's terminals). You walk the tree with dots.

StartMeans
topthe design: its instances, nets, pins, floorplan, markers
headtechnology and libraries: layers, library cells, units
selectedwhatever is selected in the layout window right now

The four options you need

OptionWhat it doesExample
-preturn the objects whose attribute matches, not the attribute values. This is the filter.dbGet -p top.insts.name u_core/*
-uunique values onlydbGet -u top.insts.cell.name
-ereturn an empty list when nothing matches (without it you get the text 0x0, which a foreach treats as one item)dbGet -e -p top.insts.pStatus unplaced
pattern as last wordkeep values matching a wildcard patterndbGet top.nets.name *clk*
Trap: 0x0. When nothing matches, plain dbGet returns the text 0x0. llength of that is 1, so "count the unplaced cells" reports one when there are none, and a foreach runs once with a value that is not an object. Use -e whenever you will count or loop over the result, and test for "nothing found" with if {[llength $result] == 0}. Do not write if {$result}: an empty string is not a valid true/false value in Tcl and raises an error.

Reading it as English

dbGet [dbGet -p top.insts.pStatus unplaced].name reads from the inside out: "among all instances, give me the objects whose placement status is unplaced; then give me the names of those objects". Almost every useful query has this two-step shape: filter to objects with -p, then ask those objects for something.

dbSet writes with the same path style, for example changing a placement status on a filtered set of objects. Writing changes the design, so do it only on a copy until you know the command well.

If your team uses the common UI: get_db

The idea is the same tree, with a different spelling. You name an object type, then attributes start with a dot, and filters are written as expressions.

A Cadence application note on moving from the legacy interface to the common UI pairs, among others, verify_drc with check_drc, verify_connectivity with check_connectivity, saveNetlist with write_netlist and saveDesign with write_db. I have not confirmed a one-to-one table between dbGet attributes and get_db attributes, so I am not printing one. Cadence publishes a rapid adoption kit about get_db on its support site (login needed); that is the right source.

Practice

  1. In a restored design, run dbGet top.?, then pick five attributes and follow each one level down with .?. Draw the tree on paper.
  2. Type recipe 1. Then change it to print only cells with more than 1000 instances, sorted by count.
  3. Select one instance in the window and print its name, cell, box and placement status in one line using selected.
  4. Run rdb_to_tcl.tcl on a results file from your own block and step through the first ten violations with recipe 4.
  5. Replace the slow loop in recipe 3 with the tool's area query, and time both with time {...}.
  6. Put all your procs in pv_procs.tcl inside namespace eval pv, and load it from your start-up file.
