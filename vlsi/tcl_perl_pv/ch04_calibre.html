Part 4 · Calibre automation · about 2 weeks

Scripting around Calibre: runs, rule files and results

Running one DRC job from the GUI is easy. The job you are paid for is running DRC, LVS, antenna and ERC on forty blocks every night, knowing by nine o'clock which ones moved, and never signing off on a broken run. That is all scripting: generate the run files, launch, check the logs, read the results.

Trap: the wrong switch is a silent wrong sign-off. Decks have switches such as "block level" versus "chip level", metal-stack choice, and "skip density". A run with the wrong switch finishes clean and means nothing. Put the switches in your generator script, from one project settings file, so nobody types them by hand. Write the switch values into your status report.
Trap: the result cap. If a rule shows exactly the maximum count (1000 in the sample), the real number is unknown. A script that compares runs should flag "count = cap" and not report "same as yesterday".

Launching

The other common style is a runset: a text file saved from the Calibre Interactive GUI that holds the same settings as key and value lines, and can be run without the window. An open-source PDK ships one, and its launcher script runs it in batch like this:

Because a runset is plain *key: value text, a ten-line Perl or Tcl script can produce one per block from a template, exactly like the control-file generator.

Rules for launch scripts

  • One directory per block per run. Never let two runs write into the same directory.
  • Keep the log. Redirect both output streams to a file named after the block.
  • Record the inputs. Write the layout path, its date, the deck version and the switch values into the run directory. Three weeks later someone will ask.
  • Check that it finished. No summary file, or a log without a completion line, is a failed run, not a clean block. log_scan.pl does this.
  • Stale results. If the summary is older than the layout file, the result belongs to an old layout. Compare the two times with file mtime in Tcl or -M in Perl.
  • Do not fill the licence pool. Launch through your farm's queue command and limit how many jobs run together.

Reading the DRC summary

The section you need starts at the header RULECHECK RESULTS STATISTICS and ends at the next long dashed line. Each line has a rule name, dots, and two numbers.

  • The line shape RULECHECK name ... TOTAL Result Count = N (M) is confirmed: an open-source sign-off script for real shuttle runs uses a regular expression of exactly this form and stops at the dashed line, as the practice scripts do.
  • The two numbers: as I remember it, the first is the count as Calibre stored it in a hierarchical run and the number in brackets is the flat count (each error counted in every placement of its cell). In the sample, 15 errors inside a memory bit cell become 240 flat. Confirm the meaning in the manual before you quote either number in a report, and always say which one you quote.
  • The by-cell section repeats the rules, indented. A careless pattern counts everything twice.

Reading the ASCII results database

The layout below matches what KLayout's open-source reader for this format expects (KLayout is a free layout viewer that can load these files). The sample file itself is written by hand for practice.

  1. Line 1: top cell name and precision (database units per micron). Every coordinate below is an integer; divide by the precision to get microns.
  2. Per rule: a line with the rule name, then a line with counts and the date. The third number on that line says how many lines of rule text follow.
  3. Per result: p number vertices for a polygon, followed by one x y line per vertex; or e number edges for an edge cluster, followed by one x1 y1 x2 y2 line per edge.

Real files carry one more thing the sample does not have: property lines between a result's header and its coordinates. They start with a letter. The important one is CN, which names the cell a result was reported in; its coordinates are then in that cell's own space, not in top-level space. The practice readers in PVReport.pm and pvlib.tcl skip property lines (tested with a file that has them) and stop with an error when the file ends in the middle of a result. So for hierarchical results they give you cell-local boxes. Placing those at top level is practice task 4 below; the simple way out is to ask Calibre for flat, top-level coordinates in the results database, which the manual describes.

With coordinates in hand you can do things the viewer cannot do quickly: cluster violations into hotspot windows, export a CSV, or hand boxes to Innovus.

Reading the LVS report

An LVS report is long, but triage needs only four things, in this order: the verdict in the box of # signs, the Error: and Warning: lines under it, the list of incorrect cells, and the object-count table where a star marks a mismatch.

The sample is a trimmed lookalike written for practice. The debugging order it teaches is real: fix the lowest incorrect cell first, because one broken leaf cell makes every parent incorrect; and look at count mismatches before connectivity details, because a missing device or an extra net explains a hundred lines of discrepancy. Putting it together: the nightly loop

  1. Pre-check each block: layout file exists and is fresh, top cell present, layer map sane, netlist ports match. Stop bad blocks here.
  2. Generate a run directory and control file per block from one list and one template.
  3. Launch through the farm, with a limit on parallel jobs.
  4. Scan logs: finished or not, errors, run time.
  5. Summarise each block: counts per rule after waivers.
  6. Compare with the previous night: new, worse, fixed.
  7. Publish one table: block, DRC open rules, LVS verdict, antenna, run time, change since yesterday.

Each step is one script in the script bank. Building this chain for your own blocks, even in a small form, is the single best project to talk about in an interview.

Practice

  1. Run gen_runs.tcl on a list of two of your own blocks in dry-run mode and read the generated files line by line against a control file your team uses.
  2. Add a second template to it for LVS, chosen with an option.
  3. Make drc_compare.pl flag any rule whose count equals the result cap.
  4. Open a real ASCII results file and find the property lines. Extend read_rdb to keep the CN cell name with each violation, and print it as a column in rdb_bbox.pl.
  5. Write stale_check.pl: for each run directory, warn if the summary is older than the layout file.
  6. Write the "publish" step: one CSV with a line per block from the outputs of the other scripts.
