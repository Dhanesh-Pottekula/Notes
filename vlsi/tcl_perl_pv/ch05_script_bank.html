The script bank: 16 working tools for daily PV jobs

Each script here answers a question a PV engineer is really asked: "is it clean?", "what changed since yesterday?", "can we waive it?", "where are the errors?", "why is LVS failing?". All of them were run on the sample files in this folder, and the output shown under each one is the real output. Download them, run them, then break and extend them.

How to use this page

  1. Copy the scripts and fixtures folders to a Linux machine (or use this folder directly). Perl 5 and tclsh are already on almost every Linux system.
  2. From inside scripts, run ./run_all.sh. It runs every script on the sample inputs. You should see the same outputs as on this page.
  3. For each script: read the situation, guess how you would solve it, then read the code, then do the "change it" tasks. Typing a script out yourself teaches more than reading it three times.
About the sample inputs. The files in fixtures are small practice files written for this guide. The DRC summary lines and the results-database layout follow the real Calibre formats as read by open-source tools; the LVS report and log samples are simplified lookalikes from memory (details on the Calibre page). When you move a script to real files, expect to adjust a regular expression or two. That adjusting is the skill. Never take real design data or foundry decks out of your company's network.

1 · drc_summary.pl: is it clean?

Situation. The run finished overnight. Your lead asks "how does the block look?". The summary file has hundreds of rules, most of them at zero. You want the failing ones, worst first, and a script exit code that a flow can test.

What to notice.

  • The loop has two phases: skip lines until the section header, then read until the dashed line. Without the last, the by-cell section would overwrite or double the numbers.
  • sort { $count{$b} <=> $count{$a} || $a cmp $b }: biggest count first, and names in order when counts are equal, so the output is the same every run.
  • It dies when no rule lines are found. An empty report must never look like a clean report.

Change it. Add --csv. Add a --top N option. Print the second (bracketed) count as another column.

2 · drc_summary.tcl: the same job in Tcl

Why twice. Seeing one problem solved in both languages is the fastest way to learn the second one. Compare line by line: Perl hash ↔ Tcl dict, sort with a comparison ↔ two lsort passes, die ↔ error caught by catch.

What to notice. Tcl's lsort keeps the old order for equal items (it is "stable"), so sorting by name first and then by count gives "count, then name". The parsing itself lives in the library pvlib.tcl.

3 · drc_compare.pl: what changed since yesterday?

Situation. The block owner says "I fixed the M1 spacing errors". Did they? And did the fix break something else? Absolute counts hide this; differences show it.

What to notice.

  • The rule list is the union of both runs, so a rule that exists in only one deck version shows up as NEW RULE or RULE GONE. A deck update that silently drops a rule is a sign-off risk worth catching.
  • $o // '-' means "use - when the value is undefined". The // operator is different from ||, which would also replace a real 0.
  • The most alarming groups are printed first. Order your output for the reader who stops after five lines.

Change it. Exit with status 1 when there is any NEW FAIL or WORSE. Flag counts equal to the result cap. Accept more than two files and print a trend row per rule.

4 · drc_waive.pl: clean after waivers?

Situation. Some violations are accepted: a foundry bit cell, a density window over analog IP. The agreed list lives in a text file. Sign-off means "nothing open outside that list, and nothing above the agreed count".

What to notice.

  • A waiver has a maximum count. Four antenna errors against a waiver for two is still a failure. Waiving by rule name alone would hide new errors forever.
  • The fourth argument of split ' ', $line, 4 keeps the reason text together with its spaces.
  • The input is validated with the file name and line number in the message.
  • It reports stale waivers. A waiver nobody needs any more should be removed before it covers a future real error.

Change it. Real waivers are usually by location, not only by count. Combine this with read_rdb: a waiver line gives a rule and a box, and a violation is waived only when its box lies inside.

5 · log_scan.pl: did everything finish?

Situation. Forty blocks ran overnight. Before reading any result you need to know which runs are real: finished, without errors.

What to notice. Three states, not two. A log with no error and no completion line is "still running or killed", and treating it as clean is the classic mistake. $first ||= $1 keeps the first error only, which is usually the cause; later ones are consequences.

Change it. The message patterns are samples: collect the real error and completion lines from your own logs and update the three patterns. Add a column for peak memory if your logs print it. Sort by run time to find the block that needs more CPUs.

6 · cell_diff.tcl: two lists, what is missing?

Situation. Cells in the merged GDS against cells that have a LEF; cells in the netlist against cells in the layout; yesterday's waiver list against today's. It is always the same question.

What to notice. The comment in only_in is the lesson: an array lookup per name, not an lsearch per name. On a full chip that is the difference between seconds and hours.

7 · layermap_check.tcl: check the map before stream-out

Situation. A new metal option arrives and somebody edits the layer map by hand. One wrong digit merges two layers in the GDS, and the run reports thousands of shorts that do not exist in the design.

What to notice. The key of the array is the pair layer/datatype, and each value is a list of everything mapped there. "Group by a key, then look for groups bigger than one" is the general recipe for finding duplicates of any kind.

Change it. Real map files have their own column order: adapt the lassign line to your team's format.

8 · cdl_ports.pl: do the pins match?

Situation. LVS at top level fails with hundreds of connectivity errors. Often the cause is small: a cell's pin list differs between the schematic netlist and the layout side (a missing test-enable pin, power pins in a different order). Comparing pin lists takes a second and can save a full LVS iteration.

What to notice.

  • SPICE continues a long line with + at the start of the next line. The reader joins those first, then parses. "Normalise the text, then parse it" keeps every parser simple.
  • Names are compared in lower case, because SPICE is case-insensitive.
  • Pin order matters in SPICE: instances connect by position. Same pins in a different order is a real problem, so it is reported separately.

9 · lvs_triage.pl: the first ten lines of an LVS debug

Situation. The LVS report is 80,000 lines. You need the verdict, the error types, which cells are wrong and which object counts differ, so you know where to start.

What to notice. The $section variable is the whole trick. The word INCORRECT appears in the verdict box and in the cell table; only the section tells you which one you are looking at. $verdict //= $1 keeps the first verdict found and ignores later ones.

Change it. Print the incorrect cells in hierarchy order (lowest first) by reading the hierarchy from the netlist with the reader from script 8.

10 · PVReport.pm: one parser, many scripts

Why a module. When the summary format needs a fix, you want to fix it in one file, not in five scripts. This module holds the summary reader and the results-database reader.

Reading read_rdb. A violation is several lines: a header (p 1 4), optional property lines that start with a letter, and then that many coordinate lines. The reader keeps a little state between lines: the previous line (it becomes the rule name when the counts line appears) and a countdown of rule-text lines to skip. Each violation is stored as a hash reference with a bounding box, in microns.

11 · rdb_bbox.pl: one line per violation

What to notice. The message "6 violations read" goes to the error stream with warn, so rdb_bbox.pl file > out.csv gives a clean CSV. The optional second argument filters by rule with a regular expression.

12 · rdb_hotspot.pl: where do they cluster?

Situation. 3,000 spacing errors look hopeless. Binned into windows, they often turn out to be three places: one bad macro abutment, one congested channel, one power-switch column. That changes the conversation with the block owner from "3,000 errors" to "three problems".

What to notice. floor(centre / window) turns a coordinate into a window index. The data structure is a hash of hashes: window → rule → count. Different rules in the same window (here M1 and M2 spacing together) usually share one root cause.

13 · gen_runs.tcl: set up and launch many blocks

Situation. Every block needs its own run directory and control file. Typing them by hand produces the wrong top cell name sooner or later.

What to notice.

  • Dry run by default. It writes the files and prints the commands; only -run executes. Any script that launches jobs or changes files should be able to show what it would do first.
  • The template uses @NAME@ markers and string map, so SVRF's own quotes and braces need no escaping.
  • The deck path comes from an environment variable, with a visible fallback.
  • exec is inside catch, and failed blocks are collected and reported at the end, so one bad block does not stop the other thirty-nine.
  • The launch step itself was not executed here (no Calibre on this machine); the dry-run output above is real.

Change it. Submit through your farm's queue command. Add an LVS template. After each run, call pv::read_summary and print the status.

14 · pvlib.tcl: a small Tcl library

pvlib_test.tcl: tests for the library

Seven checks, one second. Run it after every edit of the library. A PV utility that silently returns a wrong box is worse than no utility.

15 · rdb_to_tcl.tcl: hand the violations to the layout tool

Situation. You want to step through violations inside Innovus, or select what lies under each one. The simplest bridge between two Tcl programs is a file of Tcl data that the second one loads with source.

The Innovus side that walks this list is recipe 4 on the Innovus page.

16 · run_all.sh: your regression

One command re-runs everything and saves each output. After you change a parser, run it and compare the outputs with the previous ones (diff -r). This is how you find out that your "small fix" for the LVS report broke the DRC compare.

Projects that turn this into interview material

  1. Nightly dashboard. Chain scripts 13 → 5 → 1 → 4 → 3 into one command that prints a table: block, run status, open rules after waivers, LVS verdict, change since yesterday. Write it as CSV and HTML.
  2. Location-based waivers. Waiver file with rule and box; a violation is waived when it lies inside. Report waived, open and stale.
  3. Hotspot hand-off. From a results file to the ten worst windows, to a Tcl file, to an Innovus proc that lists the instances and nets in each window.
  4. Pre-run gate. One script that refuses to launch when the layout is older than the database, the top cell is missing, the layer map has duplicates or netlist ports differ.
  5. Port everything to the other language. Every Perl script here in Tcl, and every Tcl script in Perl. Then one of them in Python.

For each project, be ready to say in an interview: what problem it solved, how much time it saved per week, and one bug you found in it and how.
