title: Innovus scripting for a PV engineer
kicker: Part 3 · Innovus database Tcl · about 2 weeks
lede: Innovus is the place-and-route tool, not the sign-off checker. But the layout you verify is born there, and most violations are fixed there. A PV engineer who can open the design database, ask it questions in Tcl and hand the block owner an exact instance or net is worth far more than one who can only send screenshots.

<h2 id="help">Three commands that make every other command findable</h2>
<<<innovus | Works in any Tcl-based tool, because it is plain Tcl
info commands *Drc*          ;# every command with "Drc" in the name
info commands *stream*
info commands dbGet*
>>>
<<<innovus | The tool's own help
help verify*                 ;# list commands matching a pattern
man streamOut                ;# full description and options of one command
>>>
<<<innovus | Ask the database what it knows
dbGet top.?                  ;# attribute names of the design object
dbGet top.??                 ;# attribute names with their current values
dbGet top.insts.?h           ;# attribute names with a help line each
dbSchema                     ;# the whole object model
>>>
<p>With these you never need to trust a web page, including this one. If an attribute name below does not exist in your version, <code>.?</code> on the same object shows you what it is called there.</p>

<h2 id="ui">Two command languages in one tool</h2>
<p>Innovus can start in two modes, and scripts for one do not run in the other.</p>
<div class="tablewrap"><table>
<tr><th></th><th>Legacy interface</th><th>Common UI ("stylus")</th></tr>
<tr><td>Started by</td><td>default <code>innovus</code></td><td><code>innovus -stylus</code></td></tr>
<tr><td>Command style</td><td>camelCase: <code>streamOut</code>, <code>saveNetlist</code>, <code>verifyConnectivity</code></td><td>snake_case, shared with Genus and Tempus</td></tr>
<tr><td>Database access</td><td><code>dbGet</code> / <code>dbSet</code></td><td><code>get_db</code> / <code>set_db</code></td></tr>
</table></div>
<p>Ask your team which one the flow uses before you write anything. A quick test in a session: if <code>info commands get_db</code> returns a name, you are in the common UI. This page teaches the legacy <code>dbGet</code> first, because most existing PV helper scripts use it, and gives the <code>get_db</code> idea at the end.</p>

<h2 id="dbget">dbGet: the mental model</h2>
<p>The design is a tree of objects. Each object has attributes. Some attributes are plain values (a name, a box), and some are other objects (an instance's cell, a net's terminals). You walk the tree with dots.</p>
<div class="tablewrap"><table>
<tr><th>Start</th><th>Means</th></tr>
<tr><td><code>top</code></td><td>the design: its instances, nets, pins, floorplan, markers</td></tr>
<tr><td><code>head</code></td><td>technology and libraries: layers, library cells, units</td></tr>
<tr><td><code>selected</code></td><td>whatever is selected in the layout window right now</td></tr>
</table></div>
<<<innovus | Walking the tree (forms seen in Cadence community threads)
dbGet top.insts.name                              ;# names of all instances (huge on a real block)
dbGet -u top.insts.cell.name                      ;# cell types used, duplicates removed
dbGet selected.??                                 ;# everything about the selected object
dbGet [dbGet -p top.insts.pStatus unplaced].name  ;# names of unplaced instances
>>>
<h3>The four options you need</h3>
<div class="tablewrap"><table>
<tr><th>Option</th><th>What it does</th><th>Example</th></tr>
<tr><td><code>-p</code></td><td>return the <em>objects</em> whose attribute matches, not the attribute values. This is the filter.</td><td class="wrap"><code>dbGet -p top.insts.name u_core/*</code></td></tr>
<tr><td><code>-u</code></td><td>unique values only</td><td class="wrap"><code>dbGet -u top.insts.cell.name</code></td></tr>
<tr><td><code>-e</code></td><td>return an empty list when nothing matches (without it you get the text <code>0x0</code>, which a <code>foreach</code> treats as one item)</td><td class="wrap"><code>dbGet -e -p top.insts.pStatus unplaced</code></td></tr>
<tr><td>pattern as last word</td><td>keep values matching a wildcard pattern</td><td class="wrap"><code>dbGet top.nets.name *clk*</code></td></tr>
</table></div>
<div class="box trap"><strong>Trap: <code>0x0</code>.</strong> When nothing matches, plain <code>dbGet</code> returns the text <code>0x0</code>. <code>llength</code> of that is 1, so "count the unplaced cells" reports one when there are none, and a <code>foreach</code> runs once with a value that is not an object. Use <code>-e</code> whenever you will count or loop over the result, and test for "nothing found" with <code>if {[llength $result] == 0}</code>. Do not write <code>if {$result}</code>: an empty string is not a valid true/false value in Tcl and raises an error.</div>
<h3>Reading it as English</h3>
<p><code>dbGet [dbGet -p top.insts.pStatus unplaced].name</code> reads from the inside out: "among all instances, give me the <em>objects</em> whose placement status is unplaced; then give me the names of those objects". Almost every useful query has this two-step shape: filter to objects with <code>-p</code>, then ask those objects for something.</p>
<p><code>dbSet</code> writes with the same path style, for example changing a placement status on a filtered set of objects. Writing changes the design, so do it only on a copy until you know the command well.</p>

<h2 id="recipes">Recipes</h2>
<p>Each recipe is ordinary Tcl wrapped around one or two <code>dbGet</code> calls. I ran the Tcl logic of all seven recipes in <code>tclsh</code> with a fake <code>dbGet</code> that returns made-up data, so the loops and list handling work; that says nothing about the real attribute names. <code>pStatus</code>, <code>box</code>, <code>dbQuery -area … -objType inst</code>, <code>loadViolationReport -type Calibre -filename …</code> and the marker attributes <code>userOriginator</code>, <code>userType</code> and <code>box</code> appear in Cadence community threads and user scripts; the rest is from memory. Check every one with <code>.?</code> and <code>man</code>.</p>

<h3>1. How many of each cell?</h3>
<<<innovus | Filler, tap and endcap counts are the first thing to compare when LVS device counts differ
proc pv_cell_histogram {{pattern *}} {
    array set n {}
    foreach cell [dbGet -e top.insts.cell.name $pattern] {
        if {![info exists n($cell)]} { set n($cell) 0 }
        incr n($cell)
    }
    foreach cell [lsort [array names n]] {
        puts [format "%-30s %8d" $cell $n($cell)]
    }
}
pv_cell_histogram FILL*
pv_cell_histogram *TAP*
>>>

<h3>2. Anything not placed?</h3>
<<<innovus | Unplaced cells are streamed out at the origin or not at all, and cause shorts or missing devices
set objs [dbGet -e -p top.insts.pStatus unplaced]       ;# objects, or an empty list
puts "unplaced instances: [llength $objs]"
if {[llength $objs] > 0} {
    foreach name [lrange [dbGet $objs.name] 0 19] { puts "  $name" }
}
>>>

<h3>3. What sits under this DRC error box?</h3>
<<<innovus | Simple and slow version: test every instance box against the error box
proc pv_insts_in_box {llx lly urx ury} {
    set hits {}
    foreach inst [dbGet -e top.insts] {
        lassign [lindex [dbGet $inst.box] 0] x1 y1 x2 y2
        if {$x1 <= $urx && $llx <= $x2 && $y1 <= $ury && $lly <= $y2} {
            lappend hits [dbGet $inst.name]
        }
    }
    return $hits
}
puts [pv_insts_in_box 9.5 19.5 10.55 21.4]
>>>
<p>On a block with millions of instances this loop is too slow. The tool has an area query for exactly this. Cadence forum answers give it in this form, returning the instance objects in the box:</p>
<<<innovus | Fast version, as given in Cadence community answers; read "man dbQuery" for your version
proc pv_insts_in_box_fast {llx lly urx ury} {
    set objs [dbQuery -area [list $llx $lly $urx $ury] -objType inst]
    if {[llength $objs] == 0} { return {} }
    return [dbGet $objs.name]
}
>>>
<p>Writing the slow loop once is still worth it: it shows what the query does, and the same overlap test works in any tool.</p>

<h3>4. Walk the sign-off violations one by one</h3>
<p>The tested script <a href="ch05_script_bank.html#t-rdb"><code>rdb_to_tcl.tcl</code></a> turns a Calibre ASCII results file into a small Tcl file that sets <code>pv_viol</code> to a list of <code>{rule llx lly urx ury}</code>. Source it inside Innovus and step through the boxes:</p>
<<<innovus | zoomBox is the legacy zoom command as I remember it; confirm with: man zoomBox
source viol.tcl
set pv_i -1
proc pv_next {} {
    global pv_viol pv_i
    incr pv_i
    if {$pv_i >= [llength $pv_viol]} { puts "no more violations"; return }
    lassign [lindex $pv_viol $pv_i] rule llx lly urx ury
    zoomBox $llx $lly $urx $ury
    puts "[expr {$pv_i + 1}]/[llength $pv_viol]  $rule  at ($llx $lly) ($urx $ury)"
    puts "  instances: [pv_insts_in_box $llx $lly $urx $ury]"
}
pv_next          ;# call again for the next one, or bind it to a key
>>>

<h3>5. Count markers by rule</h3>
<p>Innovus can load sign-off results as violation markers. A user script quoted in the Cadence community does it with <code>clearDrc</code> followed by <code>loadViolationReport -type Calibre -filename &lt;file&gt;</code>, and a forum answer adds that the file must start with the design name and the units, which is the first line of the ASCII results database. Once they are markers, they are database objects like any other:</p>
<<<innovus | Attribute names as used in that community script (userOriginator, userType, box); confirm with: dbGet top.markers.?
clearDrc
loadViolationReport -type Calibre -filename top.drc.results

proc pv_marker_histogram {} {
    array set n {}
    foreach kind [dbGet -e [dbGet -e -p top.markers.userOriginator Calibre].userType] {
        if {![info exists n($kind)]} { set n($kind) 0 }
        incr n($kind)
    }
    foreach kind [lsort [array names n]] { puts [format "%-30s %6d" $kind $n($kind)] }
}
pv_marker_histogram
>>>

<h3>6. Which layers and units does the technology define?</h3>
<<<innovus | Useful before writing or checking a stream-out layer map
foreach layer [dbGet -e head.layers.name] { puts $layer }
puts "database units per micron: [dbGet head.dbUnits]"
>>>

<h3>7. One report procedure for the morning check</h3>
<<<innovus | Glue the pieces into one proc, write the answer to a file, call it from a batch run
proc pv_health {file} {
    set out [open $file w]
    puts $out "design      : [dbGet top.name]"
    puts $out "instances   : [llength [dbGet -e top.insts]]"
    puts $out "nets        : [llength [dbGet -e top.nets]]"
    puts $out "unplaced    : [llength [dbGet -e -p top.insts.pStatus unplaced]]"
    puts $out "markers     : [llength [dbGet -e top.markers]]"
    close $out
    puts "wrote $file"
}
pv_health pv_health.rpt
>>>
<p>Batch use is the pro step: a file <code>pv_check.tcl</code> that restores the design, sources your procs, calls them and exits, started with the tool's no-window and init-file options (see <code>innovus -help</code>). Then the same check runs on every block overnight.</p>

<h2 id="handoff">The hand-off to sign-off: where many false errors are born</h2>
<p>A large share of "DRC and LVS errors" on a first run are not layout errors. They are export mistakes. Scripted checks before the run save a full iteration.</p>
<div class="tablewrap"><table>
<tr><th>Symptom in Calibre</th><th>Usual export cause</th><th>Scripted check</th></tr>
<tr><td>Thousands of errors on a layer, or a layer completely empty</td><td>layer map sends two layers to one GDS number, or misses a layer</td><td><a href="ch05_script_bank.html#t-layermap"><code>layermap_check.tcl</code></a></td></tr>
<tr><td>Cells are empty boxes; LVS reports missing devices</td><td>cell GDS not in the merge list, so only the reference was written</td><td>list cells with <a href="ch04_calibre.html#drv">the layout viewer shell</a>, then <a href="ch05_script_bank.html#t-celldiff"><code>cell_diff.tcl</code></a></td></tr>
<tr><td>Top cell not found</td><td>stream-out top name differs from the name in the run file</td><td>generate run files from one list: <a href="ch05_script_bank.html#t-genruns"><code>gen_runs.tcl</code></a></td></tr>
<tr><td>LVS: extra instances in layout only</td><td>netlist written without fillers, taps, decaps</td><td>cell histogram (recipe 1) against the netlist cell list</td></tr>
<tr><td>LVS: power nets open or pins missing</td><td>netlist written without power and ground pins</td><td><a href="ch05_script_bank.html#p-cdl"><code>cdl_ports.pl</code></a></td></tr>
<tr><td>Everything shifted or scaled</td><td>database units in stream-out differ from the library GDS</td><td>compare units printed by recipe 6 with the library</td></tr>
</table></div>

<h2 id="getdb">If your team uses the common UI: get_db</h2>
<p>The idea is the same tree, with a different spelling. You name an object type, then attributes start with a dot, and filters are written as expressions.</p>
<<<innovus | Shapes of get_db queries, from memory: verify each with "help get_db" and "get_db insts .?" style queries
get_db insts .name                                        ;# all instance names
get_db insts -if {.place_status == unplaced}              ;# filtered objects
get_db [get_db insts -if {.base_cell.name == FILL*}] .name
get_db selected .bbox
>>>
<p>A Cadence application note on moving from the legacy interface to the common UI pairs, among others, <code>verify_drc</code> with <code>check_drc</code>, <code>verify_connectivity</code> with <code>check_connectivity</code>, <code>saveNetlist</code> with <code>write_netlist</code> and <code>saveDesign</code> with <code>write_db</code>. I have not confirmed a one-to-one table between <code>dbGet</code> attributes and <code>get_db</code> attributes, so I am not printing one. Cadence publishes a rapid adoption kit about <code>get_db</code> on its support site (login needed); that is the right source.</p>

<h2 id="practice">Practice</h2>
<ol>
<li>In a restored design, run <code>dbGet top.?</code>, then pick five attributes and follow each one level down with <code>.?</code>. Draw the tree on paper.</li>
<li>Type recipe 1. Then change it to print only cells with more than 1000 instances, sorted by count.</li>
<li>Select one instance in the window and print its name, cell, box and placement status in one line using <code>selected</code>.</li>
<li>Run <code>rdb_to_tcl.tcl</code> on a results file from your own block and step through the first ten violations with recipe 4.</li>
<li>Replace the slow loop in recipe 3 with the tool's area query, and time both with <code>time {...}</code>.</li>
<li>Put all your procs in <code>pv_procs.tcl</code> inside <code>namespace eval pv</code>, and load it from your start-up file.</li>
</ol>
