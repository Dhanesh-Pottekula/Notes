title: Scripting around Calibre: runs, rule files and results
kicker: Part 4 · Calibre automation · about 2 weeks
lede: Running one DRC job from the GUI is easy. The job you are paid for is running DRC, LVS, antenna and ERC on forty blocks every night, knowing by nine o'clock which ones moved, and never signing off on a broken run. That is all scripting: generate the run files, launch, check the logs, read the results.
---

<h2 id="header">The control file: a ten-line header around the foundry deck</h2>
<p>The foundry deck does not know your block. You tell Calibre the layout, the top cell and where to put results in a small file of your own that ends by including the deck. This is the file the practice script <a href="ch05_script_bank.html#t-genruns"><code>gen_runs.tcl</code></a> generates. This is what it wrote for one block:</p>
<<<svrf | Output of gen_runs.tcl for block blkC (statements from memory of SVRF: confirm in the SVRF manual)
// generated by gen_runs.tcl - do not edit by hand
LAYOUT SYSTEM GDSII
LAYOUT PATH    "/proj/demo/gds/blkC.gds"
LAYOUT PRIMARY "blkC_top"
DRC RESULTS DATABASE "blkC.drc.results" ASCII
DRC SUMMARY REPORT   "blkC.drc.summary" REPLACE HIER
DRC MAXIMUM RESULTS 1000
INCLUDE "/path/to/foundry/drc.deck"
>>>
<h3>Statements worth knowing by heart</h3>
<div class="tablewrap"><table>
<tr><th>Statement</th><th>Controls</th></tr>
<tr><td><code>LAYOUT PATH</code>, <code>LAYOUT PRIMARY</code>, <code>LAYOUT SYSTEM</code></td><td>which file, which top cell, GDSII or OASIS</td></tr>
<tr><td><code>DRC RESULTS DATABASE</code></td><td>name and format of the violations file. ASCII is readable by scripts.</td></tr>
<tr><td><code>DRC SUMMARY REPORT</code></td><td>name of the per-rule count report; the HIER keyword adds the by-cell section</td></tr>
<tr><td><code>DRC MAXIMUM RESULTS</code></td><td>cap per rule. A count equal to the cap means "at least this many", not the true number.</td></tr>
<tr><td><code>DRC SELECT CHECK</code> / <code>DRC UNSELECT CHECK</code></td><td>run only some rules, or skip some: fast reruns while fixing one rule</td></tr>
<tr><td><code>SOURCE PATH</code>, <code>SOURCE PRIMARY</code>, <code>SOURCE SYSTEM</code></td><td>LVS: the schematic netlist and its top</td></tr>
<tr><td><code>LVS REPORT</code></td><td>LVS: report file name</td></tr>
<tr><td><code>MASK SVDB DIRECTORY</code></td><td>LVS: database for cross-probing in the results viewer</td></tr>
<tr><td><code>LVS BOX</code></td><td>LVS: treat a cell as a black box (hard macros, analog IP)</td></tr>
<tr><td><code>INCLUDE</code></td><td>pull in the foundry deck or a shared settings file</td></tr>
<tr><td><code>#DEFINE</code> with <code>#IFDEF</code> … <code>#ENDIF</code></td><td>switches the foundry gives you (metal stack option, full-chip or block, with or without density)</td></tr>
</table></div>
<div class="box trap"><strong>Trap: the wrong switch is a silent wrong sign-off.</strong> Decks have switches such as "block level" versus "chip level", metal-stack choice, and "skip density". A run with the wrong switch finishes clean and means nothing. Put the switches in your generator script, from one project settings file, so nobody types them by hand. Write the switch values into your status report.</div>
<div class="box trap"><strong>Trap: the result cap.</strong> If a rule shows exactly the maximum count (1000 in the sample), the real number is unknown. A script that compares runs should flag "count = cap" and not report "same as yesterday".</div>

<h2 id="launch">Launching</h2>
<<<shell | Common batch forms, from memory. Run "calibre -help" and read the manual for your version
calibre -drc -hier -turbo 8 _drc_blkA.svrf  > blkA.drc.log 2>&1
calibre -lvs -hier -turbo 8 _lvs_blkA.svrf  > blkA.lvs.log 2>&1
calibre -rve -drc blkA.drc.results          # open the results viewer on a finished run
>>>
<p>The other common style is a <strong>runset</strong>: a text file saved from the Calibre Interactive GUI that holds the same settings as key and value lines, and can be run without the window. An open-source PDK ships one, and its launcher script runs it in batch like this:</p>
<<<shell | Runset lines and the batch command, as found in open-source SkyWater PDK libraries
# lines from a DRC runset file: one setting per line
*drcRulesFile: ${PDK_HOME}/DRC/Calibre/s8_drcRules
*drcRunDir: ${BAG_WORK_DIR}/calibre_run/drc/myLib/myCell
*drcLayoutPaths: myCell.calibre.db
*drcLayoutPrimary: myCell
*drcResultsFile: myCell.drc.results
*drcSummaryFile: myCell.drc.summary

# run a runset without opening the window
calibre -gui -drc -runset $RUNSET_DIR/s8_drc_runset -batch > $LOG/s8_drc_runset.log 2>&1
>>>
<p>Because a runset is plain <code>*key: value</code> text, a ten-line Perl or Tcl script can produce one per block from a template, exactly like the control-file generator.</p>
<h3>Rules for launch scripts</h3>
<ul>
<li><strong>One directory per block per run.</strong> Never let two runs write into the same directory.</li>
<li><strong>Keep the log.</strong> Redirect both output streams to a file named after the block.</li>
<li><strong>Record the inputs.</strong> Write the layout path, its date, the deck version and the switch values into the run directory. Three weeks later someone will ask.</li>
<li><strong>Check that it finished.</strong> No summary file, or a log without a completion line, is a failed run, not a clean block. <a href="ch05_script_bank.html#p-logscan"><code>log_scan.pl</code></a> does this.</li>
<li><strong>Stale results.</strong> If the summary is older than the layout file, the result belongs to an old layout. Compare the two times with <code>file mtime</code> in Tcl or <code>-M</code> in Perl.</li>
<li><strong>Do not fill the licence pool.</strong> Launch through your farm's queue command and limit how many jobs run together.</li>
</ul>

<h2 id="summary">Reading the DRC summary</h2>
<p>The section you need starts at the header <code>RULECHECK RESULTS STATISTICS</code> and ends at the next long dashed line. Each line has a rule name, dots, and two numbers.</p>
{{fixture:top.drc.summary|15-36}}
<ul>
<li>The line shape <code>RULECHECK name ... TOTAL Result Count = N (M)</code> is confirmed: an open-source sign-off script for real shuttle runs uses a regular expression of exactly this form and stops at the dashed line, as the practice scripts do.</li>
<li>The two numbers: as I remember it, the first is the count as Calibre stored it in a hierarchical run and the number in brackets is the flat count (each error counted in every placement of its cell). In the sample, 15 errors inside a memory bit cell become 240 flat. Confirm the meaning in the manual before you quote either number in a report, and always say which one you quote.</li>
<li>The by-cell section repeats the rules, indented. A careless pattern counts everything twice.</li>
</ul>

<h2 id="rdb">Reading the ASCII results database</h2>
<p>The layout below matches what KLayout's open-source reader for this format expects (KLayout is a free layout viewer that can load these files). The sample file itself is written by hand for practice.</p>
{{fixture:top.drc.results|1-16}}
<ol>
<li><strong>Line 1:</strong> top cell name and precision (database units per micron). Every coordinate below is an integer; divide by the precision to get microns.</li>
<li><strong>Per rule:</strong> a line with the rule name, then a line with counts and the date. The third number on that line says how many lines of rule text follow.</li>
<li><strong>Per result:</strong> <code>p <em>number</em> <em>vertices</em></code> for a polygon, followed by one <code>x y</code> line per vertex; or <code>e <em>number</em> <em>edges</em></code> for an edge cluster, followed by one <code>x1 y1 x2 y2</code> line per edge.</li>
</ol>
<p>Real files carry one more thing the sample does not have: <strong>property lines</strong> between a result's header and its coordinates. They start with a letter. The important one is <code>CN</code>, which names the cell a result was reported in; its coordinates are then in that cell's own space, not in top-level space. The practice readers in <code>PVReport.pm</code> and <code>pvlib.tcl</code> skip property lines (tested with a file that has them) and stop with an error when the file ends in the middle of a result. So for hierarchical results they give you cell-local boxes. Placing those at top level is practice task 4 below; the simple way out is to ask Calibre for flat, top-level coordinates in the results database, which the manual describes.</p>
<p>With coordinates in hand you can do things the viewer cannot do quickly: <a href="ch05_script_bank.html#p-hotspot">cluster violations into hotspot windows</a>, <a href="ch05_script_bank.html#p-rdb">export a CSV</a>, or <a href="ch05_script_bank.html#t-rdb">hand boxes to Innovus</a>.</p>

<h2 id="lvs">Reading the LVS report</h2>
<p>An LVS report is long, but triage needs only four things, in this order: the verdict in the box of <code>#</code> signs, the <code>Error:</code> and <code>Warning:</code> lines under it, the list of incorrect cells, and the object-count table where a star marks a mismatch.</p>
{{fixture:top.lvs.report|14-44}}
<p>The sample is a trimmed lookalike written for practice. The debugging order it teaches is real: fix the lowest incorrect cell first, because one broken leaf cell makes every parent incorrect; and look at count mismatches before connectivity details, because a missing device or an extra net explains a hundred lines of discrepancy. Script: <a href="ch05_script_bank.html#p-lvs"><code>lvs_triage.pl</code></a>.</p>
<div class="tablewrap"><table>
<tr><th>Report says</th><th>First things to check</th></tr>
<tr><td>More nets in layout than source</td><td>an open: a net split in two (missing via, text on only one piece, broken power strap)</td></tr>
<tr><td>Fewer nets in layout than source</td><td>a short: two nets joined (overlap, wrong text label, well tied wrong)</td></tr>
<tr><td>Extra layout instances</td><td>physical-only cells with devices (decaps, some fillers) missing from the netlist</td></tr>
<tr><td>Missing ports</td><td>pin text missing, on the wrong layer, or not at top level</td></tr>
<tr><td>Property errors only</td><td>device sizes differ: wrong cell version, or extraction switch</td></tr>
</table></div>

<h2 id="tvf">TVF: when the rule file itself is Tcl</h2>
<p>SVRF has no loops. TVF (Tcl Verification Format) lets a rule file be a Tcl program that prints SVRF, so one loop can produce the same check for ten metal layers. You will mostly <em>read</em> TVF in foundry decks and in your CAD team's waiver and density utilities. The shape, from memory:</p>
<<<calibre | Sketch of a TVF file. Command names (tvf::VERBATIM, tvf::RULECHECK, tvf::OUTLAYER, tvf::COMMENT) are from memory: read the TVF chapter of the SVRF manual before using them
#! tvf
namespace import tvf::*

VERBATIM {
    LAYER M1 31
    LAYER M2 32
}

# plain Tcl decides what gets written
foreach {layer space} {M1 0.07 M2 0.07} {
    RULECHECK "$layer.S.demo" {
        COMMENT "$layer spacing must be >= $space um"
        OUTLAYER "EXT $layer < $space ABUT<90 SINGULAR REGION"
    }
}
>>>
<p>The skill that matters here is the plain Tcl from Part 1: lists, <code>foreach</code>, string building and quoting. If you can read the loop above, you can read a foundry's TVF.</p>

<h2 id="drv">The layout viewer's Tcl shell</h2>
<p>Calibre's layout viewer has a batch Tcl shell (<code>calibredrv</code>) that can open a GDS or OASIS file and answer questions without a window: list the cells, the layers, the top cell, the bounding box, or merge files. It is the right tool for pre-run checks. The shape of a session, from memory:</p>
<<<calibre | Sketch only: the object-style commands are from memory. See the Calibre DESIGNrev reference manual, batch commands chapter
set L [layout create top.gds]          ;# load a layout, get a handle
puts "top cell : [$L topcell]"
puts "cells    : [llength [$L cells]]"
puts "layers   : [$L layers]"

set out [open gds_cells.txt w]
foreach c [$L cells] { puts $out $c }
close $out
>>>
<p>That last loop writes the cell list that <a href="ch05_script_bank.html#t-celldiff"><code>cell_diff.tcl</code></a> compares against your library list, which catches "cell reference without a definition" before a four-hour run does.</p>

<h2 id="daily">Putting it together: the nightly loop</h2>
<ol>
<li><strong>Pre-check</strong> each block: layout file exists and is fresh, top cell present, layer map sane, netlist ports match. Stop bad blocks here.</li>
<li><strong>Generate</strong> a run directory and control file per block from one list and one template.</li>
<li><strong>Launch</strong> through the farm, with a limit on parallel jobs.</li>
<li><strong>Scan logs</strong>: finished or not, errors, run time.</li>
<li><strong>Summarise</strong> each block: counts per rule after waivers.</li>
<li><strong>Compare</strong> with the previous night: new, worse, fixed.</li>
<li><strong>Publish</strong> one table: block, DRC open rules, LVS verdict, antenna, run time, change since yesterday.</li>
</ol>
<p>Each step is one script in the <a href="ch05_script_bank.html">script bank</a>. Building this chain for your own blocks, even in a small form, is the single best project to talk about in an interview.</p>

<h2 id="practice">Practice</h2>
<ol>
<li>Run <code>gen_runs.tcl</code> on a list of two of your own blocks in dry-run mode and read the generated files line by line against a control file your team uses.</li>
<li>Add a second template to it for LVS, chosen with an option.</li>
<li>Make <code>drc_compare.pl</code> flag any rule whose count equals the result cap.</li>
<li>Open a real ASCII results file and find the property lines. Extend <code>read_rdb</code> to keep the <code>CN</code> cell name with each violation, and print it as a column in <code>rdb_bbox.pl</code>.</li>
<li>Write <code>stale_check.pl</code>: for each run directory, warn if the summary is older than the layout file.</li>
<li>Write the "publish" step: one CSV with a line per block from the outputs of the other scripts.</li>
</ol>
