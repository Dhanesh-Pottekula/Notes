<h2 id="why">Why scripting is the fastest way up in PV</h2>
<ul>
<li>Running checks from a GUI is the entry-level skill. Everyone with one year of experience has it.</li>
<li>Product companies hire PV engineers to own sign-off for many blocks at once. That is only possible with automation: generated run files, nightly comparisons, waiver tracking, pre-run gates.</li>
<li>Job descriptions for PV roles ask again and again for Tcl, Perl or Python and shell automation next to Calibre.</li>
<li>In interviews, scripting questions are where candidates with the same tool experience separate. "I wrote the script my team uses every night" is a stronger sentence than any tool name.</li>
</ul>

<h2 id="plan">The 12-week plan</h2>
<p>Time: one hour on weekdays, two to three hours on one weekend day. The rule for every week: <strong>type, do not copy</strong>, and end the week with one small script of your own that did not exist on Monday.</p>

<div class="stage"><span class="stage-n">Before week 1 · two evenings</span>
<h3>Set up a place to practise</h3>
<ul>
<li>A Linux shell with <code>tclsh</code> and <code>perl</code> (your work machine, or any Linux or Mac at home). No EDA licence needed for weeks 1 to 6.</li>
<li>Copy this guide's <code>scripts</code> and <code>fixtures</code> folders and run <code>./run_all.sh</code>.</li>
<li>Shell basics you must already be quick at: <code>cd ls cp mv rm mkdir</code>, <code>grep</code>, <code>less</code>, <code>head tail</code>, <code>wc</code>, <code>sort uniq</code>, pipes and redirects (<code>|</code>, <code>&gt;</code>, <code>2&gt;&amp;1</code>), <code>chmod +x</code>, environment variables. If these are slow, spend week 0 on them.</li>
<li>A text editor you can drive without the mouse (vim or gvim is on every EDA machine).</li>
</ul>
<p><strong>Checkpoint:</strong> all sixteen scripts run and print the same output as the script-bank page.</p></div>

<div class="stage"><span class="stage-n">Stage 1 · weeks 1–3</span>
<h3>Tcl</h3>
<ul>
<li><strong>Week 1:</strong> substitution and quoting, variables, <code>expr</code>, strings, <code>regexp</code>. (<a href="ch01_tcl.html#rule">Tcl page</a>, first four sections.) Official Tcl tutorial lessons alongside.</li>
<li><strong>Week 2:</strong> lists, arrays, dicts, control flow, procs. Script-bank scripts 2, 6, 7.</li>
<li><strong>Week 3:</strong> files, <code>exec</code>, <code>catch</code>, namespaces, a personal library with tests. Scripts 13, 14, 15.</li>
</ul>
<p><strong>Checkpoint:</strong> without looking anything up, write a script that reads a DRC summary and prints failing rules sorted by count. Then explain the difference between <code>"..."</code> and <code>{...}</code> to a colleague.</p></div>

<div class="stage"><span class="stage-n">Stage 2 · weeks 4–6</span>
<h3>Perl</h3>
<ul>
<li><strong>Week 4:</strong> scalars, arrays, hashes, <code>sort grep map</code>, regular expressions. Scripts 1 and 5. Ten one-liners on your own logs.</li>
<li><strong>Week 5:</strong> files, references and nested data, subroutines. Scripts 3, 4, 8.</li>
<li><strong>Week 6:</strong> state-machine parsing, modules, options, exit codes. Scripts 9 to 12.</li>
</ul>
<p><strong>Checkpoint:</strong> take a report format you have never parsed (an antenna report, an ERC summary, a density report) and write a summary script for it in under an hour.</p></div>

<div class="stage"><span class="stage-n">Stage 3 · weeks 7–8</span>
<h3>Innovus database scripting</h3>
<ul>
<li><strong>Week 7:</strong> the three self-help commands, the object tree, <code>dbGet</code> with <code>-p -u -e</code>, recipes 1 to 3. Do this in a real session on a saved design copy.</li>
<li><strong>Week 8:</strong> violations as data: recipes 4 to 7, the stream-out and netlist hand-off table, a start-up file that loads your procs. If your team uses the common UI, redo the recipes with <code>get_db</code>.</li>
</ul>
<p><strong>Checkpoint:</strong> given the coordinates of a DRC error, you can name the instances and nets involved in under a minute, from the command line.</p></div>

<div class="stage"><span class="stage-n">Stage 4 · weeks 9–10</span>
<h3>Calibre automation</h3>
<ul>
<li><strong>Week 9:</strong> control files, deck switches, batch launch, runsets, log checking. Adapt <code>gen_runs.tcl</code> and <code>log_scan.pl</code> to your project's real formats.</li>
<li><strong>Week 10:</strong> results: summary, ASCII results database, LVS report. Adapt the parsers to your real files. Read one TVF file from your deck and explain its loops.</li>
</ul>
<p><strong>Checkpoint:</strong> one command sets up, launches (or dry-runs) and summarises DRC for two blocks.</p></div>

<div class="stage"><span class="stage-n">Stage 5 · weeks 11–12</span>
<h3>One real project, and interview preparation</h3>
<ul>
<li>Build one project from the <a href="ch05_script_bank.html#next">project list</a> for your own team, and get one colleague to use it. The nightly dashboard is the best first choice.</li>
<li>Write a half-page note: the problem, what the script does, time saved per week, one bug you found.</li>
<li>Work through the <a href="ch06_interview.html">interview questions</a> out loud, on paper first, then check in the shell.</li>
</ul>
<p><strong>Checkpoint:</strong> you can describe your project in two minutes, and write "count occurrences of each word in a file" in both languages on a whiteboard.</p></div>

<div class="stage"><span class="stage-n">After week 12</span>
<h3>Keep going</h3>
<ul>
<li><strong>Python.</strong> New flow code in many companies is Python. With Perl in your hands it takes two to three weeks: same hashes (dicts), same regular expressions, cleaner modules. Port three scripts from the bank.</li>
<li><strong>SVRF and TVF rule writing</strong>, so you can read a deck and write a debug rule.</li>
<li><strong>Makefiles and your company's job scheduler</strong>, to chain steps and rerun only what changed.</li>
<li><strong>Git</strong> for your scripts: every sign-off utility needs history and review.</li>
</ul></div>

<h2 id="rules">Five working rules</h2>
<ol>
<li><strong>Never take design data, decks or reports out of the company network.</strong> Practise on the sample files here and on open-source designs at home; apply the scripts to real data only at work.</li>
<li><strong>A script that can be wrong silently is worse than no script.</strong> Fail on empty input, print what you parsed, test on a file where you know the answer.</li>
<li><strong>Dry run first.</strong> Anything that launches jobs, deletes files or changes a design shows its plan before it acts.</li>
<li><strong>Keep scripts in version control</strong> and have one colleague read each one.</li>
<li><strong>The manual for your tool version beats every web page, including this one.</strong></li>
</ol>
